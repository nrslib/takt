## 変更する引き継ぎ

- `development-implement` の固定・動的・team 各版は、有効な計画の残件を同じ工程へ返す。実行可能な次の手段がない場合には、その根拠を伴って停止する。既存の最大ステップ数は変更しない。
- `development-remediation` の各版と共有の `review-remediation` は、`fix-plan → investigate → fix-plan` を持つ。調査対象は現在採用されている指摘に限定し、未確定の原因による本番修正はしない。反復調査は既存の loop monitor で監視する。
- `fix-investigation.md` は実験条件、コマンド、反復回数、観測値、否定した仮説、残件、一時的な変更を引き継ぐ。
- 実装証跡を引き継ぐ際は、元の実行記録と対象の同一性を記録する。失敗、未実行、同一性不明、影響する変更がある結果は成功として引き継がない。工程ごとの再実行が明示されていれば従う。
- 受入条件保持の手順は `preserve-acceptance-conditions.md` に集約し、実装・再計画・修正・裁定・検証で合成する。同じ修正計画へ二重に注入しない。

## 検証方法と限界

`development-loop-routing.integration.test.ts` は配布用の定義とファセットを実際のローダーで解決し、エンジンで継続・再計画・停止・局所調査の往復を検証する。エージェントと意味判定はテストダブルなので、モデルの判断精度を証明するものではない。

`eval/cases/completion-scope-routing.yaml` に、実行記録から抽出した smoke 残件、局所調査、観測能力の不足と対照例を追加した。日本語・英語の Phase 3 プロンプトは配布 YAML から生成する。タグ形式と構造化形式の両評価で使用できる。

実モデルでは固定14ケース×日英×新旧を Claude Opus 5、Codex Astra xhigh、Kimi Code k3 で比較し、各モデルの期待遷移一致が旧12/28から新28/28へ変わった。自己ラベルが事実と矛盾する追加対照も、各モデル旧0/2から新2/2へ変わった。タグ番号を比較するだけでなく、本番のタグパーサーと各版YAMLの `next` / `return` で判定した。実ログ由来の入力は全文再生ではなく、確認事実を要約した資料である。

実行条件、再採点の経緯、証跡、評価範囲は [評価記録](../../eval/results/development-loop-handoffs.md) を参照。526分の元タスク全体は再実行しておらず、収束回数や時間の削減は未測定である。

1. B〜E に渡す型と口

維持:
  core/daemon/events.ts の EventInput / AcceptedEvent / Admission / ControlEvent / TurnIdentity
  （TurnIdentity の定義場所は messages.ts）。採番・重複排除・human 優先・世代照合は維持。
  core/daemon/ports.ts の EventStore / StoredEvent / TurnQueues と turnQueues 実装。
  core/daemon/io.ts の IoOptions / AsyncLock / CommandPort / ProcessObservation / ProcessPort。
  eventId または conversationId/requestId で atomic に重複排除。
  restore は lastAcceptedSequence と queued/running/settling の AsyncIterable。
  running は interrupted として保存。settling は保存済み結果だけを再反映。AI 再実行なし。

発言ごとの上書き指定:
  TurnEvent.human_command は agentOverrides?: AssistantCliOverrides {provider?,model?} を持つ。
  F は接続の ConversationOpen.agentOverrides を各 human_command に固定する。
  B は AcceptedEvent 全体を保存し、restore/duplicate でも発言ごとの指定を保持する。
  A は設定を解決せず、TurnStart.event のまま C に渡す。
  start_turn は既存 ConversationAgentOverridesSchema で provider/model と strict shape を検証する。
  C は message の準備・runtime 解決にその指定を渡す。省略時は従来どおり設定から解決する。
  state.session の provider/model は保存済み session の識別であり、発言の指定を代替しない。
  director_message と inquiry_answer は従来どおり発言の上書きを使わない。

messages.ts の新契約:
  ConversationSession { provider, model: string|null, sessionId: string|null }
  ConversationTurnState { version, assignment, session, revision, pending, approval }
  version はすべての条件付き会話保存で増やす版。提案の revision とは別。
  ConversationChange { operationId, expectedVersion, session?, proposal?: {revision,pending}, approval? }
  null は明示的な削除。省略は変更なし。最低1項目の変更が必要。
  保存対象の conversationId は外側の TurnIdentity に固定。assignment/path/状態全体の更新は不可。
  change.operationId は複数の保存を区別する冪等 ID。turn.operationId はターンの ID。
  TurnStart { event: AcceptedEvent, turn: TurnIdentity, state: ConversationTurnState }
  TurnOutcome は completed(result) / failed(message) / interrupted、各々に change? を持つ。
  現ターンの interrupted.change は中断後も反映する。中断済みの completed/failed は変更ごと破棄。
  operationId/generation が違う通知は、終了種別にかかわらず無視する。
  TurnResult は TurnIdentity + event + outcome。変更の適用と必要な版は change に保存する。
  RuntimeMessage は turn_progress / turn_finished のまま。
  ConversationSnapshot は SnapshotRead + generation + turnState。
  items は遅延生成。dispatcher は turnState を読み、items を走査せず cancel() する。
  UI 用 SnapshotRead の AsyncIterable / 関数と turnState の中身を子 IPC にそのまま送らない。

ports.ts の新契約:
  ConversationOwner: apply(result), progress(turn,message), snapshot(conversationId)
    prepare は削除。daemon は業務の準備も設定解決も行わない。
    snapshot の戻り値は ConversationSnapshot から operationId/generation を除いた保存側の値。
    dispatcher.snapshot が読取完了時の現ターンの operationId/generation を付け、非実行時は null。
  TurnRunner: start(input: TurnStart, signal): void,
    resultCommitted(turn): void, interrupt(turn): void, close(): Promise<void>
    start は子の初期化やターン完了を待たず、全終端を bus.post(turn_finished) で通知。
    resultCommitted は saveResult → apply → markSettled が完了した後、次ターン開始前に呼ぶ。
    復元結果にも呼ばれる。C は該当する生存子がなければ送信不要として扱う。
    close は IPC の shutdown_complete だけでは完了にしない。実プロセス終了を確認する。
  DaemonStateOwner: handle(turn, request: DaemonStateRequest, signal): Promise<DaemonStateReply>
  DaemonBus: post(message): Promise<void>, request(turn,request,signal): Promise<DaemonStateReply>
    request は独立して非同期に処理し、2本のモデル用キューに入れない。
    dispatcher は現ターンの対象・operationId・generation・中断・停止を照合する。
    状態所有者は保存確定前に signal と期待版・重複を検証する。
    要求はターン単位で保持。通常終了でも取消し、全要求の副作用・後始末の完了を待って結果反映。
    取消より前に保存が確定していた要求は成功を返してよいが、Promise 完了後の副作用は禁止。
  DaemonResources.close は通信・監視だけを終了。ターン子の所有者は runner に一元化。
    停止は新規受付拒否 → 現ターンと要求の取消 → runner.close による子の終了確認
    → 要求の後始末・受付/結果保存の完了 → resources.close の順。保存失敗は停止成功にしない。
    停止開始時点の受付の結果も保持し、rejected(storage) があれば close 後に停止を失敗とする。
  DispatcherDependencies: store / conversations / runner / stateRequests / resources /
    limits {maxPendingEvents,maxPendingBytes} / onFailure。
  retryStorage と drain は維持。drain は受付・状態読取・結果保存を待ち、実行中の子を待たない。

processProtocol.ts:
  DaemonProcessMessage / TurnProcessMessage、DaemonStateRequest / DaemonStateReply。
  parseDaemonProcessMessage(value: unknown, launchId) / parseTurnProcessMessage(value: unknown, launchId)。
  起動 ID の照合、protocolVersion=1、正方向のメッセージ、strict shape、JSON データを検証。
  ターン用メッセージは TurnIdentity、要求/応答は通信専用 requestId を必須とする。
  start_turn は event と turn の conversationId/operationId、event の lane を相互検証。
  関数・AbortSignal・AsyncIterable・SnapshotRead・任意 path/状態全体は送信不可。
  件数/バイト上限:
    MAX_PROCESS_MESSAGE_BYTES = 1 MiB（JSON の UTF-8、エスケープ込み）
    MAX_PROCESS_PENDING_REQUESTS = 32（会話子1つの保留通信）
    MAX_PROCESS_PENDING_BYTES = 1 MiB（保留分の合計）
    MAX_PROCESS_PROGRESS_BYTES = 16 KiB
    MAX_PROCESS_DELIVERY_PORTS = 32
    ID / requestId は 1〜128文字。構造は深さ32・65536ノードまで。
  processRequestBytes(pendingCount,pendingBytes,message) は送信予約前の上限検証と必要バイト数。
  C が送受信で parse を呼び、保留数/バイト数を予約し、reply/切断/取消で解放する。
  この関数は pending registry や送信処理の実装ではない。

通信表（全件 protocolVersion と launchId 付き）:
  daemon → 子 initialize(conversationId,assignment,configDirectory)
  子 → daemon ready
  daemon → 子 start_turn(input: TurnStart)
  子 → daemon turn_progress(turn,message)
  子 → daemon turn_finished(turn,outcome)
  daemon → 子 result_committed(turn)
  daemon → 子 interrupt(turn)
  daemon → 子 shutdown
  子 → daemon shutdown_complete
  子 → daemon daemon_request(turn,requestId,request)
  daemon → 子 daemon_reply(turn,requestId,reply)

状態要求は次の4種類だけ:
  save_conversation(change)
    応答 state_saved(version,duplicate)。期待版が違えば version_conflict。
    同じ会話/change.operationId の再送は、期待版の照合より先に同じ保存済み結果を返す。
    B は操作 ID が同じで内容が異なる再送を許さず、原子的に変更する。
    session/提案/承認の整合・現在の assignment との対応は B が保存境界で検証。
  accept_director_message(eventId,requestId,conversationId,occurredAt,text)
    応答 event_accepted(admission)。送信元は turn.conversationId から決め、永続受付を待つ。
  notify_director(notificationId,message,subject?)
    応答 notification_saved(notificationId)。通知 ID で冪等保存し TUI/Slack へ配送。
  get_delivery(conversationId)
    応答 delivery(conversationId,assignment,connectedPorts)。接続先の必要情報のみ。
  共通のエラー応答 error(code,message)。code は stale_turn / version_conflict /
    forbidden / capacity / storage / stopping。
  返信と requestId/turn の対応・状態操作の認可・副作用前の予約応答待ちは C/B/D の実装責任。

単位別の受け取り方:
  B: EventStore、版付き会話保存と変更反映の冪等性、非同期 I/O/owner/endpoint/lock/process。
     会話の唯一の書込主体は daemon。apply の保存失敗を成功にしない。
  C: app/daemon-turn/index.ts、features/daemonTurn/**、daemon/turnProcessHost.ts。
     prepare・文脈構築・AI・MCP・業務操作と認可を子へ集約。prepare 型は必要な子内だけで定義。
     initialize→ready→start_turn。会話子を再利用し、1子1ターン。
     途中の state_saved.version を取り込み、終了 change.expectedVersion に最新の版を使う。
     IPC 切断/exit/error を監督し、二重終了を抑制。失敗ターンは自動再実行しない。
     中断時は終了通知か強制終了確認前に同じ会話の次ターンを始めない。
     result_committed を受けるまで結果を保持する。終了結果と通知が競合しても1回だけ保存。
     古い launchId の通知/要求は bus へ配送しない。保留通信も切断時に解放。
     provider/MCP を終了し、detached な自動 run の寿命は巻き込まない。
  D: snapshot の turnState は小さい保存済みデータ、items は非同期かつ遅延。
     IPC/Slack の受付・snapshot・中断・配送を業務 Store から分離。
     notify_director/get_delivery の配送情報を所有し、業務実処理は子に送る。
  E: daemon 内で小さいファイルの非同期読取、非同期プロセス照会、上限付き gh だけを観測。
     大きい goals/tasks/log の全件解析は作らない。時計だけでモデルを呼ばない。
     watcher は EventInput/WatchObservation → Ingress.accept。DaemonResources.close で終了確認。
  A′最終統合: 新 runDaemon、CLI/lifecycle から専用入口の別プロセス起動、
     stateRequests の4種類を保存・Ingress・配送へ結線し、旧業務 import と旧起動経路を除去。
     禁止 lint の常時有効化は、この到達集合の禁止診断と解析課題を解消した後。

    不可。開始時は明示 DTO の turnState だけを渡す。UI snapshot の読取口は daemon に残す。
  - 第三のモデルキュー / 汎用 WorkerJobMap / domain_changed は追加しない。
  - 新 daemon 入口は await runDaemon() のみ。旧起動元の置換と runDaemon の組立は最終統合。

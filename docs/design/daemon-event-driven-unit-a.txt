1. B〜F に渡す型と口

src/core/daemon/events.ts
  HumanCommand / TaskRef / WatchObservation / TurnEvent / ControlEvent
  EventInput / AcceptedEvent / Admission / ControlReceipt
  人の発言・承認・取消・回答は human。それ以外は other。
  eventId は事実の ID、conversationId/requestId は送信再試行の ID。
  受け箱の eventId は同じファイルを再読込しても固定する。
  operationId と全体単調増加 acceptedSequence は A が最初の await 前に発行する。
  中断は conversationId / operationId / generation の一致が必要。
  入力検証・invalid 応答・利用者認証・宛先検証は F の入口で行う。

src/core/daemon/messages.ts
  TurnIdentity / PreparedTurn / PreparedOperation / TurnOutcome / TurnResult
  RuntimeMessage / ConversationSnapshot
  PreparedOperation は turn または completed。短い状態操作は provider を呼ばない。
  PreparedTurn は agent / cwd / assignment / prompt / instruction / sessionId。
  signal は start の別引数とし、保存する TurnResult へは含めない。
  TurnOutcome は completed（OperationResult、sessionId、summary、assignment）、failed、interrupted。
  RuntimeMessage は turn_progress と turn_finished だけ。
  ConversationSnapshot は既存 SnapshotRead に generation を追加する。
  F は read.conversationId / read.operationId / read.generation で中断対象を指定する。
  取消後の結果と、実行 ID / 世代の違う進捗・結果は A が無視する。

src/core/daemon/ports.ts
  DaemonIngress: accept(input), control(event), snapshot(conversationId)
  EventStore: accept(event), markStarted(eventId, turn), saveResult(eventId, result),
              markSettled(eventId, result), restore()
  TurnQueues: add, confirm, peekNext, markStarted, remove, pending
  ConversationOwner: prepare(event, turn, signal), apply(result), progress(turn, message), snapshot(id)
  TurnRunner: start(prepared, turn, signal), interrupt(turn), close()

B（保存）:
  accept に渡す AcceptedEvent は A で採番済み。B は順序を付け直さない。
  eventId または conversationId/requestId で atomic に重複排除する。
  accept の応答は stored または duplicate（元の event と永続状態）。
  公開後に応答だけ失敗しても、再送には元の event を返す。A は未開始の queued を回収する。
  restore は lastAcceptedSequence と pending の AsyncIterable を返す。
  high-water mark は保存の完了順ではなく sequence の最大値を保存する。
  pending は queued、running（turn 付き）、settling（result 付き）。終了済みは返さない。
  終了済みの重複排除情報は accept から検索できるよう保持する。
  markStarted → D.prepare → runner.start の順。開始保存失敗では provider を呼ばない。
  saveResult → D.apply → markSettled の順。各保存操作は冪等にする。
  saveResult は会話反映より先に結果を保存する。再起動時の provider 再実行を防ぐ。
  running の復元は interrupted、settling の復元は元の結果の保存・反映だけを行う。

C（業務所有者）:
  GoalRequest は既存 MCP schema の具体的な入力型を再利用する。
  登録、pause/resume/abort、task enqueue/requeue/retry/remove/stop/merge、PR、質問、
  作業記録、通知、ゴール読取、task 結果・goal イベント・監視結果・回答の反映を定義した。
  ProjectRequest は enqueue/cleanup/list/get_run/tell_run/list_workflows と workspace 操作。
  ToolRequest.target は goal / project。返答は既存 CallToolResult。
  認可・副作用・ゴール/タスク/共有 Git の排他は C が担当し、A は配送だけを行う。
  所有者は通知に他の所有者実装を import せず、Ingress / Bus を使用する。

D（会話・実行）:
  prepare の受付イベントだけで既存提案 revision・承認予約を変更しない。
  会話・session・提案・予約と結果の保存は D が所有する。
  apply は operationId / generation を識別し、同じ結果の再反映を冪等にする。
  runner.start は待たずに戻し、全終端で bus.post(turn_finished) を必ず発行する。
  interrupt は現在ターンだけ。待機イベントを消さない。
  runner.close は provider・所有子プロセスの終了と終了通知まで待つ。
  post は配送処理を await できる。保存失敗は A が結果を保持し DispatchFailure で報告する。
  MCP 要求は executeTool へ渡す。モデル用キューには入らず、自己待ちを起こさない。
  executeTool の signal には全体停止の取消も合成する。

E/F（監視・配送・停止）:
  E の観測事実は WatchObservation から Ingress.accept へ送る。
  F の業務 accepted は EventStore.accept の永続化後。provider 完了は待たない。
  停止は新規受付を止め、現在ターンと道具要求を取消し、受付・結果保存を待つ。
  待機中の accepted は保存したまま残す。新しいターンを開始しない。
  E/F は worker・MCP・所有子プロセスの終了確認を DaemonResources.close にまとめる。
  保存未完了や close 失敗を、停止成功として返さない。

src/core/daemon/io.ts
  IoOptions { signal, timeoutMs }
  AsyncLock.exclusive(path, action: () => Promise<T>, options): Promise<T>
  CommandRequest { executable, args, cwd, env, maxOutputBytes }
  CommandResult { code, signal, stdout, stderr, truncated }
  CommandPort.run(request, options): Promise<CommandResult>
  ProcessOwner { pid, startTime }
  ProcessObservation: alive(owner) / dead / unknown(reason)
  LaunchedProcess { owner, process: 既存 ManagedProcess }
  ProcessPort.inspect(owner, options), launch(request, options)
  CommandPort の取消・期限は子の終了確認後に reject する。
  launch の期限は起動まで、signal は子の寿命に適用する。
  unknown と PID の再利用を死亡と混同しない。alive の owner は実際の観測値を返す。
  ロックは callback の Promise 完了まで保持し、解放失敗も reject する。
  複数ロックは project goal-execution → goal → tasks。
  共有 Git は共通 Git directory / ref 単位。ファイル 0600、管理 directory 0700、同一 directory rename。

A（組立側）:
  createDaemonDispatcher(dependencies) を await して復元してから公開する。
  dependencies は store / conversations / runner / goals / projects / resources /
  limits / onFailure。limits の指定基準は 32 件、1 MiB。
  容量は会話ごとの未終了イベント（保存予約中・実行中も含む）に適用する。
  onFailure は accept/start/settle/progress の障害を受ける。
  保存回復時には retryStorage() を呼ぶ。provider 失敗の再実行には使わない。
  drain() は受付・準備・保存を待ち、実行中 provider を待たない。
  準備/保存中も同じ会話の枠を保持する。別会話は並行に開始できる。
  同一 workspace の repository は入口で同じ conversationId に正規化する。
  同じキュー内は受付順。待機 human が一つでもあれば other を新規開始しない。
  未保存の先行発言も、同じ会話の後続発言に追い越させない。

2. 計画から削ったもの・具体化したもの

- WorkerJobMap の 6 job、WorkerPool、worker_finished:
  RunPage/DocumentChange/TurnContext/ResolvedConfig 等の未定義 DTO と、dispatcher での
  実際の受信先・配送先が未確定のため追加しない。E の具体的な処理内部で必要な DTO だけを決める。
  worker の停止確認の口は DaemonResources.close で固定した。
- domain_changed と汎用の宛先・messageId:
  現段階で配送先や利用者がない。既知の業務イベントは Ingress、進捗・終了は Bus に限定した。
- 道具要求/応答用 RuntimeMessage:
  executeTool の具体的な request union と Promise<CallToolResult> で用が足りる。
  第三のキューや pending-request registry は作らない。
- SnapshotRequest、LaunchRequest、別の ToolReply/GoalReply/ProjectReply:
  必要なのは会話 ID と世代、コマンド要求、既存の MCP 応答。重複 DTO は作らない。
- I/O helper の declare function 群:
  B が置き換える既存 private-file モジュールに実装するため、別の未実装 API は作らない。
- Admission.invalid:
  adapter の入力検証で扱う。dispatcher に未使用の invalid 分岐は作らない。
- EventStore.accept による採番、attempt、queue.markSettled:
  採番は最初の await 前に A が行う。実行識別は generation に統一。
  キューの remove は受付失敗・開始失敗の戻し・終了に共用する。
- saveResult と duplicate の元イベント/状態:
  計画へ追加した具体化。終了保存の再試行と、受付公開後の応答失敗でターンを失わないため。
- post:void:
  post:Promise<void> とし、結果配送の処理を追跡・停止時に待機できるようにした。

# Faceted Prompting: AIプロンプトへの関心の分離

[English](./faceted-prompting.md)

## 問題

マルチエージェントシステムが複雑になるにつれ、プロンプトはモノリシックになる。1つのプロンプトファイルにエージェントの役割、行動規範、タスク固有の指示、ドメイン知識、出力形式がすべて混在し、次の問題が生じる。

1. 同じレビュアーのペルソナを2つのステップで使っても、指示が異なればプロンプト全体を複製するしかない
2. コーディング規約が複数のプロンプトに分散し、変更のたびにそれらをすべて編集する必要がある
3. プロンプトのどの部分がエージェントの「役割」を定義し、どの部分が「やるべきこと」を定義するのか区別がつかない

## アイデア

ソフトウェア工学の基本原則である関心の分離（Separation of Concerns）をプロンプト設計に適用する。

プロンプトを「何の関心を扱っているか」に応じて、独立した再利用可能なファイルに分ける。ワークフローではステップごとに使うファイルを宣言し、それらを合成する。

## 5つの関心

Faceted Promptingはプロンプトを5つの独立した関心に分ける。

| 関心 | 答える問い | 例 |
|------|-----------|-----|
| **Persona** | *誰*として判断するか？ | 役割定義、専門性 |
| **Policy** | *何を*守るか？ | 禁止事項、品質基準、優先順位 |
| **Instruction** | *何を*するか？ | 目標、ステップ固有の手順 |
| **Knowledge** | *何を*参照するか？ | 前提知識、ドメイン資料、API仕様 |
| **Output Contract** | *どう*出すか？ | 出力構造、レポートテンプレート |

各関心の内容はそれぞれのディレクトリに独立したファイル（Markdownまたはテンプレート）として保存する。

```
builtins/{lang}/
  workflows/           # ワークフロー定義
  facets/
    personas/          # WHO — 役割定義
    policies/          # RULES — 禁止事項・品質基準
    instructions/      # WHAT — ステップ手順
    knowledge/         # CONTEXT — 前提知識・参照資料
    output-contracts/  # OUTPUT — 出力契約テンプレート
    partials/          # 他のファセットから参照される共有断片

~/.takt/facets/<type>/   # ユーザー上書き（同じファセット種別）
.takt/facets/<type>/     # プロジェクト上書き（最優先）
```

### 配置と各ファセットの典型例

TAKT の通常のエージェントステップでは Persona を system prompt に置き、Knowledge・Instruction・Output Contract・Policy を実行時の user message にまとめる。次の図はファセットの配置を示している。実際のメッセージにはタスク、実行ルール、前のステップの結果なども含まれる。

```
System Prompt:
  ┌─────────────────────────────────────────────┐
  │ Persona  — エージェントの役割・専門性・行動姿勢  │
  └─────────────────────────────────────────────┘

User Message:
  ┌─────────────────────────────────────────────┐
  │ Knowledge — 判断の前提となる参照資料            │
  │ Instruction — このステップでやるべき手順        │
  │ Output Contract — 出力の構造定義              │
  │ Policy   — 守るべきルール・禁止事項・品質基準    │
  └─────────────────────────────────────────────┘
```

TAKT の Phase 1 メッセージは参照資料と作業内容を示した後に Policy を置く。この配置は `perform_phase1_message` テンプレートで確認できる。実行時に強制する制約はワークフローの権限や遷移ルールにも定義する。

#### Persona — `personas/architecture-reviewer.md`

system promptに配置される。役割の定義、境界、行動姿勢のみを含む。

```markdown
# Architecture Reviewer

あなたはソフトウェアアーキテクチャの専門家です。
コードの構造・設計・保守性を評価します。

## 役割の境界

**やること:**
- 構造・設計の妥当性検証
- コード品質の評価
- 変更スコープの適切性確認

**やらないこと:**
- セキュリティ脆弱性のレビュー（Security Reviewerの仕事）
- 自分でコードを書く

## 行動姿勢

- 完璧な設計を求めない。現状の制約下で最善かを判断する
- 既存コードベースの規約を尊重する
```

以下の4つはすべてuser messageに配置される。

#### Policy — `policies/coding.md`

タスクをまたがって適用される共有ルール。規範的（「こうすべき」）。

```markdown
# コーディングポリシー

## 原則

| 原則 | 基準 |
|------|------|
| DRY | 3回以上の重複はREJECT |
| Fail Fast | 不正状態は早期にエラー |
| 最小権限 | 必要最小限のスコープ |

## 禁止事項

- **未使用コード** - 「念のため」のメソッド、将来用フィールド
- **オブジェクトの直接変更** - スプレッド演算子で新規作成
- **フォールバックの濫用** - `?? 'default'` で不確実性を隠さない
```

#### Knowledge — `knowledge/architecture.md`

判断の前提となる参照情報。記述的（「こうなっている」）。

```markdown
# アーキテクチャ知識

## レイヤー構造

依存の方向: 上位層 → 下位層（逆方向禁止）

| レイヤー | 責務 | 依存先 |
|---------|------|--------|
| Controller | HTTPリクエスト処理 | Service |
| Service | ビジネスロジック | Repository |
| Repository | データアクセス | なし |

## ファイル構成

| 基準 | 判定 |
|------|------|
| 1ファイル300行超 | 分割を検討 |
| 1ファイルに複数の責務 | REJECT |
| 循環依存 | REJECT |
```

#### Instruction — `instructions/implement.md`

このステップ固有の手順。命令形で記述する。

```markdown
計画に基づいてタスクを実装してください。

**やること:**
1. 変更スコープを宣言する
2. コードを実装する
3. テストを書いて実行する
4. 判断ログを記録する

**注意:** Previous Response がある場合は差し戻しです。
指摘事項を踏まえて修正してください。
```

#### Output Contract — `output-contracts/review.md`

出力の構造を定義する。エージェントはこの形式に従って出力する。

````markdown
```markdown
# アーキテクチャレビュー

## 結果: APPROVE / REJECT

## サマリー
{1-2文で結果を要約}

## 確認した観点
| 観点 | 結果 | 備考 |
|------|------|------|
| 構造・設計 | ✅ | - |
| コード品質 | ✅ | - |
| テストカバレッジ | ✅ | - |

## 問題点（REJECTの場合）
| # | 場所 | 問題 | 修正案 |
|---|------|------|--------|
| 1 | `src/file.ts:42` | 問題の説明 | 修正方法 |
```
````

## Policy

### 原則

| 原則 | 基準 |
|------|------|
| DRY | 3回以上の重複はREJECT |
| Fail Fast | 不正状態は早期にエラー |
| 最小権限 | 必要最小限のスコープ |

### 禁止事項

- **未使用コード** - 「念のため」のメソッド、将来用フィールド
- **オブジェクトの直接変更** - スプレッド演算子で新規作成
- **フォールバックの濫用** - `?? 'default'` で不確実性を隠さない
```

独立したファイルが実行時に1つのプロンプトに組み立てられる。ファイルの内容を変えればプロンプトが変わり、参照するファイルを変えれば組み合わせが変わる。

### なぜこの5つか？

エージェントの役割と作業内容を定義するために、Persona と Instruction は最低限必要である。実際のプロンプトではさらに次の3つの関心を分けて扱う。

- Policy はタスクに共通する「何を守るか」を定義する。禁止事項（フォールバック濫用の禁止、未使用コードの禁止）、品質基準（REJECT/APPROVE判定）、優先順位（正確性 > 速度）を含む。たとえばコーディングポリシーは、機能実装でもバグ修正でも同じように守るべきルールを定める「横断的関心事」である。

- Knowledge はエージェントが判断の前提として参照する情報を扱う。たとえばアーキテクチャ文書はプランナーとレビュアーの両方が参照する。Knowledge を Instruction から分けることで重複を防ぎ、Instruction の内容を手順に絞る。Knowledge は現状の説明（「このドメインはこうなっている」）を含み、規範（「こうすべき」）は Policy に含める。

- Output Contract は作業内容から独立して出力構造を定義する。同じレビューフォーマットをアーキテクチャレビュアーとセキュリティレビュアーの両方で使え、エージェントの振る舞いを変えずに出力形式を変更できる。

## 宣言的な合成

Faceted Promptingでは宣言的な合成を使う。ワークフロー定義には各ステップで組み合わせる関心を記述する。

主要な特性は次の通り。

- 各ファイルには1つの関心だけを書く。ペルソナファイルには役割と専門性のみを記述し、ステップ固有の手順は含めない。
- ワークフローには組み合わせる関心を記述し、プロンプトの組み立て方は含めない。
- 同じ `coder` ペルソナを、ステップごとに異なるポリシーやインストラクションと組み合わせられる。
- ファイル単位で再利用する。同じファイルを参照すれば、複数のワークフローでポリシーを共有できる。

### TAKTでの実装例

[TAKT](https://github.com/nrslib/takt) は Faceted Prompting を YAML ベースのワークフロー定義で実装している。各ステップからビルトインファセットの名前を直接指定して参照できる。名前とファイル名が異なるカスタムエイリアスを使う場合に限り、任意でセクションマップを定義する。

```yaml
name: my-workflow
max_steps: 10
initial_step: implement

steps:
  - name: implement
    persona: coder            # WHO — builtins/{lang}/facets/personas/coder.md
    policy: coding            # RULES — builtins/{lang}/facets/policies/coding.md
    instruction: implement    # WHAT — builtins/{lang}/facets/instructions/implement.md
    knowledge: architecture   # CONTEXT — builtins/{lang}/facets/knowledge/architecture.md
    edit: true
    rules:
      - condition: Implementation complete
        next: review

  - name: review
    persona: architecture-reviewer   # 異なる WHO
    policy: review            # 異なる RULES
    instruction: review-arch  # 異なる WHAT（共有も可能）
    knowledge: architecture   # 同じ CONTEXT — 再利用
    output_contracts:
      report:
        - name: review.md
          format: architecture-review # OUTPUT — builtins/{lang}/facets/output-contracts/architecture-review.md
    edit: false
    rules:
      - condition: Approved
        next: COMPLETE
      - condition: Needs fix
        next: implement
```

エンジンは各キーに対応するファイルを探して内容を読み込み、実行時にプロンプトを組み立てる。ワークフローの作者は使うファセットを選択する。

instructions、policies、knowledge、output contracts のファセットファイルは、専用のディレクティブを単独の行に書くと、同じ種類の別ファセットを継承できる。

```md
{extends:fix}

プロジェクト固有の追加指示。
```

継承先にはファセット名を指定する。たとえばプロジェクトの `fix.md` に `{extends:fix}` と書くと、下位の `fix.md` を継承してプロジェクト固有の指示を足せる。ペルソナファセットは継承できない。

ワークフローの各ステップの `instruction` には指示を1つ指定するか、複数の指示を配列で指定できる。ファセットの参照とインライン指示を組み合わせてもよい。指示を再利用する場合は `{{include:instructions/<name>}}`、出力契約を再利用する場合は `{{include:output-contracts/<name>}}` を使う。`default`、`takt-default`、`takt-default-team` では要求シナリオを計画から最終確認まで引き継ぐための `scenario-based-*` ファセットを使う。

## 既存手法との違い

| 手法 | 内容 | 本手法との違い |
|------|------|--------------|
| **Decomposed Prompting** (Khot et al.) | *タスク*をサブタスクに分解して異なるLLMに委任 | *プロンプトの構造*を分解する |
| **Modular Prompting** | XML/HTMLタグを使った単一プロンプト内のセクション分け | 関心を*独立ファイル*に分離し、宣言的に合成する |
| **Prompt Layering** (Airia) | エンタープライズ向けの、積み重ねて使えるプロンプトの構成要素 | 管理ツールと、プロンプト設計のデザインパターンという違いがある |
| **PDL** (IBM) | データパイプライン向けのYAMLベースプロンプトプログラミング言語 | 制御フロー（if/for/model呼び出し）と関心の分離で焦点が異なる |
| **Role/Persona Prompting** | 役割を割り当てて応答を方向付ける | ペルソナを5つの関心の1つとして扱い、ポリシー、インストラクション、ナレッジ、出力契約も分離する |

既存手法はタスク（何をするか）を分解するか、プロンプトの構造（どう書式化するか）を整理する。Faceted Promptingはプロンプトの関心（各部分がなぜ存在するか）を、独立した再利用可能な単位に分ける。

## 実用上の利点

**ワークフロー作者にとって:**
- コーディングポリシーを1つのファイルで変更すれば、それを使うすべてのワークフローに反映される
- 既存のペルソナ、ポリシー、インストラクションを組み合わせて新しいワークフローを作れる
- 各ファイルを単一の責務に集中させられる

**チームにとって:**
- プロンプトを複製せずにプロジェクト間でポリシー（品質基準・禁止事項）を標準化できる
- ドメイン専門家が Knowledge のファイルを、ワークフロー設計者が Instruction のファイルを管理する分業ができる
- 個々の関心を独立してレビューできる

**エンジンにとって:**
- 同じワークフロー定義とファイルからは同じプロンプトが組み立てられる
- ファセットごとの配置と構成を実行時に一貫して適用できる
- 他の部分に影響を与えずに、ステップごとに各関心を追加・省略・上書きできる

## まとめ

Faceted Promptingは関心の分離（Separation of Concerns）をAIのプロンプト設計に適用するデザインパターンである。Persona、Policy、Instruction、Knowledge、Output Contract を独立したファイルに分けて宣言的に合成することで、各部分の役割が分かり、再利用と保守がしやすいマルチエージェントワークフローを作れる。

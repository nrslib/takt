# manager でゴールを進める

`takt manager` は、ゴールの相談と作業の進行を扱う実験的な TUI です。manager とタスクの実行には provider の利用料金がかかります。

## 相談と登録

対話端末で `takt manager` を起動し、目的、範囲外、受け入れ条件、作業の制約を伝えます。必要なら daemon を起動して準備が整うまで待ち、TUI が接続して要求を送り、結果を表示します。入力欄に `/make-goal` と打って `Enter` を押すと、会話からゴールの登録案を作ります。表示された案を確認し、`↑` 承認 / `↓` 続行 / `Enter` 決定で操作します。承認を選んで `Enter` を押すと、daemon にゴールの登録を依頼します。修正したい場合は「会話を続ける」を選んでください。

登録案が表示されていても、`/make-goal` は今の会話から案を作り直すだけで、登録はしません。登録には案の承認と `Enter` が必要です。材料が不足している場合は、その旨を表示して会話を続けられます。manager から登録案を提示することもあります。

通常画面の上部は2行で、1行目に「担当: 名前」、2行目に進行中のゴール（実行中・一時停止中）と未回答の問い合わせの件数を表示します。完成・中止したゴールの一覧や問い合わせの本文は並べません。入力欄で `/` を打つと `/make-goal` が補完候補に出て、`Tab` で確定できます。`/make-goal` 以外の `/` で始まる入力は、普通の発言として manager に送ります。

入力欄の下には、次の2行の案内を表示します。

```text
Enter 送信  Shift+Enter 改行  Esc 中断  ^R 問い合わせ  ^G ゴール  ^C 終了
/make-goal でゴールの登録案を作る
```

manager との会話は daemon が持ち、実行します。ターンを受け付けた後で TUI を閉じても、画面の接続が外れるだけで、処理は daemon で続きます。同じリポジトリや workspace を担当先として開き直した場合も、同じ担当先で2つ目の TUI を開いた場合も、同じ会話につながります。承認待ちの登録案は再表示され、承認を選んで `Enter` を押すと登録できますが、前の画面の発言や返事は再表示されません。会話本文は TAKT に保存せず、履歴は provider のセッションに任せます。承認待ちの要約やゴールの記録は別に保存します。

同じ会話の処理中に別の発言を送ると、「処理中」と返され、後から実行されることはありません。処理が終わってから、もう一度送ってください。daemon を起動し直すと、実行中だったターンは中断として扱われ、新しい発言を受け付けます。TUI が接続している間や、受け付けた会話の操作を実行している間は daemon は自動終了しません。明示的に止めるには `takt daemon stop` を使います。

登録後は daemon 内の manager がイベントを処理し、タスクの投入、成果の確認と取り込み、次の作業を進めます。TUI は作業の記録を表示し、その記録を受け取った manager と会話を続けられます。起動済みの run も、TUI を閉じても続きます。

既定では必要な run を自動起動します。手動で `takt run` / `takt watch` を起動する場合は、自動実行を無効にします。

```yaml
manager:
  auto_run: false
  default_workflow: default
```

manager は Claude、Codex、OpenCode に対応します。道具は TAKT にある投入、再開、やり直し、削除、run の参照、差分と履歴、取り込み、完成確認の機能を使います。作業前にタスク、run の記録とレポート、git を確認し、済んだ操作は繰り返しません。

ゴールに属さない問い合わせには、次の道具を使います。

| 道具 | 用途 |
|------|------|
| `takt_list_standalone_inquiries` | 現在の担当先に保存された、ゴールに属さない未回答の問い合わせの一覧を読みます。id・種類・本文・作成時刻などを返します。 |
| `takt_withdraw_standalone_inquiry` | ゴールに属さない未回答の問い合わせを、id と理由を渡して取り下げます。未回答でないものは状態も保存済みの回答も変えません。 |

manager は毎ターン、ゴール所属とゴールなしの未回答の問い合わせを点検します。もう動いていない操作の承認など、意味がなくなったものは理由付きで取り下げ、その理由を作業の記録に残します。人の判断が今も必要なものは残します。

daemon は manager の会話とイベント処理の両方を、既存の provider 権限制御を通して `full` 権限で実行します。provider の通常の道具と利用者の MCP サーバーを利用できますが、claude（claude-sdk）または codex ではここで説明する実行前審査を行います。利用者が設定した provider options はそのまま渡します。

manager の provider が claude（claude-sdk）または codex の会話では、人が操作のたびに承認する代わりに、AI の判断役が道具の実行前に審査します。判断は許可、理由付きの拒否、人への確認のいずれかです。既定で有効になり、入切の設定はありません。

claude（claude-sdk）の `Read`、`Glob`、`Grep` は、解決後の対象が manager の担当リポジトリ（workspace の所属一覧、未所属なら現在のリポジトリ）内の読み取り可能な通常ファイルだけである場合に、審査を通らず実行できます。相対パスは道具の実行時の作業ディレクトリから解決し、`~`、`..`、シンボリックリンクも解決して比較します。担当外、秘密ファイル、対象や検索範囲を確定できない呼び出しは判断役へ渡します。既定の秘密対象は `.env`、`.env.*`、SSH 秘密鍵名（`id_rsa`、`id_dsa`、`id_ecdsa`、`id_ed25519`）、`*.key`、`*.pem`、`*.crt`、`*.cer`、`*.p12`、`*.pfx` です。グローバルとプロジェクトの `manager.sensitive_paths` は既定に追加され、既定を削除できません。`ToolSearch` と manager 自身の TAKT MCP の道具は引き続き審査を通りません。Codex では、manager 自身の TAKT MCP の道具だけが審査を通らずに実行でき、組み込みの道具はすべて審査します。どちらの provider でも、それ以外は未知の道具や外部 MCP の道具も含め、保存済み承認が適用されない操作を審査します。`Bash` などのシェルの実行も、保存済み承認が適用されなければ、内容が読み取りだけに見える場合も毎回審査します。`Task` や `Agent` による別のエージェントの起動は常に拒否し、`Bash` から別の AI コマンドラインエージェントを起動する指示も拒否します。Codex の `spawn_agent` も、判断役を通さず常に拒否します。

拒否理由は manager に返り、manager は次の発言でその理由を踏まえて動きます。人への確認と判定した場合も操作はいったん拒否し、人の確認待ちであることと理由を TUI と Slack に通知します。操作を保持したまま確認を待つことはありません。通知には既存の種類を使い、新しい種類は追加しません。

保存済みの承認は、道具名・元の引数の digest・実行場所・対象 SHA が一致する操作だけに再利用します。ゴール付きの操作は、その時点のゴールブランチの SHA に結び付けます。使用可能な許可なら判断役を呼ばずに許可し、`once` は消費を保存してから1回だけ許可します。消費済みなら再確認し、消費の保存に失敗した場合は拒否します。保存済みの拒否は人の理由を返し、未回答なら同じ問い合わせ ID の確認待ちとして拒否します。回答・消費・担当先の変更は次の要求で読み直します。

承認の正本は、ゴール指定時には対象リポジトリの `.takt/goals/<UUID>/goal.json`、未指定時には現在の担当先の `~/.takt/workspaces/<UUID>/inquiries/` または `~/.takt/projects/<project-id>/inquiries/` です。別ゴールや別担当先の回答は流用しません。

判断役には、全体の `~/.takt/manager-permissions.md`、現在の workspace の `~/.takt/workspaces/<UUID>/manager-permissions.md`、対象プロジェクトの `~/.takt/manager-permissions/projects/<project-id>.md` と、対象ゴールの承認回答のうち `goal` 範囲の許可原文を、範囲・実際の保存元パス付きで毎回渡します。project-id は正規化済みリポジトリパスの SHA-256 です。`TAKT_CONFIG_DIR` 指定時はその下を使います。人が編集する Markdown は3段のままで、ゴール用 Markdown やリポジトリ内の許可ファイルは作りません。AI から許可ファイルを書き換える道具は提供しません。

原文の読み取り失敗、UTF-8 の不正、1保存元8KiBまたは合計32KiBの上限超過は、理由を判断役へ渡して人への確認に回します。ゴールでは対象の許可回答本文を合計して上限に数え、他のゴール項目は数えません。原文を切り詰めて自動許可することはなく、保存済み許可でも読み取り失敗を迂回しません。既存の禁止・ゴール制約が優先し、その内側で拒否、毎回確認、許可の順に適用します。ゴールの一時停止・再開・中止を道具で要求する場合は原則として人へ確認し、中止は取り消せないことも確認します。

判断役の provider と model は、`runtime.yaml` の `provider.targets.internal_agents.manager-permission-judge` で指定できます。他の内部 agent の seat と同じく `profile` または `ladder` を指定でき、`pool` は指定できません。未指定なら manager と同じ provider・model・provider options を使います。

判断には30秒の期限があります。期限切れは人への確認と同じ扱いになり、承認問い合わせを保存し、操作を確認待ちとして止めて通知します。例外や判定形式の不一致は引き続き操作の拒否になります。判断を自動でやり直すことはありません。

利用者の MCP は、既存の `runtime.yaml` の割り当て規則で指定します。自分で用意したブラウザ MCP サーバーを割り当てる例です。

```yaml
version: 1
mcp:
  servers:
    browser:
      type: stdio
      command: /absolute/path/to/browser-mcp-server
  targets:
    personas:
      manager:
        servers: [browser]
```

`command` は利用するサーバーの実行ファイルへ置き換えてください。ブラウザ MCP は同梱せず、既定でも有効にしません。manager には `defaults.servers` と persona の割り当てを合成し、persona の除外と `internal_agents.selector.exclude` を適用します。manager 自身の TAKT MCP は常に追加し、利用者が同名のサーバーを定義した場合も manager 自身の定義を優先します。

## 巡回

daemon は各プロジェクトのイベント処理前に、中断タスクを `failed` に回復し、ゴールタスクの完了イベントを作成します。pending タスクの有無に関係なく回復するため、`takt run` を起動し直す必要はありません。巡回イベントを処理する manager は回復後のタスク状態を読みます。回復に失敗しても後続処理は続き、失敗は記録され、既存の巡回間隔・終了時の通知判断に渡されます。回復対象は、所有PIDがない場合、生存していない場合、または保存済み開始時刻と現在の開始時刻の既知の不一致がある場合です。生存するPIDの保存済みまたは現在の開始時刻が不明なだけでは、回復せず `running` を維持します。

daemon は未完成で active なゴールを定期的に巡回します。`manager.patrol_interval` は秒単位の正の整数で、既定は `900`（15 分）です。プロジェクト設定がグローバル設定より優先されます。新規ゴールの初回は作成時刻から、以後は巡回の終了時刻から数えます。長すぎる実行、同じ段階の繰り返し、進まないゴール、長く未回答の質問を確認し、必要な再開・やり直し・通知を行います。実行中のタスクには個別の停止を依頼でき、解決できない問題は人に知らせます。巡回が失敗した場合は `blocked` を通知し、次の間隔で再確認します。失敗として残った通常のイベントも巡回時に再試行します。

## workspace

「`/path/to/web` も担当して」「このリポジトリを担当から外して」「workspace の名前を開発に変えて」と会話で依頼できます。所属するどのリポジトリから起動しても同じ workspace が開きます。1つのゴールは1つのリポジトリで進みます。

担当から外してもリポジトリやゴールは削除されません。未完成のゴールがある場合は外せないため、先に完成または中止してください。リポジトリの外で起動すると workspace を選べます。

## Slack での会話

会話スレッドに `/make-goal` を送ると登録案が表示されます。「登録を承認」または「会話を続ける」で操作でき、古い版のボタンは使えません。

設定した1つの Slack チャンネルから、Socket Mode で manager と会話できます。公開 URL は不要です。[Slack で manager と会話する](./configuration.ja.md#slack-で-manager-と会話する)の手順で App を作成・インストールし、daemon を起動するシェルに `TAKT_SLACK_APP_TOKEN` と `TAKT_SLACK_BOT_TOKEN` を設定してください。リポジトリの `.takt/config.yaml` に `manager.slack` を設定し、`takt manager` または `takt daemon` で daemon を起動します。

スレッドの外に投稿すると、その投稿のスレッドに返事が届きます。以後はそのスレッドで続けてください。どの会話スレッドも、そのリポジトリの manager の同じ会話につながり、TUI と共有します。返事は発言したスレッドにだけ届き、TUI での発言への返事は Slack に出ません。処理中に送った発言には「処理中」と返し、後から実行しないため、処理後に再送してください。設定したチャンネルと `allowed_user_ids` のユーザーだけを受け付け、ボットへの DM には反応しません。

問い合わせ（質問・承認・操作依頼）は、設定したチャンネルにスレッド外の新しい投稿として1件ずつ届きます。承認の許可・拒否と範囲、選択肢はボタンで答えます。「今回だけ」より広い範囲で承認するときは、ボタンでモーダルが開き、提案の一文を編集して確定すると許可の Markdown に追記されます。自由記述は問い合わせの投稿のスレッドに返信してください。投稿と問い合わせの対応が有効な場合、返信は通常の会話ではなく回答として扱われます。回答は出どころ `slack` として保存されます。接続前の未回答や対応の保存・読込に失敗した場合の扱いは、[設定ガイド](./configuration.ja.md#slack-で-manager-と会話する)を参照してください。

完成などの通知は会話の返事とは別に、引き続き `TAKT_NOTIFY_WEBHOOK` の Incoming Webhook で届きます。両方を併用できます。

## 回答、一時停止、中止

メニューはキーで開きます。manager が処理中でも使えます。

| キー | 動作 |
|------|------|
| `Ctrl+R` | ゴール所属・ゴールなしの未回答の問い合わせをまとめて一覧に表示し、選んだ問い合わせに回答します。 |
| `Ctrl+G` | 進行中のゴール（実行中・一時停止中）だけを短い名前と状態で表示します。`↑↓` で選び、`Enter` で一時停止・再開・中止を選びます。 |

ゴールの一時停止では新しい投入や取り込みを止め、実行中のタスクは続けて結果を保留します。再開では保留したイベントとタスクを進めます。中止は、取り消せないことと記録・ブランチが残ることを確認してから実行し、所属する実行中タスクを中断して未実行のタスクを無効にします。`Esc` は一覧を閉じるだけで、変更しません。対象がない場合は一覧を開かず、そのことを表示します。

中止は取り消せません。ゴールの記録とブランチは残ります。質問への回答は保存され、daemon の manager が次の判断に使います。

### 問い合わせへの回答

`Ctrl+R` でゴール所属・ゴールなしの未回答の問い合わせをまとめて開きます。`↑↓` で選び、`Enter` で詳細を開いて回答します。一覧は一度に10件までを表示し、超える分は上下キーで表示範囲がずれます。詳細が画面に収まらない場合は上下キーで送れます。詳細で `Esc` を押すと一覧に戻り、一覧で `Esc` を押すと回答を保存せず閉じます。

一覧は種類・ゴールの短い名前（ゴールに属さない問い合わせは「ゴールなし」）・要点を1件1行で表示します。本文・選択肢・推奨は選択後に表示します。質問は選択肢または自由記述、承認は明示的な許可・拒否と任意コメント、操作依頼は手順を確認して「実施した」「対応できない」を選び、任意コメントを添えます。コメントだけでは承認や実施済みになりません。コメントなしの拒否も保存できます。

許可の範囲は「今回だけ」が既定で、「このゴール」「プロジェクト」「manager（workspace）」「全体」から選びます。ゴールなしの承認に「このゴール」は表示しません。1リポジトリではプロジェクトとmanagerを統合表示し、プロジェクトとして保存します。後からリポジトリを追加しても既存の許可は広がりません。

プロジェクト・workspace・全体では、提案された許可の一文を編集して確定します。提案が保存されていない場合も、道具・対象・実行場所から初期文を生成します。TUI が確定文を daemon に送り、daemon が許可 Markdown に追記してから回答を保存します。追記に失敗すると未回答と編集内容を保持するため、原因を解消してEnterで再試行できます。単独承認も保存され、別のTUIを開いて回答できます。

### 知らせを読む

通常画面に流れる知らせは、見出しの行・ゴールの行・本文の先頭数行の要点だけです。起動前に保存された知らせは、manager の起動時に画面へ流れません。

## 会話からのゴール操作

Claude（claude-sdk）と Codex の manager には、「さっきのゴールを一時停止して」「このゴールを再開して」「このゴールを中止して。理由は要件の変更です」のように依頼できます。manager は既存の一覧で対象を確認し、1つに絞れない場合は質問します。ゴールの登録には、引き続き TUI での承認が必要です。

一時停止・再開・中止は判断役の経路を通し、人の確認を経て実行します。確認待ちの間は操作を実行しません。中止前には、取り消せないことと、ゴールの記録・ブランチが残ることを確認します。一時停止中も実行中のタスクは続き、再開で保留した処理を進めます。中止すると実行中タスクを中断し、未実行タスクを無効にします。中止済みのゴールは再開できません。完成したゴールは一時停止・再開できず、一時停止は実行中のゴールだけ、再開は一時停止中のゴールだけが対象です。

判断役が接続されない provider では会話の状態操作の道具を公開しません。TUI の `Ctrl+G` で開くゴールメニューから一時停止・再開・中止を選べます。

## 成果の取り込みと完成

manager は、単独で確かめられる成果ごとに作業を分けます。互いの成果を必要とせず、変更対象を共有しない作業は、指定された順序と同時実行数の範囲で並行します。人が指定した制約は各指示書へ引き継ぎ、ゴール全体で1回だけ行う確認には担当を決めます。

成果をゴール用ブランチに集め、差分、履歴、run の報告で受け入れ条件を確かめます。組み合わせて確認する必要がある成果には、結合後の確認を行います。完成は取り込み先に取り込んだ後です。

ゴールの完成判定は `git merge-tree --write-tree` で tree を比べるため Git `>=2.38` が必要で、要件を満たさない環境では必要な版を示すエラーになります。

```yaml
manager:
  main_merge: approve
```

`main_merge` の既定値 `approve` は人の取り込みを待ち、手順を表示します。人が取り込んだ後、manager に確認を依頼してください。`auto` は自動で取り込みますが、取り込み先がチェックアウト中なら人を待ちます。

## 止まったときと通知

manager は `takt_stop_goal_task`（`manager`・`all` のツール一覧）で実行中タスク1件の停止を依頼できます。絶対パスの `cwd` を渡します。`takt_list_tasks` が返す同じタスク項目の `name` の値を `taskName` に設定し、`goalId`・固定の `executionId` もその項目の値を使います。所有PIDの生存を確認します。開始時刻が保存されている場合は、現在の開始時刻を取得して一致を確認します。保存済み開始時刻がない場合は、goalId・taskName・executionIdの一致、実行中の状態、所有PIDの生存を確認して受理します。識別情報の不一致、実行中でないタスク、所有プロセスの終了は、依頼を保存せず理由付きで拒否します。開始時刻が保存されているのに現在値を取得できない場合も拒否します。ツールは依頼だけを保存し、同じworkerが500ms間隔で検知して自身を中断します。処理と後片付けの終了後に `failed` とタスク停止理由を保存するため、ゴール中止とは区別できます。ゴールと他のタスクは継続します。重複依頼の評価時点で、同じ実行が引き続き `running` で、所有者を検証できる場合に限り保存済み依頼を返し、キューへの差し戻し・再実行には新しい実行IDを使うため、以前の依頼は適用しません。所有者を確認できれば、一時停止中のゴールの実行中タスクも停止できます。

manager はレポートと作業場所を確認し、既存タスクの再開、指示書を直したやり直し、新しい作業、片付けを選びます。解決できない場合は、理由、試したこと、人にしてほしい操作を通知か質問で伝えて、その作業と後続を止めます。独立した作業は続けます。

通知は TUI と Slack に届き、[通知設定](./configuration.ja.md#manager-の通知設定)で種類ごとに切り替えられます。manager のイベント処理や TUI の会話が失敗した場合も `blocked` を通知します。同じ失敗でも通知し、失敗状態のファイルは作りません。原因を解消してから会話の操作をやり直してください。失敗したイベントは巡回時に再試行します。

ゴールの記憶は `.takt/goals/<UUID>/goal.json` に保存します。目的、範囲外、受け入れ条件、作業の制約、質問と回答、何を投入・取り込み・取りやめたかと理由を記録します。workspace は `~/.takt/workspaces/`、未処理のイベントは `~/.takt/manager-inbox/` に保存します。`TAKT_CONFIG_DIR` を指定した場合はその下を使います。

## director の見回り

### 会話を始める

対話端末から起動します。

```bash
takt director
takt director --help
```

`takt director` は director と会話する TUI を開きます。会話は daemon が保持・実行するため、TUI を閉じて開き直すと同じ会話の続きにつながります。どの担当リポジトリから起動しても、同じ daemon 共通の会話です。前の画面の発言や返事は再表示されず、会話履歴は provider のセッションで管理します。

director は実験的機能です。動作や保存するデータの形式は予告なく変わることがあります。会話には provider の費用がかかり、定期的な見回りも provider を呼び出すため費用がかかります。

### manager との分担と人の判断

manager は担当するリポジトリまたは workspace のゴールを進め、タスクの投入、成果の取り込み、完成の申請を行います。director は全 manager のゴールと未回答の問い合わせを見渡します。マージ待ち、一時停止、保存された `blocked` 通知、未回答の問い合わせなど、人の対応が必要な事項を通知として保存します。manager に尋ねたり伝えたりするときは、話し手を `director` とする manager の会話を使います。同じ対象と保存状態への通知は重複しません。

`takt_tell_manager` は、manager が処理中でも、伝言を manager の会話の記録に「実行待ち」として保存します。保存した時点で操作 ID と manager が返り、返事は待ちません。manager ごとに会話と受け箱のイベントの実行枠は1つです。現在の処理が終わると、実行待ちの伝言を保存順に、受け箱のイベントより先に、話し手を `director` とするターンとして1度だけ実行します。人の TUI・Slack 発言は今までどおり、manager の処理中は busy で断られ、保存も後からの実行もされません。

返事・失敗・中断は同じ操作 ID で保存され、あとで director の画面に知らされます。伝言の保存に失敗した場合は受け付けず、道具の失敗として返します。受付後に接続が切れても保存した伝言は残り、director は自動で送り直しません。

daemon を起動し直すと、未開始の伝言は接続がなくても実行されます。開始後、結果を保存する前に停止した伝言は、director と人に中断として知らされ、自動では再実行しません。

director はシェルの実行、ファイルへの書き込み、設定の書き換えができません。run の段階、裁定、ログなどタスク内部の確認は各 manager の担当です。マージや仕様の判断、削除など取り返しのつかない操作は人に残し、問い合わせへの回答も代行しません。

人が明示的に「ゴール G をマージして」と指示したときだけ、director は G の manager に、その PR を `takt merge` でマージするよう伝えます。転送前に対象のリポジトリ、ゴール、manager を一意に特定し、現在のゴールが `awaiting_merge` であることと、保存済みの PR 番号・URL を確認します。対象が曖昧、状態が異なる、PR がない、読み取りに失敗した場合は転送せず、理由を人に返します。director 自身はマージしません。manager が `takt_merge_goal_pr` を通じて `takt merge` を実行します。指示の転送や受付だけではマージ成功とせず、あとで届く同じ操作 ID の結果で成否を伝えます。実行時も既存の確認により、ゴールが一時停止・中止・`awaiting_merge` 以外になった場合や、保存済みの PR 番号と違う場合はマージしません。

manager 一覧（`takt_list_managers`）と見回りは project ごとに読み取ります。git リポジトリでないディレクトリなど、読めない project は理由付きで示し、残りの manager を返して見回りを続けます。1つの project の読み取り失敗で、一覧や見回り全体は失敗しません。

### 見回りの設定

daemon 稼働中は、登録済みの repository manager と workspace manager を定期的に確認します。見回りは人との会話を引き継がずに実行し、人のマージ指示としては扱いません。daemon の既存のアイドル終了動作は変わりません。

director の設定は、プロジェクトの `.takt/config.yaml` ではなく、グローバルの `~/.takt/config.yaml` に記述します。

| 設定 | 意味 |
|------|------|
| `director.patrol_interval` | 見回り間隔。秒単位の正の整数で、既定は `900`（15分）。 |
| `director.slack.channel_id` | director と会話し、まとめた通知を受け取る Slack チャンネル。 |
| `director.slack.allowed_user_ids` | Slack から director に発言できるユーザー。`director.slack` を設定するときは必須。空配列では誰の発言も受け付けない。 |

詳しくは[グローバル設定フィールドリファレンス](./configuration.ja.md#グローバル設定フィールドリファレンス)を参照してください。

### Slack を接続する

manager と同じ Slack App と環境変数 `TAKT_SLACK_APP_TOKEN` / `TAKT_SLACK_BOT_TOKEN` を使います。ボットを director のチャンネルへ招待し、`takt daemon` を起動するシェルで両変数を設定してください。Slack 設定を変更したら daemon を起動し直します。トークンは設定ファイルに書かず、環境変数で渡します。

許可された人の発言は同じ director の会話につながり、返事は元の投稿のスレッドに届きます。1回の会話または見回りで出た新しい知らせは、チャンネルへの1件の投稿にまとまります。`director.slack` を設定しなければ Slack で送受信しません。App の作成と接続の詳細は、[Slack で director と会話する](./configuration.ja.md#slack-で-director-と会話する)を参照してください。

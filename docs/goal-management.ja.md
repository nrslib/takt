# manager でゴールを進める

`takt manager` は、ゴールの相談と作業の進行を扱う実験的な TUI です。manager とタスクの実行には provider の利用料金がかかります。

## manager の見回り

見回りは毎回、会話とは別の新しいセッションで動き、会話の履歴を読みません。必要な業務の文脈は最初のプロンプトに渡します。結果は作業記録に残り、次の会話では業務の文脈から参照できます。人との会話は元のセッションで続きます。

動いているゴール（一時停止・中止・完成・人のマージ待ち以外）があるリポジトリでは、manager が定期的に対象のゴールをまとめて点検します。対象がなければ見回りは動きません。`.takt/config.yaml` または `~/.takt/config.yaml` の `manager.patrol_interval` に正の整数で秒数を指定します。リポジトリの設定を優先し、既定は 1800 秒（30 分）です。

人のマージ待ちは、`awaiting_merge` で、紐づく仕上げタスク（`merge_task: true`）に `pending` / `running` がなく、最後の仕上げタスクも `failed` / `exceeded` / `pr_failed` ではないゴールです。「最後」は `tasks.yaml` の並びで決めます。仕上げタスクが一度もない場合も人のマージ待ちです。仕上げが動いている場合や、最後の仕上げが失敗している場合は、見回りの対象になります。

daemon は、リポジトリごとに前回の見回りを受け付けた時刻を保存します。起動時に対象のゴールがあり、前回から間隔が過ぎているか、一度も受け付けていなければ、最初の観測で見回りを1件積みます。間隔が過ぎていなければ、前回の受付時刻＋間隔まで待ちます。daemon を何度起動し直しても、その間隔が過ぎる前に見回りが増えることはありません。

マージ待ち（`awaiting_merge`）のゴールは、PR の見張りで監視します。マージ・クローズに加え、取り込み先との衝突（`mergeable: CONFLICTING`）をイベントで manager に届けます。同じ衝突が続く間は繰り返さず、衝突が解消した後に再発すると、再び届けます。`mergeable: UNKNOWN` は変化に数えません。時間や回数で異常を判断しません。manager は現在状態と既存タスクを確認し、必要なら `takt_merge_goal_pr` で仕上げタスクを積みます。既定の `approve` では `until: prepare` で仕上げ、人のマージを待ちます。

```yaml
manager:
  patrol_interval: 1800
```

見回りは人以外のイベントのキューに入ります。処理の順番は人の発言、見回り以外のイベント、見回りで、先の2つに待機中の入力がないときだけ見回りを始めます。同じ会話に TUI・Slack から人の入力を受け付けると、実行中の見回りだけを中断して人の入力を先に処理します。人の入力や明示的な中断で止まった見回りはやり直さず、次の間隔で行います。daemon の停止・再起動で中断した見回りは、次の起動で届け直します。待機中の入力やイベントは消しません。見回り以外のターンは、人の入力が来ても中断しません。待機中・実行中の見回りは積み重ならず、daemon の停止中の分も後からまとめて実行しません。TUI の接続中は完了した見回りの短い結果を「見回り: ゴール 2 件、異常なし」のように1回表示し、途中結果は表示しません。細部は作業記録に残します。点検だけの記録は進展として数えません。問題がなければ Slack などへ通知しません。問題がある場合は manager が既存の通知や問い合わせを使います。

見回りでは、実行中の run の最新の報告と記録を指示書・受け入れ条件に照らし、頼んだ作業から外れていないかを確かめます。対象の範囲を超えた脅威や想定、起こりえない前提、受け入れ条件にない要求、必要以上の仕組みがあれば、根拠とともに run へ伝えます。実行時間や段階の回数で異常を判断しません。待機中のタスクが30秒たっても起動しない TAKT 自身の故障を知らせる `run_launch_stalled` は残ります。director の見回りは行いません。旧設定の `director.patrol_interval` は読み取っても無視します。

## 相談と登録

対話端末で `takt manager` を起動し、目的、範囲外、受け入れ条件、作業の制約を伝えます。必要なら daemon を起動して準備が整うまで待ち、TUI が接続して要求を送り、結果を表示します。入力欄に `/make-goal` と打って `Enter` を押すと、会話からゴールの登録案を作ります。表示された案を確認し、`↑↓` で「登録する」または「登録せずに会話に戻る」を選び、`Enter` で決定します。既定では会話に戻り、登録案を取り下げます。「登録する」を選ぶと、daemon にゴールの登録を依頼します。会話に戻る操作、待機中の `Esc`、修正内容の入力は登録案を取り下げます。修正したい場合は manager に変更を伝え、案を作り直してください。処理中の `Esc` は処理の中断です。

処理中のTUIには、経過時間と現在の動作を表示します。Bashはdescriptionがあればその説明を、その他の道具は名前を表示します。長い表示は末尾を「…」で省略し、幅80でも経過時間を残します。通常のターンと `/verify` の解釈段階では、途中の文を次の道具の開始時に、最後の返答より前へ順番に表示します。ターンまたは解釈段階の終了時に残った文は、途中出力として表示せずに破棄します。最後の返答は引き続き表示します。途中の文は保存せず、再接続しても再表示しません。見回りでは道具の表示と経過時間だけを表示し、途中の文は出しません。Slackには途中の文や道具のdescriptionを送りません。

登録案が表示されていても、`/make-goal` は今の会話から案を作り直すだけで、登録はしません。登録には「登録する」の選択と `Enter` が必要です。材料が不足している場合は、その旨を表示して会話を続けられます。manager から登録案を提示することもあります。

通常画面の最下部には、担当名・進行中のゴール（実行中・一時停止中）・人のマージ待ち・未回答の問い合わせの件数を表示します。仕上げが動いているゴールや、最後の仕上げが失敗したゴールは進行中に数えます。担当の見出しが長い場合は中央を省略して件数を残し、狭い端末では担当名と件数を2行に分けます。実験的機能の注意書きは、起動ごとに会話表示の先頭に黄色で一度だけ表示します。完成・中止したゴールの一覧や問い合わせの本文は並べません。入力欄で `/` を打つと `/make-goal` と `/verify` が補完候補になり、`↑↓` で選んで `Tab` で確定できます。`/make-goal` と `/verify` 以外の `/` で始まる入力は、普通の発言として manager に送ります。

入力欄の下にはキー操作の案内、その下にステータスラインを表示します（以下は表示例）。`/make-goal` と `/verify` の説明は常時表示せず、スラッシュ補完に表示します。実験的機能についての長い注意書きは起動時に一度表示します。

```text
Enter 送信  Shift+Enter 改行  Esc 中断  ^R 問い合わせ  ^G ゴール  ^C 終了
担当: takt | 進行中 1 ／ 未回答 0
```

manager との会話は daemon が持ち、実行します。ターンを受け付けた後で TUI を閉じても、画面の接続が外れるだけで、処理は daemon で続きます。同じリポジトリや workspace を担当先として開き直した場合も、同じ担当先で2つ目の TUI を開いた場合も、同じ会話につながります。承認待ちの登録案は再表示され、「登録する」を選んで `Enter` を押すと登録できますが、前の画面の発言や返事は再表示されません。会話の履歴は provider のセッションに任せます。処理待ちの発言本文は実行開始まで TAKT に保存します。承認待ちの要約やゴールの記録は別に保存します。

daemon はイベントで動きます。キューは人の入力と、それ以外のイベントの2本です。次のターンでは人の入力を先に処理します。人以外のキューでは見回りを後回しにし、人の入力同士・見回り以外のイベント同士・見回り同士では受け付けた順を守ります。見回り以外のターンは1本の会話セッションを使い、イベントで知った内容も次の人との会話に引き継ぎます。処理中でも発言・承認・問い合わせ回答を保存して受け付け、画面の読み出しと現在のターンの中断を行えます。accepted は永続化済みの受付で、処理の完了ではありません。中断しても待機中の入力は消えません。失敗したターンは盲目的に自動再送せず、manager が現在状態と副作用を調べて復旧方法を判断します。

daemon の停止で中断した人以外のイベント（タスクの成功・失敗、PR の変更、見回り、director の伝言など）と、起動時に `running` のまま見つかったイベントは、元の受付順でキューへ戻して届け直します。人の入力を優先し、見回りを後回しにする順序は変わりません。`Esc` など人が明示的に中断したターンは処理済みとし、届け直しません。人の発言は従来どおり `interruptedMessage` として次の発言へ引き継ぎます。

登録後は daemon 内の manager がイベントを処理し、タスクの投入、成果の確認と取り込み、次の作業を進めます。TUI は通知を表示し、イベントを受け取った manager と会話を続けられます。作業の記録は TUI に表示しません。起動済みの run も、TUI を閉じても続きます。

既定では必要な run を自動起動します。手動で `takt run` / `takt watch` を起動する場合は、自動実行を無効にします。

```yaml
manager:
  auto_run: false
```

グローバルの `~/.takt/config.yaml` またはプロジェクトの `.takt/config.yaml` の `manager.workflows` で、新しい開発タスクに使える workflow を指定します。project の値は global の一覧全体を置き換えます。各要素は名前の文字列か、`{ 名前: 使い分けの説明 }` の1対だけを持つオブジェクトです。`workflow_categories.workflows` と同じ記法です。

```yaml
manager:
  workflows:
    - default: 普通の機能追加や不具合の修正。計画からレビューまで一通り行う
    - simple: 1〜2 ファイルで済む小さな修正。軽い流れで進める
    - takt-default
```

`manager.workflows` が project と global のどちらにも設定されていない場合、候補は `default` と `simple` です。manager は `language` に合わせた上記の使い分けの説明を受け取り、タスクに合う workflow を選択します。名前だけを明示した要素には説明を補いません。`workflows: all` なら従来どおり制限しません。見つからない名前は manager の会話の plan を作るときに警告して無視します。空の名前や複数キーのオブジェクトなど、不正な形は設定読み込み時にエラーになります。

manager の `takt_list_workflows` は選べる候補だけを返し、workflow 自身の `description` に加えて、設定した使い分けの説明を `usageDescription` で返します。`takt_enqueue_goal_task` で選べない workflow を新規登録すると、道具が候補一覧と設定ファイルの場所を示すエラーで断ります。既存タスクの再開・積み直し・やり直しは、保存済みの workflow のまま可能です。`takt_merge_goal_pr` による PR の仕上げ（`merge.workflow` / `merge-prepare`）、子の `workflow_call`、manager 以外の MCP、人が手で使う CLI には制限しません。workspace manager は、一覧取得・タスク投入の対象リポジトリごとの設定を使います。

manager は Claude、Codex、OpenCode に対応します。道具は TAKT にある投入、再開、やり直し、削除、run の参照、差分と履歴、取り込み、完成確認の機能を使います。作業前にタスク、run の記録とレポート、git を確認し、済んだ操作は繰り返しません。

ゴールに属さない問い合わせには、次の道具を使います。

| 道具 | 用途 |
|------|------|
| `takt_list_standalone_inquiries` | 現在の担当先に保存された、ゴールに属さない未回答の問い合わせの一覧を読みます。id・種類・本文・作成時刻などを返します。 |
| `takt_withdraw_standalone_inquiry` | ゴールに属さない未回答の問い合わせを、id と理由を渡して取り下げます。未回答でないものは状態も保存済みの回答も変えません。 |

manager は毎ターン、ゴール所属とゴールなしの未回答の問い合わせを点検します。もう動いていない操作の承認など、意味がなくなったものは理由付きで取り下げ、その理由を作業の記録に残します。人の判断が今も必要なものは残します。

manager は、担当のゴールを完成まで進める TAKT に詳しいエンジニアとして、自分で調査・実装・確認・Git 操作を行い、必要に応じて委任します。provider の通常の道具と割り当てた MCP を `full` 権限で使い、利用者の provider options は維持します。manager 固有の権限判断役、読取範囲の審査、保存許可による実行制御はありません。

取り込み先への反映、force push、リモートブランチや未保存成果の削除、ゴール中止、依頼範囲外の新しい投稿は、対象と作用が分かる人の明示指示に従うファセットの方針です。直接の発言、director の伝言、保存された継続指示を扱い、PR 作成・通常 push・設定済み通知は依頼作業に含めます。指示済みのことを再確認しません。ゴールの PR をマージした後も、確認と後続の作業に使うゴールブランチは保持します。秘密値を読むにはその必要を含む人の指示が必要で、応答・記録・成果物に秘密値を残しません。

旧設定 `manager.sensitive_paths` と runtime の `provider.targets.internal_agents.manager-permission-judge` は非推奨です。既存ファイルに残っていても読み飛ばし、効果はありません。古い許可 Markdown や承認回答も実行可否には使いません。過去の問い合わせ記録は読み取り・取り下げのために残します。

利用者の MCP は、既存の `runtime.yaml` の割り当て規則で指定します。自分で用意したブラウザ MCP サーバーを割り当てる例です。

```yaml
version: 1
mcp:
  servers:
    browser:
      type: stdio
      command: /absolute/path/to/browser-mcp-server
  targets:
    personas:
      manager:
        servers: [browser]
```

`command` は利用するサーバーの実行ファイルへ置き換えてください。ブラウザ MCP は同梱せず、既定でも有効にしません。manager には `defaults.servers` と persona の割り当てを合成し、persona の除外と `internal_agents.selector.exclude` を適用します。manager 自身の TAKT MCP は常に追加し、利用者が同名のサーバーを定義した場合も manager 自身の定義を優先します。

## イベントと見張り

コードの見張りがプロセス消失、PR の状態変化などを観測し、変化や異常があるときだけイベントを届けます。manager の定期的な見回りは、上記の間隔でリポジトリごとに1回行います。director は時計で呼びません。PID の生存や開始時刻を確認できない場合は、死亡と決めつけません。会話ごとの常駐子プロセスがターンの準備・AI・MCP・業務操作を行い、daemon は受付・保存・配送・監視を担います。子の異常終了は実行中のターンの失敗として記録し、自動ではやり直しません。

## workspace

「`/path/to/web` も担当して」「このリポジトリを担当から外して」「workspace の名前を開発に変えて」と会話で依頼できます。所属するどのリポジトリから起動しても同じ workspace が開きます。1つのゴールは1つのリポジトリで進みます。

担当から外してもリポジトリやゴールは削除されません。未完成のゴールがある場合は外せないため、先に完成または中止してください。リポジトリの外で起動すると workspace を選べます。

## Slack での会話

会話スレッドに `/make-goal` を送ると登録案が表示されます。「登録する」または「登録せずに会話に戻る」で操作でき、古い版のボタンは使えません。

設定した1つの Slack チャンネルから、Socket Mode で manager と会話できます。公開 URL は不要です。[Slack で manager と会話する](./configuration.ja.md#slack-で-manager-と会話する)の手順で App を作成・インストールし、daemon を起動するシェルに `TAKT_SLACK_APP_TOKEN` と `TAKT_SLACK_BOT_TOKEN` を設定してください。リポジトリの `.takt/config.yaml` に `manager.slack` を設定し、`takt manager` または `takt daemon` で daemon を起動します。

スレッドの外に投稿すると、その投稿のスレッドに返事が届きます。以後はそのスレッドで続けてください。どの会話スレッドも、そのリポジトリの manager の同じ会話につながり、TUI と共有します。返事は発言したスレッドにだけ届き、TUI での発言への返事は Slack に出ません。処理中の発言も永続化して受け付け、人の入力を先に処理し、結果を元のスレッドへ返します。設定したチャンネルと `allowed_user_ids` のユーザーだけを受け付け、ボットへの DM には反応しません。

問い合わせ（質問・操作依頼）は設定した Slack チャンネルへ一件ずつ届きます。選択肢と実施結果はボタン、自由記述は問い合わせのスレッドで回答し、出所 `slack` を保存します。許可範囲の選択や許可文の保存画面はありません。

完成などの通知は会話の返事とは別に、引き続き `TAKT_NOTIFY_WEBHOOK` の Incoming Webhook で届きます。両方を併用できます。

## 回答、一時停止、中止

メニューはキーで開きます。manager が処理中でも使えます。

| キー | 動作 |
|------|------|
| `Ctrl+R` | ゴール所属・ゴールなしの未回答の問い合わせをまとめて一覧に表示し、選んだ問い合わせに回答します。 |
| `Ctrl+G` | 進行中のゴール（実行中・一時停止中）だけを短い名前と状態で表示します。`↑↓` で選び、`Enter` で一時停止・再開・中止を選びます。 |

ゴールを一時停止すると、新しい投入や取り込みに加え、実行中のタスクも止めます。停止したタスクはやり直せる失敗として残り、その結果のイベントは保留されます。再開すると manager が保留したイベントを受け取り、停止したタスクの継続方法を判断して作業を進めます。中止は、取り消せないことと記録・ブランチが残ることを確認してから実行し、所属する実行中タスクを中断して未実行のタスクを無効にします。`Esc` は一覧を閉じるだけで、変更しません。対象がない場合は一覧を開かず、そのことを表示します。

中止は取り消せません。ゴールの記録とブランチは残ります。質問への回答は保存され、daemon の manager が次の判断に使います。

### 問い合わせへの回答

`Ctrl+R` でゴール所属・ゴールなしの未回答の問い合わせをまとめて開きます。`↑↓` で選び、`Enter` で詳細を開いて回答します。一覧は一度に10件までを表示し、超える分は上下キーで表示範囲がずれます。詳細が画面に収まらない場合は上下キーで送れます。詳細で `Esc` を押すと一覧に戻り、一覧で `Esc` を押すと回答を保存せず閉じます。

一覧は種類・ゴールの短い名前・要点を一件一行で表示し、選択後に詳細を開きます。質問は選択肢か自由記述、操作依頼は「実施した」「対応できない」と任意コメントを保存します。旧来の道具承認は回答対象にせず、記録の参照・取り下げだけを行えます。

### 知らせを読む

通常画面に流れる知らせは、見出しの行・ゴールの行・本文の先頭数行の要点だけです。起動前に保存された知らせは、manager の起動時に画面へ流れません。

## 会話からのゴール操作

必要な MCP 能力を持つ全 provider の manager に、「さっきのゴールを一時停止して」「このゴールを再開して」「このゴールを中止して。理由は要件の変更です」のように依頼できます。manager は既存の一覧で対象を確認し、1つに絞れない場合は質問します。ゴールの登録には、引き続き TUI での承認が必要です。

一時停止すると実行中のタスクも止まり、やり直せる失敗として残ります。再開すると manager が保留したイベントを受け取り、停止したタスクの継続方法を判断して作業を進めます。中止すると実行中タスクを中断し、未実行タスクを無効にします。中止済みのゴールは再開できません。完成したゴールは一時停止・再開できず、一時停止は実行中のゴールだけ、再開は一時停止中のゴールだけが対象です。

TUI の `Ctrl+G` のゴールメニューからも一時停止・再開・中止を選べます。会話では同じ状態操作の道具を全 provider で使えます。

## 外部の状態を待つコマンド

manager 専用の `takt_wait_command` は、daemon への要求経路がある会話で利用でき、待つためのシェル1行を登録して、すぐに登録 ID を返します。例は `gh run watch <id> --exit-status`、`gh pr checks <n> --watch`、`until curl -sf …; do sleep 30; done` です。引数は `command`、待つ対象の `description`、担当リポジトリ内の絶対ディレクトリ `cwd`、任意の `goalId` と `timeoutSeconds` です。サブディレクトリの指定もそのまま実行場所になります。待ち時間は既定3600秒、上限86400秒です。daemon のイベント受付容量に合わせ、実行中と完了配送・再送待ちの登録を合わせて daemon 全体で32件まで保持します。上限時は新規登録をエラーで拒否し、完了イベントの配送で空きができれば再登録できます。

登録後はターンを終えてかまいません。daemon はメモリ内で依頼を管理し、成功・失敗・時間切れ・ゴール停止によるキャンセルを `wait_command_completed` イベントで依頼元の会話に1回届けます。イベントには登録 ID、説明、関連ゴール、終了状態、終了コード（取得できない場合は `null`）、シグナル、経過時間、stdout/stderr を合わせた末尾16 KiB が入ります。

`goalId` は指定したリポジトリの実行中ゴールに限ります。そのゴールの一時停止・中止は5秒周期で検出し、コマンドのプロセスツリーを停止します。時間切れでも停止します。daemon 終了時は依頼と子プロセスを停止し、可能なら `cancelled` の完了イベントを依頼元の会話へ配送します。登録は再起動時に再実行しないため、manager は起動後の見回りで状態を確かめ、必要なら再登録します。

Windows で Job 停止や handle close の後に自然終了と停止を区別できない場合は、停止エラーを記録し、完了イベントを送らず登録・監視・配送待ちを保持します。Job 停止用コードとの一致や close の成功だけではキャンセルや時間切れを確定しません。daemon の終了処理は共通の15秒期限で失敗し、再度終了処理を呼び出せます。原因不明のままなら、再試行後も完了扱いにはしません。

このコマンドは daemon が直接実行し、manager の `auto` 権限の AI 審査を通りません。待つためのコマンドに使い、状態を変える操作には使いません。この用途制限を仕組みで強制するものではありません。

## 成果の取り込みと完成

manager は、単独で確かめられる成果ごとに作業を分けます。互いの成果を必要とせず、変更対象を共有しない作業は、指定された順序と同時実行数の範囲で並行します。人が指定した制約は各指示書へ引き継ぎ、ゴール全体で1回だけ行う確認には担当を決めます。

成果をゴール用ブランチに集め、差分、履歴、run の報告で受け入れ条件を確かめます。組み合わせて確認する必要がある成果には、結合後の確認を行います。完成は取り込み先に取り込んだ後です。

ゴールの完成判定は `git merge-tree --write-tree` で tree を比べるため Git `>=2.38` が必要で、要件を満たさない環境では必要な版を示すエラーになります。

```yaml
manager:
  main_merge: approve
```

`main_merge` は `approve` と `auto` のどちらも PR を作成します。既定の `approve` では manager が `takt_merge_goal_pr` に `until: prepare` を渡して仕上げ、人のマージを待ちます。`auto` は人が設定した継続の取り込み指示として、`until: merge` でマージまで進めます。人が「マージして」と指示した場合も `until: merge` を使います。

完成申請は、確認済みの SHA を `origin` に push し、ゴールブランチから保存済みの取り込み先への PR を作成または再利用します。失敗は作業記録と `blocked` 通知に残し、manager が原因と副作用を確認して次の操作を判断します。時間や回数を決めた PR 作成の自動再試行は行いません。PR が未保存なら、原因解消後に `takt_complete_goal` を呼び直せます。

`takt_merge_goal_pr` は必須の `cwd`、`goalId`、`prNumber`、`until` を受け、`merge_task: true` と `goal_id` を持つタスクを `tasks.yaml` に pending で積み、すぐにタスク名を返します。`prepare` は `merge-prepare`、`merge` は `merge.workflow`（未設定なら `merge-review-fix-simple`）を使います。同じ対象の pending / running タスクは二重に積めません。

daemon は通常のゴールタスクと同じように実行し、取り込み先の取り込み、競合解消、レビューと修正、push、Caccia、CI 待ちを行います。PR が競合しても普通の修正タスクは作りません。マージ用タスクは PR のブランチへ直接 push するため、成果を `takt_merge_goal_task` で取り込みません。`takt_list_tasks` は `mergeTask` と完了結果を表示します。完了イベントには `mergeOutcome`（`prepared`・`merged`・`unresolved`）と `branchSynchronization` が入り、マージ済みなら manager が `takt_check_goal_completion` で完成にします。

push 後は、元リポジトリのゴールブランチが origin の祖先なら fast-forward します。分岐していれば両方の履歴を保持して失敗結果とイベントで知らせます。チェックアウト中の作業コピーは書き換えず、追従を止めて知らせます。タスクの取り込み前と再申請の push 前にも同じ確認を行います。追従で先端が変わった場合は、その新しい SHA の受け入れ条件を確認し直して申請します。

## 止まったときと通知

manager は `takt_stop_goal_task`（`manager`・`all` のツール一覧）で実行中タスク1件の停止を依頼できます。絶対パスの `cwd` を渡します。`takt_list_tasks` が返す同じタスク項目の `name` の値を `taskName` に設定し、`goalId`・固定の `executionId` もその項目の値を使います。所有PIDの生存を確認します。開始時刻が保存されている場合は、現在の開始時刻を取得して一致を確認します。保存済み開始時刻がない場合は、goalId・taskName・executionIdの一致、実行中の状態、所有PIDの生存を確認して受理します。識別情報の不一致、実行中でないタスク、所有プロセスの終了は、依頼を保存せず理由付きで拒否します。開始時刻が保存されているのに現在値を取得できない場合も拒否します。ツールは依頼だけを保存し、同じworkerが500ms間隔で検知して自身を中断します。処理と後片付けの終了後に `failed` とタスク停止理由を保存するため、ゴール中止とは区別できます。ゴールと他のタスクは継続します。重複依頼の評価時点で、同じ実行が引き続き `running` で、所有者を検証できる場合に限り保存済み依頼を返し、キューへの差し戻し・再実行には新しい実行IDを使うため、以前の依頼は適用しません。所有者を確認できれば、一時停止中のゴールの実行中タスクも停止できます。

manager はレポートと作業場所を確認し、既存タスクの再開、指示書を直したやり直し、新しい作業、片付けを選びます。解決できない場合は、理由、試したこと、人にしてほしい操作を通知か質問で伝えて、その作業と後続を止めます。独立した作業は続けます。

通知は TUI と Slack に届き、[通知設定](./configuration.ja.md#manager-の通知設定)で種類ごとに切り替えられます。manager のイベント処理や TUI の会話が失敗した場合も `blocked` を通知します。同じ失敗でも通知し、失敗状態のファイルは作りません。原因を解消してから会話の操作をやり直してください。失敗したターンは盲目的に自動再送せず、manager が現在状態と副作用を調べて復旧方法を判断します。

ゴールの記憶は `.takt/goals/<UUID>/goal.json` に保存します。目的、範囲外、受け入れ条件、作業の制約、質問と回答、何を投入・取り込み・取りやめたかと理由を記録します。workspace は `~/.takt/workspaces/`、未処理のイベントは `~/.takt/manager-inbox/` に保存します。`TAKT_CONFIG_DIR` を指定した場合はその下を使います。


workflow は名前・scope reference・ファイルパスで指定できます。merge_pr / close_pr を含む workflow も投入でき、`autoPr` と `shouldPublishBranchToOrigin` は投入時に指定します。省略時は false のまま、worktree とゴールブランチ基点を維持します。

`takt_remove_goal_task` は一時停止中の pending も取り消せます。未取り込みの完了成果を破棄するときは `discardUnmerged: true` と理由を渡します。実行中の拒否・所属・cleanup 成功の検査は残ります。

`takt_merge_goal_pr` は必須の `cwd`、`goalId`、保存 PR と一致する `prNumber`、`until` を使い、会話 ID や director 限定の認可はありません。停止状態・保存 PR・head/base の検査は維持します。push や PR 作成の失敗は manager 自身が調べて復旧でき、`awaiting_merge` で PR 未保存なら `takt_complete_goal` の呼び直しで準備をやり直せます。最終確認の実行は委任できますが、対象 SHA・方法・結果の証拠は manager が確認します。

## director の役割

### 会話を始める

対話端末から起動します。

```bash
takt director
takt director --help
```

`takt director` は director と会話する TUI を開きます。会話は daemon が保持・実行するため、TUI を閉じて開き直すと同じ会話の続きにつながります。どの担当リポジトリから起動しても、同じ daemon 共通の会話です。前の画面の発言や返事は再表示されず、会話履歴は provider のセッションで管理します。

director は実験的機能です。動作や保存するデータの形式は予告なく変わることがあります。人の発言とイベントによるターンには provider の費用がかかります。時計だけのモデル呼び出しは行いません。

### manager との分担と人の判断

manager は担当するリポジトリまたは workspace のゴールを進め、タスクの投入、成果の取り込み、完成の申請を行います。director は全 manager のゴールと未回答の問い合わせを見渡します。マージ待ち、一時停止、保存された `blocked` 通知、未回答の問い合わせなど、人の対応が必要な事項を通知として保存します。manager に尋ねたり伝えたりするときは、話し手を `director` とする manager の会話を使います。同じ対象と保存状態への通知は重複しません。

`takt_tell_manager` は、manager が処理中でも中心へ director_message を送り、永続化された時点で操作 ID と manager を返します。伝言は人以外のイベントのキューに入り、人の入力が先に処理されます。manager の同じ会話を使い、返事・失敗・中断は同じ操作 ID で後から通知されます。

返事・失敗・中断は同じ操作 ID で保存され、あとで director の画面に知らされます。伝言の保存に失敗した場合は受け付けず、道具の失敗として返します。受付後に接続が切れても保存した伝言は残り、director は自動で送り直しません。

daemon を起動し直すと、未開始の伝言は接続がなくても実行されます。daemon の停止で中断した伝言と、起動時に `running` のまま見つかった伝言は、元の受付順で届け直します。人が明示的に中断した伝言は届け直しません。

director はシェルの実行、ファイルへの書き込み、設定の書き換えができません。run の段階、裁定、ログなどタスク内部の確認は各 manager の担当です。マージや仕様の判断、削除など取り返しのつかない操作は人に残し、問い合わせへの回答も代行しません。

人が明示的に「ゴール G をマージして」と指示したときだけ、director は G の manager に、その PR を `takt merge` でマージするよう伝えます。転送前に対象のリポジトリ、ゴール、manager を一意に特定し、現在のゴールが `awaiting_merge` であることと、保存済みの PR 番号・URL を確認します。対象が曖昧、状態が異なる、PR がない、読み取りに失敗した場合は転送せず、理由を人に返します。director 自身はマージしません。manager が `takt_merge_goal_pr` を通じて `takt merge` を実行します。指示の転送や受付だけではマージ成功とせず、あとで届く同じ操作 ID の結果で成否を伝えます。実行時も既存の確認により、ゴールが一時停止・中止・`awaiting_merge` 以外になった場合や、保存済みの PR 番号と違う場合はマージしません。

manager 一覧（`takt_list_managers`）は、読めない project を理由付きで示し、読める manager の処理を続けます。

### イベントと通知

コードの見張りがプロセス消失、PR の状態変化などを観測し、変化や異常があるときだけイベントを届けます。manager の定期的な見回りは、上記の間隔でリポジトリごとに1回行います。director は時計で呼びません。PID の生存や開始時刻を確認できない場合は、死亡と決めつけません。会話ごとの常駐子プロセスがターンの準備・AI・MCP・業務操作を行い、daemon は受付・保存・配送・監視を担います。子の異常終了は実行中のターンの失敗として記録し、自動ではやり直しません。

director の設定は、プロジェクトの `.takt/config.yaml` ではなく、グローバルの `~/.takt/config.yaml` に記述します。

| 設定 | 意味 |
|------|------|
| `director.slack.channel_id` | director と会話し、まとめた通知を受け取る Slack チャンネル。 |
| `director.slack.allowed_user_ids` | Slack から director に発言できるユーザー。`director.slack` を設定するときは必須。空配列では誰の発言も受け付けない。 |

詳しくは[グローバル設定フィールドリファレンス](./configuration.ja.md#グローバル設定フィールドリファレンス)を参照してください。

### Slack を接続する

manager と同じ Slack App と環境変数 `TAKT_SLACK_APP_TOKEN` / `TAKT_SLACK_BOT_TOKEN` を使います。ボットを director のチャンネルへ招待し、`takt daemon` を起動するシェルで両変数を設定してください。Slack 設定を変更したら daemon を起動し直します。トークンは設定ファイルに書かず、環境変数で渡します。

許可された人の発言は同じ director の会話につながり、返事は元の投稿のスレッドに届きます。1回のターンで出た新しい知らせは、チャンネルへの1件の投稿にまとまります。`director.slack` を設定しなければ Slack で送受信しません。App の作成と接続の詳細は、[Slack で director と会話する](./configuration.ja.md#slack-で-director-と会話する)を参照してください。

## 今後の構想

Docker とローカルから選べる実行環境、リポジトリをまたぐゴール、委任した作業の終了通知、裁定機能を検討しています。director が作業どうしの依存、変更対象の重なり、結合後の確認をもとに manager 間の順序を決める機能は未実装です。

## manager のゴールと形式仕様

`assistant.formal_spec` は manager のゴール登録案にも適用されます。manager は登録のたびに質問せず、`true` と `"Y/n"` では Quint と Alloy を両方含め、`false` と `"y/N"` では含めません。project が global に優先し、object の各フィールドを独立に解決します。`comments` と `model_check_timeout_seconds` も対話モードと同じ設定を使います。

開発・実装のゴールには、解釈の誤りで結果が変わる重要な観測可能な振る舞いを Gherkin で記述します。同じ期待結果を受け入れ条件にも重ねて書きません。Gherkin のキーワードは英語で、説明は日本語にできます。調査・文書・運用など、実装を成果物としないゴールには Gherkin を付けません。

TUI と Slack の manager の会話で `/verify` を入力すると、現在の合意から Quint と Alloy の仕様を生成し、対話モードと同じ検査器で検証します。結果は同じ会話に戻り、manager が診断や反例を解釈します。形式仕様が無効なら利用できない旨を表示します。登録前に自動では検証せず、検証だけではゴールを登録したり、登録案や保存済み仕様を書き換えたりしません。

仕様はゴールの任意項目 `specifications: { gherkin?, quint?, alloy? }` にコード本文として保存し、登録案の TUI・Slack 両方に表示します。仕様のない既存ゴールも読み込めます。manager は受け入れ条件と同様に、担当タスクの指示書へ関連する仕様の全文を含め、実装・レビューの基準にします。PR の最終レビュー用タスクには保存された全仕様が自動で入ります。

仕様の全文は `takt_get_goal` の `path: specifications.gherkin`、`specifications.quint`、`specifications.alloy` で読めます。仕様は登録時に決まり、ゴールに保存されます。

workspace の `/verify` は、登録案の対象リポジトリの設定を使います。登録案がない場合は、担当リポジトリが 1 つならその設定を使います。複数ある場合は検証を始めず、対象を伝えて `/make-goal` で登録案を作るよう案内します。

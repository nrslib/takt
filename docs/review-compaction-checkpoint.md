# Progress notes and compaction recovery

## Scope and design

Progress notes and compaction recovery are generic. They are not limited by workflow name, step name or reviewer role. No YAML syntax is added. `takt-development-review` (ja/en) still lacks the unconditional `any("error") -> review` transition; its `needs_fix` paths remain.

The guidance and the storage are separate:

- **Guidance is always composed.** The `progress_notes` template is part of the system prompt of every AI call. `buildWrappedSystemPrompt` (`src/agents/runner-prompt.ts`) adds it to every `runAgent` call: normal Phase 1/2/3 calls, Team Leader parts, parallel sub-steps, internal judges/structured callers and contextless calls such as merge selection. Calls that set up a provider directly compose it through the same `withProgressNotesGuidance` (`src/shared/prompts/progress-notes.ts`): task-name summarization, the sync conflict resolver, interactive assistant calls, and the manager/director turns including formal-spec generation and interpretation. Nothing is excluded by agent kind. The guidance itself promises no storage: it says notes are recorded only when the instructions name a progress notes location, and that a response which must be a specific format (report body, JSON, status tag, single choice) stays in that format.
- **Other obligations and restrictions come first.** The generic feature is called *progress notes* so that it is not confused with the manager's goal work log (`takt_record_goal_work_log`). The guidance says that progress notes do not relax any other obligation or restriction: when the instructions require another way of recording (a recording tool, a report or a file), the agent records there as instructed, and progress notes do not replace it. When a phase or the instructions forbid or limit tool use or file reads (Phase 2/3, judges, companion structured calls), that limit applies.
- **Resumed work checks the current state where tools are allowed.** The guidance tells the agent that work can resume after compaction, an interrupted attempt or a new session, and that the same instructions may arrive again with or without notes. When tools or file reads are allowed, it checks the current files, Git status, command results and reports before acting; otherwise it proceeds with the information provided. It does not repeat completed work or side effects such as edits, commits, appends or external operations. TAKT does not make recovery of an editing step depend on saved notes; this state check is the safeguard, not an extra runtime restriction.
- **Every step's Phase 1 in a run is eligible for recovery and stores notes in the run.** The review scope is resolved while the step's Phase 1 instruction is built, as before this feature, for every step kind. `StepExecutor.prepareInstruction` returns that resolved scope with the instruction (`PreparedStepInstruction.reviewScope`). The callers that start a Phase 1 call then attach the request with `OptionsBuilder.buildProgressNotesRequest(step, reviewScope)`: normal steps (`StepExecutor`), parallel sub-steps (`ParallelRunner`), arpeggio batches (`ArpeggioRunner`, with the engine's current scope) and Team Leader parts (`TeamLeaderRunner` / `team-leader-part-runner.ts`). `buildAgentOptions` itself does not attach a request, so Phase 2/3 options and builders that never start a Phase 1 call (for example the completion-retry judge) have none. The request carries the run report directory, task, step name, step definition and `bindsSourceRevision`; only an `edit: false` request also carries the resolved scope, so the notes identity uses the same scope as the rendered instruction. The run report directory is the storage destination, so notes are stored whether or not the working directory is a Git repository. `runAgent` appends the location line (`parts/progress_notes_location`, in the call's language) and any matched `progress_notes_data` to the user instruction. When the store cannot be opened (an unsafe path, or an I/O, Git or disk failure while fingerprinting), no path or revision is invented and the provider call still starts: the call gets the same compaction recovery and resends the original Phase 1 instruction (with the current attempt's additions) after a compaction. Internal judges started through `executeStructuredAgent` do not carry the request, so they receive the guidance without a location and keep the existing behavior of not resending after a compaction.

The notes are **ordinary agent-authored text**, not a machine checkpoint. Agents leave short visible notes after meaningful units (features, call paths, responsibility boundaries): what was checked or changed, evidence, remaining work and findings/decisions. TAKT records these notes using the existing provider-neutral text event/response path into a private `.log` file below the run's `reports/.takt-report-internal/progress-notes/` directory. Agents do not edit files to save notes. The earlier review-only names are replaced: `src/core/workflow/review-checkpoint.ts` became `progress-notes.ts` (`ProgressNotesRequest`, `progressNotesDirectory`, `excludeProgressNotesPaths`, `excludeProgressNotesScope`, `composeRecoveryInstruction`), `src/infra/review-checkpoint/` became `src/infra/progress-notes/` (`ProgressNotesStore`, `ProgressNotesUnavailableError`, `ProgressNotesRecorder`, `ProgressNotesSession`, `startProgressNotes`), the user-instruction template `review_checkpoint.md` became the system-prompt guidance `progress_notes.md`, and the storage directory `review-checkpoints/` became `progress-notes/`. Logs written under the old directory are not migrated. This document keeps its file name. The historical experiment and verification sections below keep the names that existed when they were run (`review-checkpoint.integration.test.ts`, `src/infra/review-checkpoint/`, work log); they are records, not current file references. There is no marker to emit, JSON progress schema, new tool, RPC, MCP server, shared progress state, lock, progress percentage or state-transition logic.

Progress notes do not change the step's permissions. Earlier revisions forced `readonly`, `edit: false` and disabled bypass for the five reviewers, and the Codex adapter replaced `provider_options.codex.permission_control` with `takt` whenever a recovery instruction was attached. Both overrides are removed: saving is done by TAKT, so it needs no provider permission, and tying it to permissions would make a step's sandbox depend on whether its cwd is a Git repository. Each step keeps its own `edit`, permission profile, Codex `permission_control`/`config_profile`, allowed tools and bypass setting. Only TAKT writes the assigned log; it never interprets a path appearing in a note as an output destination. Caller-configured MCP servers are passed through the existing adapters without extra trust. A Copilot step that resolves to readonly still refuses a nonempty effective caller MCP set unless the record has existing conversation/task-state identity-based trust; workflow caller records do not acquire that trust. The review-specific MCP tool/server/approval list are removed, and the transport remains at its original `src/features/mcp/localConnection.ts`; manager/director imports have no changes.

### Source revision binding

- A step with `edit: false` cannot change its sources, so its log is bound to the source revision (`bindsSourceRevision: true`) exactly as the review logs were: in a Git repository, identity includes the scope and PR OIDs, the file name includes the revision, and reads/saves validate it.
- Any other step (`edit: true` or no `edit` setting) changes the revision and the scope itself. Its log is bound only to cwd, run report directory, task, step name, step definition and the stable Phase 1 instruction (`bindsSourceRevision: false`). Its instruction still renders the review scope resolved for it, but its notes neither use that scope nor run any Git command (including `git rev-parse --show-toplevel`). Notes therefore survive the step's own edits and are reused by same-session compaction recovery and `provider_error_fresh` in the same step attempt. The current files remain authoritative over the notes. A different instruction (a later iteration, other reviewer feedback) is a different log.
- Outside Git (`not_a_git_repository`), an `edit: false` step has no revision to bind. Its log follows the same step identity as an editing step; no Git content or revision is invented.
- The recovery data shows whether TAKT checked the sources: `target.revision` is the revision string for a Git-bound `edit: false` log and `null` for an editing step, work outside Git, or an `edit: false` step whose sources TAKT cannot fingerprint (a submodule gitlink in the parent index, or an untracked entry that is neither a regular file nor a symlink, such as a nested repository or a FIFO). Such an `edit: false` log keeps the scope and PR OIDs in its identity but is not validated again during the call. The guidance tells the agent that `null` means the notes were not checked against the sources.
- When a bound (`edit: false`) step's sources change during the call, for example because a test command writes a non-ignored file or a parallel sibling edits the same worktree, TAKT stops saving and reusing that log for the rest of the call and continues the step. This uses the "notes unavailable" path described below. The same applies when an untracked input listed by Git disappears or is replaced while it is being fingerprinted (an error from `lstat`/`readlink`/no-follow `open`, or a descriptor that no longer matches).
- Notes are auxiliary to the provider's work. The store converts expected failures into `ProgressNotesUnavailableError` (with the original error as `cause`) at its I/O boundary: each filesystem, Git, diff-spool and private-file operation runs through one helper (`storageOperation` in `store.ts`). The helper converts only failures that are known to describe the environment (an allowlist, `isEnvironmentFailure`): a system call error (an error with a `syscall`, such as `EACCES` or `ENOSPC` from the filesystem or a Git spawn failure), a Git process that exits with a status or is killed by a signal (for example an ownership rejection or a broken ref/config/index), the private-file helpers' typed errors (`UnsafePrivateArtifactPathError` for an unsafe, replaced or wrong-type private path, `PrivateArtifactPublicationConflictError`, `PrivateArtifactContentWriteFailedError`, and an `AggregateError` made only of these), and `NonUtf8GitPathError` for an untracked path whose bytes are not UTF-8. The private-file helpers' "not a directory" and "not a regular file" checks now throw `UnsafePrivateArtifactPathError` like the equivalent path checks; their other plain `Error`s are invariants of the helpers. The store's own detections (a changed source revision, an input replaced while it is fingerprinted, a diff spool that ends early) are thrown as `ProgressNotesUnavailableError` directly. The session absorbs only this type, whether it happens while opening the store or during the call: the call starts or continues without notes, keeps compaction recovery with the plain original instruction, and its response and session ID are never discarded, so a successful editing step is not turned into a failure after its side effects. Anything else fails the call, even from inside a storage operation: `TypeError`, `RangeError`, `ReferenceError`, `SyntaxError`, a broken helper invariant such as "Expected file state belongs to another path", and Git path output that is not NUL-terminated or contains an empty path. Such an error is not thrown inside the provider's stream callback, because some clients turn a callback exception into an ordinary provider error (the Codex client catches every exception of its stream loop), which Phase 1 would then retry in a fresh session and repeat the step's side effects. The session stops recording, keeps the error and throws it when the provider call has returned (when the runner finishes the response, builds a recovery instruction or flushes at the end), so `runAgent` rejects with the original error and no `provider_error_fresh` retry happens. `ProgressNotesStore` itself still refuses these targets (it never writes through an unsafe path or trusts an incomplete fingerprint).
- Absorbed failures go to TAKT's debug log (`progress-notes` component, WARN level, with the store's description as `reason` and the original error message as `cause`). That log is written only when debug logging (`logging.debug`) or verbose console output is enabled, and manager/director turns suppress it entirely. With the default settings a storage failure is not visible to the user; no new ordinary warning is added.

### Identity and retention

- A revision-bound log's name binds cwd, run report directory, step name, original task, step definition, review scope, original Phase 1 instruction and repository revision. An editing step's log, and an `edit: false` log outside Git, omit scope, PR OIDs and revision (see above). Separate steps, Team Leader parts and runs do not share files.
- Scope/base discovery, PR ref/OID resolution and log fingerprints use the same `buildReviewGitEnvironment` policy. It preserves the caller's `GIT_INDEX_FILE`, including an alternate index, while anchoring repository discovery to cwd by stripping `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR`. Inherited command config and pathspec overrides are removed on both paths. Hook/filter disabling is shared with the existing safe-Git builder; review calls also disable fsmonitor, recursive submodule traversal and child dirty checks, use C-locale diagnostics and disable external diff/textconv. Metadata helpers receive the resolved environment too (branch/default-branch/merge-base/reflog), rather than falling back to raw `process.env`. Only the review policy preserves the alternate index: existing stage/commit callers retain their original sanitized-index behavior. Each synchronous scope operation resolves its environment once; a Store retains its creation environment for later validations. A new attempt rebuilds it from the current caller environment. Neither path invokes network/credential operations.
- For a materialized PR range, the store resolves the effective base/head refs to commit OIDs with `git rev-parse --verify --end-of-options <ref>^{commit}` in its existing safe Git environment (no shell). Both OIDs are included in identity and revision, and are resolved again on every read/save/append validation. Moving either ref with unchanged local HEAD, worktree bytes and scoped paths invalidates the old log; a missing/non-commit/unresolvable ref is an error, never an empty fingerprint. The effective range uses `HEAD` on the PR head branch as before, not an unused stale PR head ref. During scope collection, missing or non-commit explicit/inferred PR refs leave the range unmaterialized, without substituting another range; local working-tree candidates remain. Operational Git errors still propagate. Once a range is materialized, Store validation requires both refs to keep resolving.
- Scope discovery distinguishes a genuine non-repository from Git failures before the instruction is built. Git uses exit 128 for both, so discovery runs with `LC_ALL=C` and accepts only the canonical non-repository discovery diagnostic (including its filesystem-boundary variant). Configuration errors, ownership rejection, invalid cwd repository metadata, other nonzero results and spawn errors propagate through `createTaskReviewScopeResolver`; they are never treated as a non-repository. Instruction building, which renders the scope, fails the step on them; opening progress notes treats them as a store that cannot be opened and continues without notes. Missing/non-directory cwd retains its existing non-repository result; other filesystem errors propagate. This diagnostic check is limited to repository discovery, not HEAD/ref validation.
- Revision validation includes HEAD (or an explicit unborn marker), separately framed staged and unstaged diffs, and non-ignored untracked contents. The scope likewise unions staged, unstaged and untracked paths, both with and without HEAD. Before the first commit, the staged diff compares against the empty tree; unstaged-only additions can be represented by Git's intent-to-add state. A staged change remains in scope even if working-tree bytes match HEAD. Changing only the index invalidates saved evidence even when scope and working-tree bytes remain unchanged. No commit or tree object is created by validation. The first commit invalidates the unborn log even if source contents are unchanged.
- An unborn HEAD is accepted only when `git rev-parse --verify --quiet HEAD` exits 1, `git symbolic-ref HEAD` successfully names a local branch, and `git show-ref --verify --quiet <branch>` also exits 1 (absent ref). Other statuses, spawn failures, malformed refs/config/index and ownership rejection remain errors, not reusable evidence. No stderr text matching or blanket catch converts Git failures into empty revisions.
- Only the current run's exact `reports/.takt-report-internal/progress-notes/` subtree is excluded from review-scope enumeration and identity, even when not gitignored. The engine passes its resolved report directory to the scope resolver before instructions and `OptionsBuilder` identity inputs are built. Store identity also filters progress notes paths from supplied scope. Other reports, similarly named user files and other runs' logs remain inputs. Enumeration and fingerprint inputs are repository-root relative, including when cwd is a subdirectory. Tracked progress notes are excluded with a literal Git pathspec as well; HEAD itself remains part of the revision. Before creating or accessing a log, Store rejects symlinks and unsafe path components, including ancestors above `.takt`; filesystem-root aliases such as macOS `/var` are normalized separately. Unsafe output paths and operational I/O errors make the Store refuse the log; the step continues without notes.
- Untracked entries have JSON-delimited headers containing path, file/symlink type, mode and content byte length, followed by exactly those bytes. Symlink target bytes are hashed without following the link. Normal files are hashed through a fixed 64 KiB buffer; a non-regular entry is not opened and makes the revision `null` (see above), and no-follow/nonblocking open plus descriptor checks handle replacements. Each staged/unstaged diff has its own kind-and-byte-length header. Untracked path inventories require a final NUL delimiter, nonempty entries and reversible UTF-8; malformed or lossy paths fail closed before exclusions or file hashing, even if they decode to a valid filename. A path that is not UTF-8 can be created by any command during the call, so it makes the notes unavailable without failing an `edit: false` step; a malformed inventory is a Git contract violation and fails the call. The revision format is versioned (`progress-notes-revision-v1`, after the review logs' v5); older-format log files remain historical and are not migrated or trusted under the new fingerprint.
- Flushing a note validates the revision once and then reads/appends the bounded log, rather than validating once to read and again to write (hashing inputs twice). Creating the store computes the revision that names the log and reads that log in the same step, so a call fingerprints once at its start whether or not notes already exist; the session keeps that log for the call's first instruction. Later reads still validate current contents before trusting an existing log, but a read first checks whether the log exists and fingerprints only when it does. Likewise, a recovery instruction built right after a save reuses the log that the save returned instead of reading and fingerprinting again: the session keeps the log from creation or the last save until the provider reports anything other than the compaction itself or the turn's `result`. Codex (rollout compaction) and Pi (compaction after the reply) report the compaction and then the turn's `result` with nothing in between, so the log saved at the compaction serves the recovery instruction. Any other event (text, thinking, tool use or output, a new attempt's init) drops the kept log, because tools or sibling steps may have changed the sources since. When the compaction follows the last save directly, it costs one fingerprint (the save of the last pending text, or none when nothing new was observed since the last save) plus nothing for the recovery instruction. When another event came after the last save and no new text needs saving, for example a tool call that changed the sources, the recovery instruction reads the log and fingerprints once, so a log that no longer matches the sources is not resent. There is no stale metadata cache or lock. Git writes each tracked diff directly to a private temporary spool (directory 0700, file 0600), which TAKT hashes through a fixed 64 KiB buffer and removes in `finally` on success or failure. There is no tracked-diff stdout size ceiling or whole-diff memory read. This preserves synchronous provider callbacks and avoids adding asynchronous note queues; the tradeoff is temporary disk space for one diff and extra disk I/O. Disk/Git/read failures fail closed rather than trust an incomplete hash. Git stderr has a separate 64 KiB diagnostic buffer. Metadata commands (HEAD/ref checks and the untracked path inventory) retain the existing 64 MiB buffer; exceptionally large path inventories still fail explicitly, not silently truncate. Safe Git environment and disabled fsmonitor/external diff/textconv preserve the non-execution safeguards. Scope conservatively includes every tracked submodule path as a review candidate without inspecting child dirtiness. Whenever the parent index contains a gitlink, the store does not fingerprint child contents and records the log with `revision: null` instead of trusting unhashed child contents as a revision; untracked nested repositories and other non-regular inputs are treated the same way.
- Different task/instruction (and, for revision-bound logs, diff) means a different log. For a revision-bound log, changing the target during an attempt refuses further saves and prevents reuse without failing the step. Old files remain available as historical artifacts, not current progress.
- Existing private-file helpers write mode-0600 files atomically. Notes are sanitized with the existing sensitive-text helper. Text chunks are buffered until a non-text event (tool use, thinking, result), call termination or the construction of a recovery instruction; a newline alone does not save. Pending text is also saved when it reaches the 32 Ki-character log bound. Normal split chunks therefore do not split a note in storage, and a revision-bound step fingerprints its sources once per saved batch instead of once per streamed line. Thinking/tool output is not recorded as work notes. Without text events, a successful result/response supplies the note. A failed result/response supplies notes only through the optional provider-confirmed `partialOutput` field, never by guessing whether `content`/`result` differs from `error`. Devin sets this field for nonempty visible assistant output on incomplete (`max_tokens`, `max_turn_requests`, `refusal`) turns, not for empty/auth/transport diagnostics. Event/response copies are not recorded again after visible text or a result has already supplied the note. The marked partial text is available to `provider_error_fresh`; diagnostics are not injected as progress. A storage failure is logged and is not treated as successful persistence; the provider callback never throws for it, only for a programming error as described above.
- Reused notes are JSON data inside `progress_notes_data`; `<`, `>` and `&` in the entire JSON payload are Unicode-escaped so note text cannot close or forge its tag boundary. JSON decoding preserves ordinary Japanese/English notes and literal tag text. This prevents delimiter spoofing, not model-level prompt injection or proof of note accuracy.
- Each retained log is bounded to 32 Ki characters with an explicit omission notice (`[Earlier progress notes omitted; this is not complete coverage.]`). The always-composed guidance asks agents to keep essential evidence/findings in the latest note. A log is evidence, not mechanically verified coverage. Undelivered or unsaved work can be lost.

### Sessions and recovery

Keep `session: continue`, including later steps in the same run and parent workflow calls. Earlier conversation is supporting context but is not authoritative: current instructions/files/latest reports/latest matched log win. An outdated revision-bound log is invalidated without discarding the conversation. Ordinary missing-session-ID behavior, empty continuation, report/completion retry and existing retry limits remain.

The runner uses the optional `ProviderAgent.recoverFromCompaction` abstraction. Every supported recovery rebuilds the original Phase 1 request plus the newest matched notes when storage exists, and the original request alone when it does not. Empty continuations retain their short request and the controller's stable original instruction. `provider_error_fresh` reopens the same target's log for the new session. No log means no fabricated progress. There is no mtime/stagnation heuristic.

Progress notes capture observes raw events **before** the runner suppresses an intermediate successful compaction result. It also finalizes each provider call's response before discarding/replacing that response or rebuilding recovery instructions, including the last call at the recovery limit. Thus successful visible output survives even if the provider emits only a result event or only a response, without text deltas. The recorder, including the callback that rebuilds the recovery instruction from the latest saved notes, is a runner-local argument of the provider call, not a provider option/event; `ProviderCallOptions` has no progress-notes field, so no adapter can change its permissions or profile based on notes. Normal downstream callbacks still receive only the unsuppressed final result; successful intermediate events are not replayed through ordinary result processing. Text, result and response share one per-call deduplication state, reset at call completion even if a same-session recovery emits no new `init`. The existing explicit `partialOutput` requirement for failed output and diagnostic exclusions remain unchanged.

### Final answer and working text

Progress notes are visible text that arrives before the answer, so `AgentResponse.content` (and with it `previous_response`, arpeggio batch output, reports built from Phase 1 output and downstream rule evaluation) contains only the agent's last message. Earlier messages still reach progress notes and the live display through ordinary `text` events; only the result changes. The guidance tells the agent to give the final answer as its last message. Each adapter applies this at its own message boundary.

Text before a tool call is never reused as the answer. A turn that ends with a tool call and no text after it therefore has an empty answer: the adapter returns a successful (`done`) response with empty `content` and the session ID, and Phase 1 continues that session with the existing empty continuation. It is not turned into a provider error, which would start `provider_error_fresh` in a new session and repeat the tools' side effects. Only an output that carries neither assistant text nor tool activity is still reported as unreadable.

Structured output and the rate-limit notice check use it only when the message completed, as before. ### Pi continuation ownership (RC-PI-001)

The pinned `@earendil-works/pi-coding-agent` **1.5.0** declares `compaction_end.willRetry` as a required boolean in `dist/core/agent-session.d.ts`. In `dist/core/agent-session.js`, `_checkCompaction()` selects overflow retry when the interrupted assistant's stop reason is not `stop`; completed-response overflow and threshold compaction pass `false`. `_runAutoCompaction()` emits the successful event and returns `true` when `willRetry` is true. `_startRun()` then awaits `agent.continue()` in its post-run loop, before the original `session.prompt()` resolves. Notifying TAKT for that event used to replay Phase 1 a second time after SDK continuation had already completed.

The Pi adapter now requires **explicit `willRetry === false`** in addition to its existing automatic-reason/result/no-abort/no-error checks. A missing field is not evidence that TAKT owns recovery. Successful threshold and completed-response overflow retain TAKT's same-session Phase 1 plus latest-log reinjection, subject to the existing runner success/session/limit checks. SDK-owned retry emits no TAKT recovery notification. The SDK can also continue to deliver queued messages with `willRetry: false`; this adapter does not submit steering/follow-up messages, and this fix does not add queue coordination or claim a new upstream guarantee for extension-driven queues.

Deterministic client tests cover reason (threshold/overflow/manual/missing) × retry (true/false/missing) × result/abort/error outcomes. Only complete SDK-shaped events are treated as classified; missing-field probes intentionally test malformed runtime input. Runner → actual Pi provider → actual client tests double only the SDK boundary: simulated overflow continuation inside `prompt()` produces one instruction submission and returns the SDK continuation's output, while threshold and overflow with `false` produce exactly two submissions in the same SDK session. This is not a live Pi model/compaction experiment. Codex/OpenCode conditions, ordinary-text saving, MCP policy and `session: continue` are unchanged.

## Unresolved risks / intentionally unchanged behavior

- Copilot steps that resolve to readonly with arbitrary caller MCP servers are intentionally refused by the existing trust boundary; they need a no-MCP assignment or a compatible setup. No live Copilot/MCP execution was performed for this boundary fix.
- DeepSeek's current SDK integration cannot enforce readonly; that provider cannot execute readonly steps safely. The common saving mechanism does not solve this separate capability gap.
- Reviewers are no longer forced to readonly by the checkpoint. Their permissions now come only from their own step settings (`edit: false`, capability sets, profiles, bypass), as before this feature.
- Every step's Phase 1 call in a run now creates a log. The scope is resolved while each step's instruction is built, as before. A revision-bound (`edit: false`) step in a Git repository validates its revision when the store is created (which also covers the existing log used by the call's first instruction), at each save, and when a recovery instruction needs an existing log that was not saved since the provider's last event (one compaction therefore validates once). Saves happen at non-text events after visible text, at the call's end, before a recovery instruction and at the 32 Ki-character bound, not per streamed line. A step that alternates text and tool calls still validates roughly once per text-to-tool transition. Each validation runs synchronous `execFileSync` Git commands (HEAD, index listing, staged and unstaged diffs into a spool, untracked listing) and hashes every relevant untracked file. These calls block the Node.js event loop, so in parallel sub-steps and arpeggio batches they also delay the sibling steps' streams. Large working trees or many untracked files make this cost visible across plan, supervise, review, arpeggio and other `edit: false` steps. Editing steps do not hash sources. The tradeoff of batching is that a stale save is refused at the next boundary rather than at the next line, and text that never reaches a boundary before the process is killed is not saved.
- An editing step's log is not tied to source contents. If something other than the step changes the files between a failure and its fresh retry, the notes can be stale; the guidance tells the agent that current files are authoritative, but TAKT does not detect this.
- Step Phase 1 calls without storage (unsafe paths, storage or Git failures while opening or saving) keep TAKT compaction recovery and resend the original instruction; the agent's current-state check is the only protection against repeating completed side effects. Calls that are not a step's Phase 1 (Phase 2/3, judges, selectors, companion structured calls, auto-routing, task decomposition, calls outside a run and direct provider calls) get the guidance but no recovery request. As before, they do not resend a completed request after a compaction.
- A storage failure (`ProgressNotesUnavailableError`), whether it happens while opening the store or during the call, is recorded only in TAKT's debug log, and only when debug logging or verbose output is enabled (never inside manager/director turns). With default settings it is invisible. The step continues without notes, so a later compaction or `provider_error_fresh` resumes from the original instruction and the current state alone.
- An `edit: false` step outside Git or with sources TAKT cannot fingerprint (submodule gitlinks, untracked nested repositories, non-regular files), like an editing step, reuses notes that TAKT did not check against the sources (`target.revision: null`). Different submodule contents therefore share one log; the agent checks the current state before relying on it.
- Whether a model follows the precedence of other recording obligations (for example the manager's `takt_record_goal_work_log`) and phase tool restrictions over the generic progress notes is model behavior. Deterministic tests verify only that the manager/director prompts are kept intact alongside the guidance; no live manager evaluation scenario was run for this change.
- The guidance is model-facing text in every system prompt. Whether a model leaves useful notes, or keeps format-only responses (reports, JSON, tags) free of notes, is not mechanically guaranteed.
- Model compliance, evidence quality and whether it emits useful/final notes are not mechanically guaranteed. Historical notes and conversational context may be obsolete; current artifacts must take precedence.
- Text not delivered before compaction/failure cannot be recovered. A bounded tail can omit older evidence, and the agent must not infer full coverage from an incomplete log.
- Codex automatic/manual cause classification is not available on the checked path and is not guaranteed. Natural large-review recovery with progress notes, provider outages, and live non-Codex integrations remain unproven. OS-level isolation is not claimed for ordinary provider tool policies.
- Diff spool cleanup covers normal completion and thrown Git/read errors, not uncatchable process termination (for example SIGKILL), which may leave a private temporary directory/file. There is no new background cleanup service or lock.
- Repository discovery relies on Git's canonical C-locale diagnostic because its exit status alone does not distinguish non-repositories from operational errors. An unknown/upstream-changed diagnostic fails closed instead of permitting a log-free review. Ref/content validation is not an atomic repository snapshot; concurrent mutation after a validation remains possible without introducing locks. The next validation detects a changed OID/content, but this does not claim race-free concurrent reviews.
- A programming error (`TypeError`, `RangeError`, `ReferenceError`, `SyntaxError`, a broken private-file helper invariant) and a malformed Git path inventory (missing final NUL or an empty path) are not absorbed and fail the step's Phase 1 call. The environment allowlist is limited to the error shapes listed above; an environment failure that some helper reports as a plain `Error` would also fail the call rather than be hidden. An untracked file whose name is not reversibly UTF-8 makes only the notes unavailable. Review scope collection still fails instruction building for such a file, so this mainly concerns a file created during the call.
- The Claude SDK and claude-headless fallbacks, like claude-terminal, take the text after the last tool call. A turn that ends with a tool call and an empty result now has an empty answer and goes to the empty continuation; a message with only thinking after the last text keeps that text as the answer. The Codex and OpenCode clients likewise start over at each tool item or tool part. OpenCode's `tool` part is the only part type treated as a tool boundary. No live Claude, Codex, OpenCode, Kiro, Cursor or Copilot call was made for these boundaries; deterministic tests cover them.
- Kiro's `finalText` and Copilot's terminal `result` are used only for an output without assistant text. If an upstream version puts all of the turn's messages there and emits no assistant text events, progress notes would reach `content`; no live Kiro or Copilot call was made. Cursor's final answer is taken from its assistant messages because its `result` was confirmed to be the concatenation; no live Cursor call was made.
- DeepSeek takes the answer from the `assistant/message` events it observes. The bundled `@deepseek-ai/dsh-sdk-client` builds `finalResponse` from the same events (the text blocks of the run session's last `assistant/message`) and passes every one of them to the notification callback, so `finalResponse` is used only when no such message was observed, where it is also empty. No live DeepSeek call was made to check whether the harness completes a turn on a message that ends with a tool call; the tests double the SDK. When the answer itself contains sensitive text and the message also has text before its last tool call, the boundary redaction can replace the whole answer with `[REDACTED]` rather than only the sensitive part; this errs toward hiding the answer, not toward exposing a credential.
- Ignored external files/dependencies are not included in the Git target fingerprint. Git/storage errors while opening the store or during the call are logged and stop notes for that call; they do not fail the step. Fixed-size hashing bounds TAKT's content-buffer memory, not Git's internal diff memory, total I/O time or temporary disk use. Every validation still scans tracked diffs and relevant untracked bytes; tracked diffs require enough temporary disk space, and very large metadata/path inventories can exceed their separate Git output buffer. The `progress-notes-revision-v1` format intentionally does not reuse older-format logs.
- Other review workflows' error retry rules remain unchanged: ja/en `development-review`, `mini-core`, `peer-review-suite-{base,cqrs,frontend,frontend-cqrs}`, `review-{backend,backend-cqrs,dual,dual-cqrs,frontend,takt-default}`, `review-fix-{backend,backend-cqrs,dual,dual-cqrs,frontend}`, and `terraform`. `compound-eye` routes its error aggregate to `evaluate`, not the same review step.

# Review work logs and compaction recovery

## Scope and design

`takt-development-review` (ja/en) supplies work-log guidance automatically to its five Phase 1 reviewers when a Git review scope is available. No YAML syntax is added. Only these workflows lose the unconditional `any("error") -> review` transition; their `needs_fix` paths remain.

The log is **ordinary agent-authored text**, not a machine checkpoint. Reviewers leave short visible notes after meaningful units (features, call paths, responsibility boundaries): checked scope, evidence, remaining scope and existing finding IDs. TAKT records these notes using the existing provider-neutral text event/response path into a private `.log` file below the run's `reports/.takt-report-internal/review-checkpoints/` directory. Reviewers do not need to edit files themselves. There is no marker to emit, JSON progress schema, new tool, RPC, MCP server, shared progress state, lock, progress percentage or state-transition logic.

This is intentionally an output-capture approach rather than adding native writable-path exceptions to every provider. There is no common exact-file write permission across the current adapters. Source permissions and allowed tools are not widened, and bypass is disabled. Only TAKT writes the assigned log; it never interprets a path appearing in a note as an output destination. Caller-configured MCP servers are still passed through the existing adapters; they are not granted extra trust. Enforcing readonly on these reviewers can therefore reject configurations that ran under a broader profile. In particular, Copilot refuses any nonempty effective caller MCP server set in readonly mode unless the record has existing conversation/task-state identity-based trust. Workflow caller records do not acquire that trust, even if their names/arguments describe read-only tools. There is no existing generic read-only caller-MCP certification mechanism to reuse safely. Remove the caller MCP assignment for a Copilot review or choose another compatible setup; this change does not loosen permissions or extend MCP trust. The review-specific MCP tool/server/approval list are removed, and the transport remains at its original `src/features/mcp/localConnection.ts`; manager/director imports have no changes.

### Identity and retention

- A log's name binds cwd, run report directory, reviewer, original task, reviewer definition, review scope, original Phase 1 instruction and repository revision. Separate reviewers/runs do not share files.
- Scope/base discovery, PR ref/OID resolution and log fingerprints use the same `buildReviewGitEnvironment` policy. It preserves the caller's `GIT_INDEX_FILE`, including an alternate index, while anchoring repository discovery to cwd by stripping `GIT_DIR`, `GIT_WORK_TREE` and `GIT_COMMON_DIR`. Inherited command config and pathspec overrides are removed on both paths. Hook/filter disabling is shared with the existing safe-Git builder; review calls also disable fsmonitor, recursive submodule traversal and child dirty checks, use C-locale diagnostics and disable external diff/textconv. Metadata helpers receive the resolved environment too (branch/default-branch/merge-base/reflog), rather than falling back to raw `process.env`. Only the review policy preserves the alternate index: existing stage/commit callers retain their original sanitized-index behavior. Each synchronous scope operation resolves its environment once; a Store retains its creation environment for later validations. A new attempt rebuilds it from the current caller environment. Neither path invokes network/credential operations.
- For a materialized PR range, the store resolves the effective base/head refs to commit OIDs with `git rev-parse --verify --end-of-options <ref>^{commit}` in its existing safe Git environment (no shell). Both OIDs are included in identity and revision, and are resolved again on every read/save/append validation. Moving either ref with unchanged local HEAD, worktree bytes and scoped paths invalidates the old log; a missing/non-commit/unresolvable ref is an error, never an empty fingerprint. The effective range uses `HEAD` on the PR head branch as before, not an unused stale PR head ref. During scope collection, missing or non-commit explicit/inferred PR refs leave the range unmaterialized, without substituting another range; local working-tree candidates remain. Operational Git errors still propagate. Once a range is materialized, Store validation requires both refs to keep resolving.
- Scope discovery distinguishes a genuine non-repository from Git failures before checkpoint setup. Git uses exit 128 for both, so discovery runs with `LC_ALL=C` and accepts only the canonical non-repository discovery diagnostic (including its filesystem-boundary variant). Configuration errors, ownership rejection, invalid cwd repository metadata, other nonzero results and spawn errors propagate through `createTaskReviewScopeResolver`; they do not select a log-free review. Missing/non-directory cwd retains its existing non-repository result; other filesystem errors propagate. This diagnostic check is limited to repository discovery, not HEAD/ref validation.
- Revision validation includes HEAD (or an explicit unborn marker), separately framed staged and unstaged diffs, and non-ignored untracked contents. The scope likewise unions staged, unstaged and untracked paths, both with and without HEAD. Before the first commit, the staged diff compares against the empty tree; unstaged-only additions can be represented by Git's intent-to-add state. A staged change remains in scope even if working-tree bytes match HEAD. Changing only the index invalidates saved evidence even when scope and working-tree bytes remain unchanged. No commit or tree object is created by validation. The first commit invalidates the unborn log even if source contents are unchanged.
- An unborn HEAD is accepted only when `git rev-parse --verify --quiet HEAD` exits 1, `git symbolic-ref HEAD` successfully names a local branch, and `git show-ref --verify --quiet <branch>` also exits 1 (absent ref). Other statuses, spawn failures, malformed refs/config/index and ownership rejection remain errors, not reusable evidence. No stderr text matching or blanket catch converts Git failures into empty revisions.
- Only the current run's exact `reports/.takt-report-internal/review-checkpoints/` subtree is excluded from review-scope enumeration and identity, even when not gitignored. The engine passes its resolved report directory to the scope resolver before instructions and `OptionsBuilder` identity inputs are built. Store identity also filters checkpoint paths from supplied scope. Other reports, similarly named user files and other runs' logs remain inputs. Enumeration and fingerprint inputs are repository-root relative, including when cwd is a subdirectory. Tracked checkpoint outputs are excluded with a literal Git pathspec as well; HEAD itself remains part of the revision. Before creating or accessing a checkpoint, Store rejects symlinks and unsafe path components, including ancestors above `.takt`; filesystem-root aliases such as macOS `/var` are normalized separately. Unsafe output paths disable checkpoint reuse/capture, not the review; operational I/O errors propagate.
- Untracked entries have JSON-delimited headers containing path, file/symlink type, mode and content byte length, followed by exactly those bytes. Symlink target bytes are hashed without following the link. Normal files are hashed through a fixed 64 KiB buffer; unsupported non-regular entries fail closed before opening, and no-follow/nonblocking open plus descriptor checks handle replacements. Each staged/unstaged diff has its own kind-and-byte-length header. Untracked path inventories require a final NUL delimiter, nonempty entries and reversible UTF-8; malformed or lossy paths fail closed before exclusions or file hashing, even if they decode to a valid filename. The revision format is versioned (now v5); older-format log files remain historical and are not migrated or trusted under the new fingerprint.
- Flushing a note validates the revision once and then reads/appends the bounded log, rather than calling public `read()` and `save()` (and hashing inputs twice). Reads/recovery still validate current contents; there is no stale metadata cache or lock. Git writes each tracked diff directly to a private temporary spool (directory 0700, file 0600), which TAKT hashes through a fixed 64 KiB buffer and removes in `finally` on success or failure. There is no tracked-diff stdout size ceiling or whole-diff memory read. This preserves synchronous provider callbacks and avoids adding asynchronous note queues; the tradeoff is temporary disk space for one diff and extra disk I/O. Disk/Git/read failures fail closed rather than trust an incomplete hash. Git stderr has a separate 64 KiB diagnostic buffer. Metadata commands (HEAD/ref checks and the untracked path inventory) retain the existing 64 MiB buffer; exceptionally large path inventories still fail explicitly, not silently truncate. Safe Git environment and disabled fsmonitor/external diff/textconv preserve the non-execution safeguards. Scope conservatively includes every tracked submodule path as a review candidate without inspecting child dirtiness. Store refuses checkpoints whenever the parent index contains a gitlink, so reviews proceed without checkpoint reuse/capture rather than trust unhashed child contents; untracked nested repositories and other non-regular inputs likewise disable checkpoints.
- Different task/instruction/diff means a different log; changing the target during an attempt refuses further saves and prevents reuse. Old files remain available as historical artifacts, not current progress.
- Existing private-file helpers write mode-0600 files atomically. Notes are sanitized with the existing sensitive-text helper. Text chunks are buffered until a newline, a non-text event or call termination, so normal split chunks do not split a note in storage. Thinking/tool output is not recorded as work notes. Without text events, a successful result/response supplies the note. A failed result/response supplies notes only through the optional provider-confirmed `partialOutput` field, never by guessing whether `content`/`result` differs from `error`. Devin sets this field for nonempty visible assistant output on incomplete (`max_tokens`, `max_turn_requests`, `refusal`) turns, not for empty/auth/transport diagnostics. Event/response copies are not recorded again after visible text or a result has already supplied the note. The marked partial text is available to `provider_error_fresh`; diagnostics are not injected as progress. A storage failure is surfaced outside provider callbacks as well; it is not successful persistence.
- Reused notes are JSON data inside `review_checkpoint_data`; `<`, `>` and `&` in the entire JSON payload are Unicode-escaped so note text cannot close or forge its tag boundary. JSON decoding preserves ordinary Japanese/English notes and literal tag text. This prevents delimiter spoofing, not model-level prompt injection or proof of note accuracy.
- Each retained log is bounded to 32 Ki characters with an explicit omission notice. Agents are instructed to keep essential evidence/findings in the latest note. A log is evidence, not mechanically verified coverage. Undelivered or unsaved work can be lost.

### Sessions and recovery

Keep `session: continue`, including later reviews in the same run and parent workflow calls. Earlier conversation helps recall finding history and references but is not authoritative: current instructions/code/latest reports/latest matched log win. An outdated log is invalidated without discarding the conversation. Ordinary missing-session-ID behavior, empty continuation, report/completion retry and existing retry limits remain.

The runner uses the optional `ProviderAgent.recoverFromCompaction` abstraction. Every supported recovery rebuilds the original Phase 1 request plus the newest matched log. Empty continuations retain their short request and the controller's stable original instruction. `provider_error_fresh` reopens the same target's log for the new session. No log means no fabricated progress. There is no mtime/stagnation heuristic.

Work-log capture observes raw events **before** the runner suppresses an intermediate successful compaction result. It also finalizes each provider call's response before discarding/replacing that response or rebuilding recovery instructions, including the last call at the recovery limit. Thus successful visible output survives even if the provider emits only a result event or only a response, without text deltas. The recorder is runner-local, not a new provider option/event. Normal downstream callbacks still receive only the unsuppressed final result; successful intermediate events are not replayed through ordinary result processing. Text, result and response share one per-call deduplication state, reset at call completion even if a same-session recovery emits no new `init`. The existing explicit `partialOutput` requirement for failed output and diagnostic exclusions remain unchanged.

## Provider capabilities (current adapters, not upstream promises)

| Provider | Work-log saving | TAKT compaction-triggered reinjection |
|---|---|---|
| Codex | Ordinary text events, TAKT-owned private log; source sandbox remains readonly | **Confirmed `compacted`, cause unclassified**: a stream event or a new rollout record becomes `context_compacted`. Includes explicit `new_context`; no automatic/manual distinction is guaranteed. Phase 1 resumes the same session after a `done` response, with the existing limit of three recoveries |
| Claude / claude-sdk / claude-headless / claude-terminal | Same text/response capture, existing readonly tools/permissions | No `recoverFromCompaction` on these adapters |
| OpenCode | Same text/response capture, existing permissions | **v2 automatic completion only**: `session.compaction.ended` with `reason: auto` becomes `context_compacted`, then the same session is resumed. Manual/start/failure events and v1 `session.compacted` without a verified reason do not trigger it. Explicit `session: compact` remains separate |
| Pi | Same text/response capture, existing readonly tool policy | **Successful automatic completion without SDK retry only**: SDK `compaction_end` with threshold/overflow reason, `willRetry: false`, a result, no abort and no error becomes `context_compacted`. `willRetry: true` leaves continuation to the SDK, without TAKT replay. Missing retry/reason classification and manual/failed/aborted events do not trigger it; same-session resume is guarded |
| Kiro | Same text/response capture, existing `--trust-tools=read,grep` policy | No. Current overflow-notice handling returns an error, not a validated compaction notification/session recovery |
| Cursor / Devin | Same text/response capture, existing permission handling | No `recoverFromCompaction` on these adapters |
| Copilot | Same capture **without arbitrary caller MCP**; a nonempty effective caller MCP set is rejected under readonly before the client call. Existing identity-trusted conversation/task-state exceptions are not extended to workflow callers | No `recoverFromCompaction` on this adapter |
| deepseek-harness | Capture itself is provider-neutral, but **readonly review execution is blocked** by the existing adapter: it rejects permission controls before starting the SDK | No. This change does not remove the refusal or silently run the unrestricted coding tools |
| Mock | Same capture for deterministic testing | No real automatic compaction capability |

Kiro's client currently emits its text after CLI completion. Other providers can also buffer delivery, so the file cannot recover notes that never reached TAKT. This implementation does not claim live coverage for every provider or introduce unsupported SDK permission settings. DeepSeek readonly review availability is an unresolved limitation, not a successful all-provider execution result.

### Pi continuation ownership (RC-PI-001)

The pinned `@earendil-works/pi-coding-agent` **1.5.0** declares `compaction_end.willRetry` as a required boolean in `dist/core/agent-session.d.ts`. In `dist/core/agent-session.js`, `_checkCompaction()` selects overflow retry when the interrupted assistant's stop reason is not `stop`; completed-response overflow and threshold compaction pass `false`. `_runAutoCompaction()` emits the successful event and returns `true` when `willRetry` is true. `_startRun()` then awaits `agent.continue()` in its post-run loop, before the original `session.prompt()` resolves. Notifying TAKT for that event used to replay Phase 1 a second time after SDK continuation had already completed.

The Pi adapter now requires **explicit `willRetry === false`** in addition to its existing automatic-reason/result/no-abort/no-error checks. A missing field is not evidence that TAKT owns recovery. Successful threshold and completed-response overflow retain TAKT's same-session Phase 1 plus latest-log reinjection, subject to the existing runner success/session/limit checks. SDK-owned retry emits no TAKT recovery notification. The SDK can also continue to deliver queued messages with `willRetry: false`; this adapter does not submit steering/follow-up messages, and this fix does not add queue coordination or claim a new upstream guarantee for extension-driven queues.

Deterministic client tests cover reason (threshold/overflow/manual/missing) × retry (true/false/missing) × result/abort/error outcomes. Only complete SDK-shaped events are treated as classified; missing-field probes intentionally test malformed runtime input. Runner → actual Pi provider → actual client tests double only the SDK boundary: simulated overflow continuation inside `prompt()` produces one instruction submission and returns the SDK continuation's output, while threshold and overflow with `false` produce exactly two submissions in the same SDK session. This is not a live Pi model/compaction experiment. Codex/OpenCode conditions, ordinary-text saving, MCP policy and `session: continue` are unchanged.

### Codex cause-identification evidence and decision

The checked contract is `@openai/codex-sdk` **0.164.0**, pinned in `managed/codex/package.json` and installed in `node_modules/@openai/codex-sdk/`. Its `dist/index.d.ts` `ThreadEvent` union has no compaction event or cause field. `dist/index.js` `runStreamedInternal` parses CLI JSON and yields it without adding cause information. TAKT's `src/infra/codex/client.ts` accepts a runtime `compacted` event through its open event shape, or detects a `type: compacted` record in the call's rollout range via `compaction.ts`. The typed SDK does not promise that a streaming compaction event will be delivered; the saved live run below includes a rollout record that this detector recognizes.

The current ordinary-log experiment's raw rollout, `worklog-SoCaJN/codex-home/sessions/2026/11/14/rollout-2026-11-14T22-04-33-01a1da28-d936-79a3-8d5e-da0f825ffaab.jsonl` (under `.takt/checkpoint-experiment/`), records explicit `new_context` at ordinal **27**, then `compacted` at **31**. The record has history/retention/window/usage/resume metadata but no automatic/manual cause discriminator. Its `resume_metadata.turn_attribution.turn_trigger` is `exec`, the turn's entrypoint, not a compaction cause; input usage is **16,362** tokens. `events.jsonl` then records `context_compacted` followed by init for the same session and the B-only source read. This proves reinjection after explicitly reproduced compaction, **not natural-threshold-only detection**.

The original failed-review rollout `/Users/nrs/.codex/sessions/2026/11/14/rollout-2026-11-14T17-13-28-01a1d91e-5c04-76f1-83b8-2a04c33716a4.jsonl` also records `new_context` (**347**) before `compacted` (**351**), with **247,289** input tokens and the same payload fields/`exec` attribution. Both rollouts identify CLI **0.164.0** and originator `codex_sdk_ts`. The presence of a `new_context` call therefore cannot distinguish the forced experiment from the large-review case; token counts do not establish why the call occurred. The large-review artifact is not proof of a separately identified automatic trigger either.

No reliable cause discriminator was found in these SDK/runtime artifacts or the current client path. This is a scoped finding, not a claim about every upstream version or protocol. **Keep Codex recovery enabled for confirmed compaction regardless of cause**: excluding explicit `new_context`, or disabling recovery whenever cause is unknown, would remove requested recovery rather than correct an implementation bug. A `new_context` call alone is not completion evidence. Successful Phase 1 completion and session matching/continuation safeguards still apply. OpenCode's verified `reason: auto` and Pi's successful threshold/overflow completion with explicit `willRetry: false` retain their separate provider contracts; their stronger cause contracts are not imposed on Codex.

## Unresolved risks / intentionally unchanged behavior

- Copilot readonly reviews with arbitrary caller MCP servers are intentionally refused by the existing trust boundary; they need a no-MCP assignment or a compatible setup. No live Copilot/MCP execution was performed for this boundary fix.
- DeepSeek's current SDK integration cannot enforce readonly; that provider cannot execute these readonly reviews safely. The common saving mechanism does not solve this separate capability gap.
- Model compliance, evidence quality and whether it emits useful/final notes are not mechanically guaranteed. Historical notes and conversational context may be obsolete; current artifacts must take precedence.
- Text not delivered before compaction/failure cannot be recovered. A bounded tail can omit older evidence, and the agent must not infer full coverage from an incomplete log.
- Codex automatic/manual cause classification is not available on the checked path and is not guaranteed. Natural large-review recovery with work logs, provider outages, and live non-Codex integrations remain unproven. OS-level isolation is not claimed for ordinary provider tool policies.
- Diff spool cleanup covers normal completion and thrown Git/read errors, not uncatchable process termination (for example SIGKILL), which may leave a private temporary directory/file. There is no new background cleanup service or lock.
- Repository discovery relies on Git's canonical C-locale diagnostic because its exit status alone does not distinguish non-repositories from operational errors. An unknown/upstream-changed diagnostic fails closed instead of permitting a log-free review. Ref/content validation is not an atomic repository snapshot; concurrent mutation after a validation remains possible without introducing locks. The next validation detects a changed OID/content, but this does not claim race-free concurrent reviews.
- Ignored external files/dependencies are not included in the Git target fingerprint. Git/storage errors are explicit failures. Fixed-size hashing bounds TAKT's content-buffer memory, not Git's internal diff memory, total I/O time or temporary disk use. Every validation still scans tracked diffs and relevant untracked bytes; tracked diffs require enough temporary disk space, and very large metadata/path inventories can exceed their separate Git output buffer. The v5 revision format intentionally does not reuse older-format work logs.
- Other review workflows' error retry rules remain unchanged: ja/en `development-review`, `mini-core`, `peer-review-suite-{base,cqrs,frontend,frontend-cqrs}`, `review-{backend,backend-cqrs,dual,dual-cqrs,frontend,takt-default}`, `review-fix-{backend,backend-cqrs,dual,dual-cqrs,frontend}`, and `terraform`. `compound-eye` routes its error aggregate to `evaluate`, not the same review step.

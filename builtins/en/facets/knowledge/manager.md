# Choosing TAKT operations

Goal lists/details, task lists and run details read persisted state and results.
Workflow listing provides candidates and descriptions. Goal task submission fixes the base to the goal branch, saves the goal ID and purpose, and checks prohibited system effects through workflow calls.
Code coordinates execution within the existing concurrency limit. Goal tasks do not use automatic resubmission or post-PR Caccia, so the manager owns failure decisions.
Completion events contain the result, branch, SHA, interruption, failure reason and run identifier. Every event turn uses a fresh session and pending events can be recovered later.
Review results with takt_get_goal_diff (goal/task file list, line counts and a requested file patch), takt_get_goal_history (bounded history), and takt_get_goal_relation (target containment and goal commits ahead). Truncated output is incomplete evidence; request needed files to supplement it.
takt_merge_goal_task accepts goalId, taskName and expectedSha, verifies saved ownership and the current SHA, merges into the saved goal branch, and records the work unit result. Business acceptance belongs to the manager. Checked-out targets return locations; conflicts abort and return file names. Human worktrees remain unchanged.
takt_complete_goal accepts goalId, expectedSha and summary (satisfied acceptance criteria and evidence). Repository manager.main_merge is auto / approve, defaulting to approve. Auto integrates into the configured target before completing. Approve, or auto with a checked-out target, saves the branch, SHA, summary and instructions and waits for a human merge. summary contains acceptance criteria and evidence. The tool generates changeSummary separately from the diff. truncated marks omitted files; totalsTruncated marks incomplete totals. Explain the change summary and saved worktrees and instructions to the human.
takt_check_goal_completion verifies containment of the saved approved SHA after a human merge and completes the goal. It does not substitute the current goal tip for that SHA. If recorded is false, distinguish the actual operation result from the persistence error, recheck and retry recording. Completed goals cannot accept new work.
Summaries are persisted and displayed on TUI startup or the next user message.

takt_ask_goal_question saves goalId, body and optional options, recommendation and dependentWorkKeys, returning questionId. takt_list_goal_questions and takt_get_goal_question read pending / answered / withdrawn status and answer content. takt_withdraw_goal_question withdraws a pending question. When takt_enqueue_goal_task workKey matches a pending question's dependentWorkKeys, submission is rejected before saving with the question ID. Work with no key or an unrelated key remains available.
Humans use /answer questionID in the TUI and arrow keys and Enter to choose an option or free text. Answers are saved with source: tui and a timestamp; common events with kind: answer, questionId and answer reach a fresh event turn. Failed turns are recovered using the same pending event.
takt_notify_goal accepts goalId, kind (blocked / custom), body and optional severity (info / warning / error). Question creation, work integration and transitions to awaiting_merge / completed notify automatically. manager.notifications question / awaiting_merge / completed / progress / blocked / custom are per-kind booleans, all enabled by default. Disabling a kind affects TUI events and Slack notifications; question display and dependency checks remain. Code delivers to Slack after saving, skips delivery when no webhook is configured, and records delivery failures as diagnostics while work continues.

Progress status and executionStatus are independent. Humans switch between active and paused with single-line TUI commands /pause <goalId> and /resume <goalId>. The goal ID is required, and the current display identifies paused goals. No MCP tools pause or resume goals. Pause and resume preserve awaiting-merge completion evidence, SHA and instructions. Submission, resubmission, integration, completion and completion checks for paused goals return an error explaining the reason; pending tasks remain unclaimed. Ordinary tasks and other goals continue to be claimed. In-flight tasks finish, and completion results and answer events are saved while manager turns are deferred during pause. Resume processes saved pending events and judges automatic startup even without events, using the existing auto_run, content resolution and run/watch ownership conditions. Paused tasks alone do not start a run automatically. Aborted goals still save events without invoking the manager. Humans can transition active or paused to aborted by confirming /abort <goalId>. The ID is required, cancellation is the default, and abort cannot be undone. The current display and restarted TUI identify aborted goals. Resuming an aborted goal is rejected. Only its pending tasks are saved as failed with an abort reason and retryable: false, and excluded from claim and automatic launch. Pending update failures retain aborted state and can be retried through another confirmed abort. Running tasks in automatic run and direct run/watch read saved state every 500ms and interrupt only the belonging task signal. Other goals and ordinary tasks continue; paused tasks are not interrupted. Abort reasons, run identity and completion results are saved. Submission, resubmission, integration, completion and completion checks after abort are rejected before replaying saved results. Branches, sub-PRs and goal records are retained without automatic deletion or closing. No abort MCP tool is exposed, and existing Ctrl+C behavior is preserved. Acceptance criteria start at version 1.
Decisions own choices, reasons and evidence; operations own pending / completed side effects and results. Submission, integration, completion, questions, notifications, question withdrawal and completion checks can retry using event operation names. Operations are saved before side effects. If goal saving fails after successful queue publication, goal_operation_id recovers the same task; if goal saving fails after a Git update, containment of the saved SHA recovers original evidence. New Git changes retain ownership, SHA and checkout checks. Replays do not add saved notifications or resend to Slack. Slack delivery loss after saving and before sending is not guaranteed against.
Legacy ID-less events, sessions and decisions are normalized on read without changing saved files; the next update saves only the new format. Old event sessions are never resumed. Question recipient is human / director; answer source is tui / slack / director. Director forwarding and Slack reception are not implemented. delegation_completion represents requestId, result and evidenceRefs. Decision actor is manager / human / adjudicator, and adjudicator operations can represent permission, stopping or escalation to a human. Request execution and adjudicator execution are not implemented.

# Choosing TAKT operations

## Workspaces

A workspace stores its ID, name and assigned repositories in `~/.takt/workspaces/<ID>/workspace.json`. A repository belongs to at most one workspace. Adding a second repository to a standalone manager creates a workspace.

The three assignment tools are available only in the manager tool set. Additions must be Git repositories and must not belong to another workspace. Subdirectories and symbolic links resolve to the Git repository root. Removal changes membership only. Repositories with unfinished goals cannot be removed; paused goals count as unfinished, completed and aborted goals do not.

Manager MCP reads the current assignment for each operation and requires the Git repository containing `cwd` to be assigned. Nested unassigned repositories are also rejected. A subdirectory of an assigned repository operates on that repository. All tasks in a goal run within its repository.

## Execution mechanics

Submitted tasks start from the goal-branch tip at the time execution begins.
The Concurrency limit line in the system prompt gives this project's run / watch limit, not free slots. Other goals and ordinary tasks share the slots; work above the limit waits.
Goal tasks do not use automatic resubmission or post-PR Caccia, so the manager owns failure decisions.
Completion saves a JSON event containing the result, branch, SHA, interruption, failure reason and run identifier in a project inbox under the global configuration directory. Registration and human answers also create events. Between human conversation turns, the TUI delivers one event at a time to the same session and deletes its file after processing. Events remain in the inbox while the TUI is absent.

## Tools and persisted state

Goal lists/details, task lists and run details read persisted state and results.
Workflow listing provides candidates and descriptions. Goal task submission saves the goal ID and purpose, and checks prohibited system effects through workflow calls.
takt_requeue_goal_task returns the same failed or exceeded goal task to pending to resume from its saved stopping position, with optional additional instructions in retryNote. takt_retry_goal_task redoes the same failed task using corrected full instructions in task and an optional startStep. Omitting the start uses the existing retry default. It cannot be used for exceeded tasks. When resuming or redoing a failed task, if an error says the saved resume position cannot be used, choose where to restart from the start positions listed in the error and the run details, and call again with that position in startStep. Resuming an exceeded task does not accept startStep, and fails when no saved stopping position exists.
takt_remove_goal_task accepts cwd, goalId, taskName, required reason to cancel unneeded pending tasks or clean up stopped tasks you will not retry and integrated completed tasks. Running tasks and completed tasks that have not been integrated are excluded. Pending cancellation is available only for goals still in progress and not paused.
Review results with takt_get_goal_diff (goal/task file list, line counts and a requested file patch), takt_get_goal_history (bounded history), and takt_get_goal_relation (target containment and goal commits ahead). Truncated output is incomplete evidence; request needed files to supplement it.
takt_merge_goal_task accepts goalId, taskName and expectedSha, verifies saved ownership and the current SHA, merges into the saved goal branch, and records the integration in workLog. Business acceptance belongs to the manager. Checked-out targets return locations; conflicts abort and return file names. Human worktrees remain unchanged.
takt_complete_goal accepts goalId, expectedSha and summary (satisfied acceptance criteria and evidence). Repository manager.main_merge is auto / approve, defaulting to approve. Auto integrates into the configured target before completing. Approve, or auto with a checked-out target, saves the branch, SHA, summary and instructions and waits for a human merge. summary contains acceptance criteria and evidence. The tool generates changeSummary separately from the diff. truncated marks omitted files; totalsTruncated marks incomplete totals. Explain the change summary and saved worktrees and instructions to the human.
takt_check_goal_completion verifies containment of the saved approved SHA after a human merge and completes the goal. It does not substitute the current goal tip for that SHA. Completed goals cannot accept new work.
Summaries are persisted and displayed on TUI startup or the next user message.

takt_ask_goal_question saves goalId, body and optional options and recommendation, returning questionId. Read questions and answers with takt_list_goal_questions and takt_get_goal_question, and withdraw pending questions with takt_withdraw_goal_question. The manager decides which work can proceed while awaiting an answer.
Humans answer via /answer <questionId> in the TUI. The answer is saved in goal memory with source: tui and a timestamp, and an answer event is delivered from the inbox to the same conversation.
takt_notify_goal accepts goalId, kind (blocked / custom), body and optional severity (info / warning / error). Question creation, work integration and transitions to awaiting_merge / completed notify automatically. manager.notifications question / awaiting_merge / completed / progress / blocked / custom are per-kind booleans, all enabled by default. Disabling a kind affects TUI events and Slack notifications; question display remains. Code delivers to Slack after saving, skips delivery when no webhook is configured, and records delivery failures as diagnostics while work continues.

Progress status and executionStatus are independent. Humans switch between active and paused with single-line TUI commands /pause <goalId> and /resume <goalId>. The goal ID is required, and the current display identifies paused goals. No MCP tools pause or resume goals. Pause and resume preserve awaiting-merge completion evidence, SHA and instructions. Submission, resubmission, integration, completion and completion checks for paused goals return an error explaining the reason; pending tasks remain unclaimed. Ordinary tasks and other goals continue to be claimed. In-flight tasks finish, and completion results and answer events are saved while manager turns are deferred during pause. Resume processes saved pending events and judges automatic startup even without events, using the existing auto_run, content resolution and run/watch ownership conditions. Paused tasks alone do not start a run automatically. Abort deletes the goal inbox events and prevents new ones from being saved. Humans can transition active or paused to aborted by confirming /abort <goalId>. The ID is required, cancellation is the default, and abort cannot be undone. The current display and restarted TUI identify aborted goals. Resuming an aborted goal is rejected. Only its pending tasks are saved as failed with an abort reason and retryable: false, and excluded from claim and automatic launch. Pending update failures retain aborted state and can be retried through another confirmed abort. Running tasks in automatic run and direct run/watch periodically read saved state and interrupt only the belonging task signal. Abort is not necessarily immediate; paused tasks are not interrupted. Abort reasons, run identity and completion results are saved. Submission, resubmission, integration, completion and completion checks after abort are rejected before replaying saved results. No abort MCP tool is exposed. Acceptance criteria start at version 1.

Before acting, inspect tasks.yaml, run records and reports, and Git. Do not repeat submissions, merges, resumes or removals that have already happened. For interrupted work, inspect its reports and working directory; tell the human if you cannot resolve it. Tools check goal membership, current state immediately before acting and the reviewed SHA. Keep short workLog entries describing submissions, integrations, abandoned work and their reasons.

Goal memory contains the objective, out-of-scope items, acceptance criteria, constraints, workLog, questions and answers. Registration is performed directly by the TUI after human approval. The manager can append workLog entries from any conversation turn. Current task and merge state comes from tasks.yaml, run artifacts and Git.

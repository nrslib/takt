**Impact path audit (required before finalizing the plan):**

1. Before planning, enumerate the source of truth's atomic contract elements that can independently affect an observation. Include named fields or members, variants, default-versus-explicit precedence, authority / precedence / override among multiple candidates (which input or source of truth wins), modes, order, and other elements that can be changed, omitted, or reordered independently. For a collection, list, or map, also separate member identity, membership / cardinality, order, duplicates, omissions, and any tie / precedence defined by the source of truth or code. Runtime immutability or `Object.freeze` only prevents in-place mutation at runtime; it does not make finite variants in the source of truth or source fixture, an isolated copy, or equivalent input at the same consumer boundary inapplicable to mutation testing. Naming only a parent object, section, or path does not count as confirming its independent children. Assign a stable ID to every enumerated atomic element and reuse that ID in the mutation ledger and final table; a parent label or path name cannot stand in for those IDs
2. Map every atomic element to the actual consumer's read, transform, terminal, or preservation of an unchanged value. For each consumer boundary, record the accepted states, rejected states, and failure behavior from the source of truth and code; a positive state alone is not confirmation. The applicable finite scope inventory for an accepted finding must include not only defect paths requiring code changes, but also sibling paths that are currently correct and therefore verify-only / preservation, at the same level of detail; do not shrink the scope to the first change target found. When a top-level entry evaluates independent siblings in sequence, do not stop at a direct helper: record the shared / prior stages and each target consumer / terminal actually reached from that entry. Do not add unrelated imaginary stages. Trace, from entry to terminal in code, only the stages that exist in the current implementation and are actually traversed from an actual top-level production entry to the target consumer / terminal within the finite scope set by the task / accepted finding, including verify-only / preservation paths: definition, generation, transformation or validation, persistence or restoration, consumer, retry, fallback, parallel path, or external result. For every applicable contract element / path, include at least one canonical row that follows an actual top-level production entry end to end through the actual shared / prior stages, target consumer, and terminal. An isolated copy or direct consumer-boundary mutation is an additional falsification, not a substitute for the canonical full-path trace. A direct helper may be canonical only when the source and code establish it as the production entry; state that evidence

A canonical entry-to-terminal row is not an endpoint list: record every real intermediate stage that actually reads, loads, selects, resolves, parses, transforms, serializes, escapes, interpolates, templates, dispatches, or persists the value, with each stage's source path, function / helper name, and execution order. Treat a path that omits even one value-affecting intermediate stage as incomplete, and add no unrelated stage.

Within that row, identify every real file or module and function / helper as a caller-to-callee sequence in execution order. When the top-level entry reaches independent sibling branches, trace each branch separately from that entry through its own consumer and terminal instead of collapsing them into one endpoint summary.

Every canonical row and evidence-path entry must begin at the actual top-level production entry and include, before its terminal, every shared / prior, value-affecting, and effectful stage in execution order; do not begin at the defining source or a direct consumer. Repeat the full entry prefix for each sibling terminal instead of abbreviating it as "same as above". Omitting any such prefix stage makes the row incomplete and must fail final reconciliation.

For each accepted finding or repair unit and each stable element ID, maintain an evidence inventory for the root cause, boundary, and in-scope path. Every inventory entry must name the source file path, symbol / function / helper, and the relevant caller → callee relationship when one exists; if no caller relationship exists, state that and provide the direct production-entry evidence. A semantic summary without these concrete source references is not evidence.
3. In the output contract's "Input, State, and Path Check" table, restrict the cross-product to finite combinations whose applicability is confirmed in both the source of truth and the code, and make one row for each atomic element × concrete input/state × entry path. If independently changeable elements share a path, use separate rows or state each element's falsification in the same row. Do not invent combinations without applicability evidence, unsupported states or paths, a mechanical cross-product, or imaginary paths. For every row, name the actual function, helper, consumer, and terminal, classify each location as edit, migrate-remove, or verify-only, and provide an observable expected result. Do not abbreviate coverage with "all consumers," "same as above," or "add a related test"

Finite variants selected by a registry or configuration (locale, template, asset, provider mode, and so on) must be recorded individually with each variant's concrete source asset path, selection input / state, shared and variant-specific stages, terminal, expected result, and falsification. Do not merge different asset or input variants merely because they use a shared implementation; only when the path and observation are identical may one row explicitly include all information for each variant. Do not invent a variant absent from the source of truth or code. Mark a currently correct variant or path through shared code as verify-only, rather than an edit target based on symmetry alone, and make edit versus verify-only unambiguous for every variant.
4. Make each falsification concrete: state what is changed, omitted, reordered, or separated into another state, and which observable result or terminal fails when that element's invariant is violated. A falsification does not necessarily mean rejection. When the source of truth and code accept a state, observe its expected preservation / propagation / transformation. For a collection without a uniqueness constraint, a duplicate must not be silently deduplicated: show that duplicate membership remains at the sorted terminal; for an omission, show that the omitted member does not reappear at the terminal; for a tie, observe the precedence / stability actually implemented. Decide accepted versus rejected from evidence, and do not omit falsification for an accepted state merely because no constraint exists. For a collection, list, or map, record each applicable state defined by the source of truth and code—such as member swaps, duplicates, omissions, membership / cardinality changes, or tie / precedence changes—and its failing observation separately. Runtime immutability or `Object.freeze` does not exclude a mutation of a finite source-of-truth or source-fixture variant, an isolated copy, or equivalent input at the same consumer boundary; only exclude a state the consumer rejects or for which the source/code provides no applicability evidence. Even when the current source or input is positive, treat a negative state reachable through an existing entry path—such as changing a source-of-truth entry to an unknown value—as an applicable falsification. Do not force every state on every collection; use only finite, applicable states. Do not omit falsification for a verify-only path merely because it is not an edit target. A generic test name or "add tests" without the affected element and failing observation is not evidence

When literal-data preservation or boundary safety is an invariant, for each applicable variant inject a minimal adversarial sentinel meaningful to the real transformation syntax (replacement metacharacter, escape character, delimiter, or similar) and observe exact-value preservation at every intermediate boundary and the terminal. Identify the transform where each falsification changes the value; do not create a mechanical cross-product of all characters, and use only sentinels relevant to an actual transform. Do not later withdraw an applicable sentinel or boundary falsification as unreachable without source-and-code evidence.

For every applicable atomic field, member, or variant in the finite inventory, whether it is edit or verify-only, describe an individual single-element sentinel mutation with every other input, state, and element held constant, run it through the canonical top-level production entry, and record the concrete terminal or artifact observation for that element. A boundary-only test, a mutation changing multiple elements at once, or merely listing the element is not a substitute.

Maintain a mutation ledger keyed by the stable element IDs. For each applicable ID, show a concrete baseline input or state separately from a mutation that differs from that baseline in exactly that element, and record the resulting mutated terminal or artifact observation. A baseline-only or preservation-only statement is not a falsification, including for a verify-only path. If the source declares an element immutable, use an isolated copy or equivalent input at the same consumer boundary; if a mutation is unsupported, exclude it only with source-and-code evidence and never substitute baseline confirmation.

Where the source or code marks a file, asset, or configuration reference as required, include each applicable unavailable or omitted state as an individual falsification and trace its failure propagation from the canonical entry through the actual consumer to the concrete failure terminal. When a real transformation is driven by a placeholder, delimiter, or other transform token, add a separate single-token omission or alteration in addition to data sentinels and observe the unexpanded, rejected, or changed terminal required by the source and code. For every value-affecting effectful intermediate stage, especially persistence, writing, or dispatch, include an applicable bypass or omission mutation or a boundary spy and record the resulting terminal or artifact absence or change. Include only negative states and stages grounded in the source and code; do not create a cross-product of all stages or states.
5. Before the final output, reconcile only the applicable finite set of atomic elements, inputs/states, and entries re-derived from the source of truth with individual table rows and individual falsifications. Both defect paths requiring code changes and currently correct verify-only / preservation sibling paths must have individual falsifications at the same level of detail. Do not later contradict the table by withdrawing an applicable falsification as "unreachable"; if you exclude one, record the source-and-code evidence for inapplicability. Do not fill gaps with combinations or negative states without applicability evidence, unsupported states or paths, a mechanical cross-product, or imaginary paths. If any applicable element or path cannot be traced with evidence, do not finalize the plan; record the additional investigation or the reason task-level replanning is required

In the final reconciliation, compare the finite asset and variant list from the source of truth and configuration with the actual call graph represented by the rows. Do not finalize when an applicable asset path, intermediate function / helper, terminal, or individual falsification is missing.

Reconcile the applicable stable element IDs one-to-one between the inventory, mutation ledger, and final table, including their counts. Record source-and-code evidence for any excluded unsupported ID rather than substituting baseline confirmation. If a shared path is grouped in one row, that row must still contain an independent baseline → single-element mutation → mutated terminal or artifact observation for every ID; otherwise use separate rows.

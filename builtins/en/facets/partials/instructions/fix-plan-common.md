**Tasks:**
1. Enumerate every remediation target and acceptance criterion, mapping each issue ID or source to exactly one fix unit or follow-up verification without omissions
2. Separate independent local issues, structural issues that share a cause, and items that cannot be demonstrated in the current environment. Exclude an item from implementation remediation as environmental only when the current prompt provides such judgment criteria and every condition is met
3. For each structural issue, derive every invariant, valid example, failing example, and boundary value from the authoritative source, then identify the responsibility and source of truth plus every actual definition, producer, normalizer, validator, consumer, retry, fallback, parallel path, persistence and restoration path, and terminal or API output. Distinguish the family's vertical paths from a neighboring contract
4. For every fix unit, assign a family ID and invariant stable ID and state the observable invariant and authoritative owner. For a structural issue or a unit whose recorded recurrence trigger is true, also state the enforcement point: a single change point, a single validation point, or a type or structure that makes violation impossible. For an independent local defect, allow a direct repair that preserves the existing responsibility without adding an enforcement point. Define acceptance criteria by the invariant holding across the confirmed bounded graph, enforcement at the authoritative owner when required, and representative adversarial counterexamples, not merely by correction of the reported reproduction
5. When replanning from `persists` or `reopened`, consume the recorded recurrence classification and determine whether the previous remediation was a path-local patch. When the trigger is true after repeated path-local patches, plan a design correction that changes the enforcement point rather than another local patch
6. Define dependency order and completion criteria without separating boundary or source-of-truth changes, consumer migration, and removal of duplicate or obsolete paths. Do not include follow-up that cannot be demonstrated due to environmental factors in the implementation order
7. Preflight each fix unit's methods and evidence and replace conflicting candidate methods while preserving acceptance criteria. Define tests or reproducible evidence capable of disproving every invariant and the final quality gates. Separate evidence from current completion criteria only when provided applicable criteria classify it as environmental, and define deterministic alternative evidence plus follow-up verification
8. Before finalizing an implementation method, confirm the cause that method assumes. Record confirmed facts, possible causes, evidence for the selected cause, and other causes that were checked and ruled out. Except where the code path makes the cause clear, separate runtime, concurrency, resource-contention, and timing causes by repeating the same conditions, changing one condition at a time, tracing the code that actually failed, or checking logs and measurements that show a shared resource. Neither "fails in parallel but passes alone" nor success after a change that avoids the failure establishes the cause by itself. If the cause cannot be confirmed, do not put a change based on it in the execution order; keep the finding unresolved, do not finalize the fix plan, and record the required investigation or decision in replanning requirements
9. Select a method that changes concurrency, timeouts, retries, test selection or skipping, or a public contract only when its relationship to the cause is confirmed and the finding's authorization and remediation boundary permit that change. Do not plan a change that merely avoids the problem as the root fix
10. If no compliant method exists under the same requirements and design assumptions, do not finalize the plan; state why task-level replanning is required

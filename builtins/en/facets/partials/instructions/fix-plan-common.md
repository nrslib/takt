**Tasks:**
1. Enumerate every remediation target and acceptance criterion, mapping each issue ID or source to exactly one fix unit or follow-up verification without omissions
2. Separate independent local issues, structural issues that share a cause, and items that cannot be demonstrated in the current environment. Exclude an item from implementation remediation as environmental only when the current prompt provides such judgment criteria and every condition is met
3. For each structural issue, derive every invariant, valid example, failing example, and boundary value from the requirement, specification, schema, or public contract that defines it, then identify the responsibility and source of truth plus every actual definition, producer, normalizer, validator, consumer, retry, fallback, parallel path, persistence and restoration path, and terminal or API output. Distinguish the family's vertical paths from a neighboring contract
4. For every fix unit, assign a family ID and invariant name, which must not change once chosen, and state the observable invariant and its responsible source (the single responsibility and source that defines the invariant and guarantees it holds). Do not use a physical code location or file path as identity, and do not treat a file move or split alone as a different invariant. State an enforcement point for a fix unit independently classified as structural. Separately, also state an enforcement point—a single change point, a single validation point, or a type or structure that makes violation impossible—when recurrence on a different path is `confirmed` or `cannot determine`. For an independent local defect whose recurrence on a different path is `not confirmed`, allow a direct repair that preserves the existing responsibility without adding an enforcement point. Define acceptance criteria by the invariant holding across the confirmed bounded graph, enforcement at the responsible source when required, and representative adversarial counterexamples, not merely by correction of the reported reproduction
5. When replanning from `persists` or `reopened`, use the recorded recurrence classification and determine whether the previous remediation was a path-local patch. When the same invariant has remained broken on different paths at least twice and recurrence on a different path is recorded as `confirmed`, plan a design correction that changes the enforcement point rather than another local patch
6. Define dependency order and completion criteria without separating boundary or source-of-truth changes, consumer migration, and removal of duplicate or obsolete paths. Do not include follow-up that cannot be demonstrated due to environmental factors in the implementation order
7. Preflight each fix unit's methods and evidence and replace conflicting candidate methods while preserving acceptance criteria. Define tests or reproducible evidence capable of disproving every invariant and the final quality gates. Separate evidence from current completion criteria only when provided applicable criteria classify it as environmental, and define deterministic alternative evidence plus follow-up verification
8. If no compliant method exists under the same requirements and design assumptions, do not finalize the plan; state why task-level replanning is required

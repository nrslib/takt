**Invariant recurrence:**

- For each invariant, advance the verification number once for each completed verification in which that invariant is `incomplete`. Multiple paths reported for one invariant in the same verification share one number; only a later `incomplete` verification after another fix receives the next number
- Treat two records as the same invariant only when their family ID, invariant name (which must not change once chosen), and responsible source (the single responsibility and source that defines this invariant and guarantees it holds) match. Do not use a physical code location or file path as identity; moving or splitting files does not create a different invariant when that responsibility and source remain the same
- When adjudication merges a new finding into a different path of an existing family, add the finding ID, source, and affected contract path to the existing family row in Actionable Families in review-resolution.md, and record the target family and rationale in Finding Dispositions or Prior Finding Dispositions. Preserve all 13 fields of the existing Invariant Register Carry-forward row unchanged. Adjudication must not update verification numbers, cumulative `incomplete` count, previous path, current path, recurrence judgment, or whether recurrence on a different path is confirmed. The fix plan maps the merged finding and path to the same family's Finding Coverage, New and Current Planning Rows, and Defect-Family Final State while preserving the carry-forward row unchanged. The fix report also preserves that carry-forward row unchanged. Only when a later completed verification finds that invariant `incomplete` may the fix verifier record that path as the current path and increment the existing row's cumulative count at most once for that verification
- Review adjudication must consider only `subworkflows/iteration-N--step-remediation--*/fix-verification.md` directly under the same peer review's Report Directory. Never consider files under `.takt-report-internal`. When multiple candidates exist, select the one with the greatest numeric `N` as the most recent and record every recurrence row and all 13 fields unchanged in the review resolution's Invariant Register Carry-forward. When no remediation directory matches, record No prior remediation. When the greatest `N` does not identify one candidate uniquely, its `fix-verification.md` is unreadable or missing, its recurrence record is missing, or all 13 current fields cannot be identified, record Carry-forward source missing with the reason and do not fill the gap from an older candidate or convert it to initial values. For a rename that changes any of these three fields, carry values forward only when adjudication explicitly records the old-to-new row mapping and reason: retain the old row as predecessor history and add a new row whose other fields are unchanged. Reappearance under a different name without that mapping is a plan inconsistency
- For a final decision, when the current review-resolution.md is present in the input, use its Invariant Register Carry-forward as the source and copy the source statement and every row with all 13 fields unchanged. When review-resolution.md is not present in the input, inspect the current Report Directory recursively and use the latest preceding fix-verification.md in report history, excluding `.takt-report-internal`. When there is no candidate, the latest candidate is not unique, it cannot be read, its recurrence record is absent, or all 13 fields cannot be identified, start with a blank register and record only Carry-forward source missing and the reason in the source statement. Do not infer or initialize invariant rows or fill them from an older candidate
- A fix plan must not search sibling remediations. When an earlier published fix-verification exists in the same remediation, use its latest recurrence record as the carry-forward source and do not use the review resolution's carry-forward table. If that fix-verification is unreadable or its recurrence record is missing, record Carry-forward source missing with the reason and do not switch to the review resolution. Only when no earlier fix-verification exists in the same remediation may the fix plan use the current review resolution. Copy every invariant row and all 13 fields unchanged from the selected source into the plan before adding new rows. Do not make No prior remediation or Carry-forward source missing and its reason into an invariant row; preserve their distinction through the fix report. Use carried rows only for the established-invariant diff scan and preservation of existing contracts; do not add a carried row outside the families made actionable by the current adjudication to Finding Coverage, Execution Order, or code changes
- When one verification reports multiple affected paths, record the complete previous and current path sets and compare them as sets. Ordering and duplicates do not affect comparison. When deciding whether recurrence on a different path has newly been confirmed for the same invariant, count the current verification as a different path only when its set contains at least one path absent from the preceding `incomplete` verification's set; removals or shrinkage alone do not qualify
- Record recurrence on a different path as `confirmed` only when the same invariant is `incomplete` in at least two separate verifications and this added-path condition holds. Increment the cumulative `incomplete` count at most once per invariant per verification
- For the same ledger row, decide whether recurrence on a different path is confirmed in this order. First, when the carried value is `confirmed`, keep it `confirmed` even when other recurrence fields are missing or inconsistent. Otherwise, when the record is complete, use `confirmed` when the same invariant has now broken on different paths at least twice and `not confirmed` when it has not. Once `confirmed` for a row with matching family ID, invariant name, and responsible source, keep it `confirmed` in every later verification, including another failure on the same path; it may return to `not confirmed` only after an explicit plan change whose reason is recorded. Once confirmed, do not resubmit a repair limited to the reported path: create one enforcement point, make violation impossible through the state structure, or return for plan revision. The plan's `Local / Structural` classification describes the cause and change boundary and must be recorded independently from this observed fact
- The fix verifier reads history only from the invariant-register carry-forward in the fix report. The fixer must keep one row for every planned invariant and initialize no verification number, cumulative count `0`, and recurrence on a different path `not confirmed` only when the carry-forward information is complete and the invariant has no carried row in the fix plan. Keeping and copying every field of a carried row unchanged applies only when review adjudication produces the review resolution, the fix plan copies its register, and the fixer copies it into the fix report. The fix verifier is the only stage that updates the recurrence record for the current verification: for each invariant that is `incomplete` now, increment the cumulative count once and update the current and previous verification numbers, paths, recurrence judgment, and whether recurrence on a different path is confirmed under the conditions stated here. Preserve the recorded verification numbers, paths, count, and whether recurrence on a different path is confirmed unchanged only for rows not `incomplete` now; preserve a recorded `confirmed` regardless of the current judgment. If a later record omits a planned invariant, add its family ID, invariant name, and responsible source from the plan, preserve any known `confirmed`, mark the remaining recurrence fields `cannot determine` rather than resetting them, and record the omission separately as a carry-forward deficiency. The verifier must output every planned invariant even when it is not `incomplete` now
- Complete carry-forward information is a prerequisite for treating an invariant as its first verification. It is complete only when a register contains every row from the selected source, or when no earlier fix-verification exists in the same remediation and the review resolution explicitly records No prior remediation. With that prerequisite satisfied, classify a first verification only when either no row matches the family ID, invariant name, and responsible source or the matching row was initialized from the fix plan with no verification number, cumulative count `0`, and recurrence on a different path `not confirmed`. Never treat the same invariant as its first verification when a carried row exists. When Carry-forward source missing or a reason that prevents unique selection is recorded, copy the reason through the fix plan and fix report, do not convert it to initial values, and continue conservatively as an artifact deficiency. For a complete first verification, record the recurrence judgment as `cannot determine (first verification)`, record recurrence on a different path as `not confirmed`, and allow a normal repair. Preserve a known `confirmed`; otherwise record whether recurrence on a different path is confirmed as `cannot determine`. Treat `cannot determine` with the same caution as `confirmed`: do not choose a repair limited to the reported path, and instead create one enforcement point, make violation impossible through the state structure, or return for plan revision. If the same invariant reappears with its family ID, invariant name, or responsible source changed, record the explicit plan change and its reason and retain the old row as predecessor history; without that record, classify a plan inconsistency rather than a first verification
- When an invariant is not `incomplete` in the current verification, preserve its recorded `incomplete` verification numbers, paths, count, and whether recurrence on a different path is confirmed without shifting them; mark only the current judgment as maintained. This preserves the last `incomplete` path when other verifications occur in between
- Mark each missing or inconsistent recurrence field as `cannot determine` without overriding a carried `confirmed`. Only when whether recurrence on a different path is confirmed cannot be reconstructed and no carried `confirmed` is known, record `cannot determine`; do not infer `not confirmed` or `not recurrent`. Treat `cannot determine` with the same caution as `confirmed` and do not choose a repair limited to the reported path. Reconstruct missing artifact fields from the fix-plan register, retain one row per planned invariant, and record the reason as an artifact deficiency; record plan deficiencies by checking the conditions under which the fix plan remains valid

**Fix plan validity:**
- Preserve each finding's problem, evidence, authorization basis, acceptance criteria, and remediation boundary. Treat reviewer-proposed remediation methods as candidates that do not override requirements, specifications, schemas, or public contracts
- When an issue belongs to a contract family recorded in a requirement, specification, schema, or public contract, use definitions, references, and actual call and data flow to identify every existing path with the same invariant across definition, production, normalization, validation, every consumer, retry/fallback/parallel paths, persistence, restoration, and terminal or API output. Bound remediation by that family's completion obligations rather than the latest reported location. Do not split violations of the same invariant into location-by-location repairs or add a horizontal improvement to a neighboring contract
- Reconcile remediation methods, verification methods, and completion criteria with the requirements, current code, and public contracts, applying any relevant judgment criteria or supporting material provided by the current prompt. Make completion externally observable; lock internal representation or natural-language structure only when it is itself a public contract
- Behavioral verification must traverse the target contract path and observe a point that fails when an invariant is broken. Static invariants may instead be verified through appropriate static analysis or code inspection
- Classify whether each item of evidence can be obtained in the current execution environment. Separate evidence from completion criteria only when provided applicable criteria classify it as environmental. Verify the implementation through deterministic alternative tests, static inspection, and execution-path or CI wiring before recording follow-up verification
- Treat a fix plan as invalid or requiring revision only when it omits or inconsistently records a required family, invariant name that must not change once chosen, responsible source (the single responsibility and source that defines the invariant and guarantees it holds), affected path or bounded graph, acceptance condition, applicable enforcement boundary, or enforcement point required for a structural issue or after the same invariant has broken on different paths at least twice; or when its assumptions, remediation boundary, methods, or evidentiary power are insufficient and a plan change can resolve the deficiency. Do not use a physical code location or file path as identity, and do not treat a file move or split alone as a different invariant. A required structural correction that exceeds the recorded remediation boundary belongs to this set. Missing implementation, execution evidence, or carry-forward artifacts do not constitute a plan defect

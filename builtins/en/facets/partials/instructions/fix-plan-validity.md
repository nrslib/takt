**Fix plan validity:**
- Preserve each finding's problem, evidence, authorization basis, acceptance criteria, and remediation boundary. Treat reviewer-proposed remediation methods as candidates that do not override requirements, specifications, schemas, or public contracts
- When an issue concerns an invariant recorded in a requirement, specification, schema, or public contract, use definitions, references, and actual call and data flow to identify every existing path governed by that invariant across definition, production, normalization, validation, every consumer, retry/fallback/parallel paths, persistence, restoration, and terminal or API output. Bound remediation by those completion obligations rather than the latest reported location. Do not split violations of the same invariant into location-by-location repairs or add a horizontal improvement to a neighboring contract
- When the source of truth or implementation defines an enum, locale set, optional presence, state transition, input format, candidate order, result limit, or another finite set, record every applicable member or state as its own row with the evidence source, then map it to its entry, consumer or terminal, expected result, and disproof method. Follow delegated helpers to their actual constraints, including result limits, search order, no-match behavior, and fallback. Do not mechanically combine dimensions whose applicability the evidence does not establish
- Do not treat umbrella phrases such as "every consumer," "every format," "every locale," "boundary cases," or "and so on" as evidence that paths or acceptance criteria were checked unless they name the applicable concrete members and states with observable outcomes
- Separate the path in each concrete row into "Current" and "After the fix." Start "Current" with the actual highest-level command or API function name, show the current caller, helper, consumer, and terminal in execution order, and explicitly relate any faulty delegation or constraint to the current failure. In "After the fix," trace the same entry to the terminal after remediation. Use the smallest source-backed set of concrete rows that maps every configured member and every applicable entry to a path at least once; do not create every member-by-entry combination unless evidence shows different behavior for each pairing. In each row, classify the existing path locations individually as edit, migrate/remove, or verify-only. When only a shared helper changes, mark already-correct entries, assets, and consumers as verify-only and only the helper actually edited as edit. Do not omit an entry, configured member, or intermediate function by writing "shared path," "same as above," or a category such as "command / delivery"
- Before finalizing the output, check every applicable finite set and state dimension for omissions. For each member or state confirmed by the source of truth or current implementation, verify that the plan independently maps the concrete input or state, including the applicable normal, absent, rejected, and boundary states; the complete path from every applicable highest-level real entry through the actual named current delegating caller and constraint-defining helper, through each applicable consumer to its terminal; the observable expected return or public result and the presence or absence of side effects; the edit, migrate/remove, or verify-only disposition of each participating path or location; and a disproof method that fails if the row is violated. For an ordered candidate set with a result limit, separately check an ordinary match within the retained range, the last retained position, the first excluded or any later position, and no match when applicable. When a zero-based implementation index and a one-based user-facing position or another pair of bases coexist, state both and do not confuse the last retained position with the first excluded position. Do not collapse paths for distinct configured members, entries, or states, and do not construct combinations unsupported by evidence. If any applicable item is not source-backed and independently traceable, continue investigation or planning instead of finalizing with umbrella wording
- When language, runtime, standard-library, or dependency behavior supports a cause, boundary, or disproof, verify the actual input and result from the target code, type or API specification, or a minimal read-only execution available now. Do not infer sort order, matching, replacement, fallback, or parsing results from names, numeric values, or general recollection, and record only inputs that were actually checked as concrete examples
- Do not expose a private definition, rename a return value, schema, or field, or add a production enumeration API solely to simplify tests or improve naming. Limit public-boundary changes to those required by a requirement or an existing consumer, and verify behavior through existing entries and observable results
- Reconcile remediation methods, verification methods, and completion criteria with the requirements, current code, and public contracts, applying any relevant judgment criteria or supporting material provided by the current prompt. Make completion externally observable; lock internal representation or natural-language structure only when it is itself a public contract
- Behavioral verification must traverse the target contract path and observe a point that fails when an invariant is broken. Static invariants may instead be verified through appropriate static analysis or code inspection
- Classify whether each item of evidence can be obtained in the current execution environment. Separate evidence from completion criteria only when provided applicable criteria classify it as environmental. Verify the implementation through deterministic alternative tests, static inspection, and execution-path or CI wiring before recording follow-up verification
- Treat a fix plan as invalid or requiring revision only when it omits or inconsistently records a required invariant, its name that must not change once chosen, responsible source (the single responsibility and source that defines the invariant and guarantees it holds), affected path or bounded graph, concrete rows for applicable finite sets and state dimensions, acceptance condition, applicable enforcement boundary, or enforcement point required for a structural issue or after the same invariant has broken on different paths at least twice; or when its assumptions, remediation boundary, methods, or evidentiary power are insufficient and a plan change can resolve the deficiency. Do not use a physical code location or file path as identity, and do not treat a file move or split alone as a different invariant. A required structural correction that exceeds the recorded remediation boundary belongs to this set. Missing implementation, execution evidence, or carry-forward artifacts do not constitute a plan defect

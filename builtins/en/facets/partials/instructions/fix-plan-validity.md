**Fix plan validity:**
- Preserve each finding's problem, evidence, authorization basis, acceptance criteria, and remediation boundary. Treat reviewer-proposed remediation methods as candidates that do not override requirements, specifications, schemas, or public contracts
- When an issue belongs to a contract family recorded in a requirement, specification, schema, or public contract, use definitions, references, and actual call and data flow to identify every existing path with the same invariant across definition, production, normalization, validation, every consumer, retry/fallback/parallel paths, persistence, restoration, and terminal or API output. Bound remediation by that family's completion obligations rather than the latest reported location. Do not split violations of the same invariant into location-by-location repairs or add a horizontal improvement to a neighboring contract
- When the source of truth or implementation defines an enum, locale set, optional presence, state transition, input format, candidate order, result limit, or another finite set, record every applicable member or state as its own row with the evidence source, then map it to its entry, consumer or terminal, expected result, and disproof method. Follow delegated helpers to their actual constraints, including result limits, search order, no-match behavior, and fallback. Do not mechanically combine dimensions whose applicability the evidence does not establish
- Do not treat umbrella phrases such as "every consumer," "every format," "every locale," "boundary cases," or "and so on" as evidence that paths or acceptance criteria were checked unless they name the applicable concrete members and states with observable outcomes
- Show each concrete row as one continuous path from every applicable highest-level real entry through the caller and constraint-defining helper to the consumer and terminal, and classify each existing location from evidence as edit, migrate/remove, or verify-only. A shared suffix may be referenced to avoid duplication, but do not collapse away the mapping from distinct entries or configured members
- Before finalizing the output, perform a coverage audit for every applicable finite set and state dimension. For each member or state confirmed by the source of truth or current implementation, verify that the plan independently maps the concrete input or state, including the applicable valid control, absent, rejected, and boundary states; the complete path from every applicable highest-level real entry through the actual named current delegating caller and constraint-defining helper, through each applicable consumer to its terminal; the observable expected return or public result and the presence or absence of side effects; the edit, migrate/remove, or verify-only disposition of each participating path or location; and a disproof method that fails if the row is violated. For an ordered candidate set with a result limit, separately audit an in-range match, a match at the first excluded or any later position, and no match when applicable. Shared path suffixes may be referenced, but do not collapse mappings for distinct configured members, entries, or states, and do not construct unsupported cross-products. If any applicable item is not source-backed and independently traceable, continue investigation or planning instead of finalizing with umbrella wording
- Reconcile remediation methods, verification methods, and completion criteria with the requirements, current code, and public contracts, applying any relevant judgment criteria or supporting material provided by the current prompt. Make completion externally observable; lock internal representation or natural-language structure only when it is itself a public contract
- Behavioral verification must traverse the target contract path and observe a point that fails when an invariant is broken. Static invariants may instead be verified through appropriate static analysis or code inspection
- Classify whether each item of evidence can be obtained in the current execution environment. Separate evidence from completion criteria only when provided applicable criteria classify it as environmental. Verify the implementation through deterministic alternative tests, static inspection, and execution-path or CI wiring before recording follow-up verification
- Treat a fix plan as invalid or requiring revision only when it omits or inconsistently records a required family, invariant name that must not change once chosen, responsible source (the single responsibility and source that defines the invariant and guarantees it holds), affected path or bounded graph, concrete rows for applicable finite sets and state dimensions, acceptance condition, applicable enforcement boundary, or enforcement point required for a structural issue or after the same invariant has broken on different paths at least twice; or when its assumptions, remediation boundary, methods, or evidentiary power are insufficient and a plan change can resolve the deficiency. Do not use a physical code location or file path as identity, and do not treat a file move or split alone as a different invariant. A required structural correction that exceeds the recorded remediation boundary belongs to this set. Missing implementation, execution evidence, or carry-forward artifacts do not constitute a plan defect

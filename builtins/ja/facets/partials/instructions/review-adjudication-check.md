提出された各指摘について、現在のコードから不変条件、担当箇所、証拠、必要な移行、隣接する別契約との境界を確認してください。一般的な初回探索は行わず、提出元のレビュアーが担当した観点内で、指摘の妥当性と見落としを確認するために必要な経路だけを比較してください。

判断を始める前に、Report Directory で現在参照できる各レビューレポートから、提出元ごとの指摘 ID を重複を除かず一覧化してください。以前のラウンドについては既存の裁定に記録された判断を維持し、過去の同名レポートを参照できると仮定しないでください。現在のレポートにある未判断の ID だけを新たに判断してください。修正履歴と完了検証は根拠として参照できますが、指摘の提出元として数えないでください。

`architect-review.md`、`testing-review.md`、`coding-review.md` など、実際のレビューレポートごとに、記録された指摘だけでなく、問題なし、対象外、根拠なし、未確認として除外した経路も確認してください。要求、現在の変更、記録済みの修正範囲と照合し、同じ破られる条件と受入条件が適用される実在経路なのに除外する根拠が成立しない場合は、担当観点内の見落としとして裁定してください。既存の受入条件が、関係する全利用箇所で必須の情報または状態を保持することを要求し、実在経路がそれを失う場合は、局所的な別仕様を確認できないことだけを理由に除外しないでください。「全利用箇所」の範囲は、同じ名前や型かどうかではなく、受入条件の対象となる入力を実際に受け取り、その結果を変換、保存、転送、または公開するコード上の接続で判断してください。一方、明示された条件を満たす経路に、元の要求、公開仕様、または実在する利用側が保証していない一意性、可逆性、入力制約などを加えて、新しい違反にしないでください。同じ概念の値、似た表現、同じ外側の結果を持つことだけでは、同じ問題に含める根拠になりません。別の専門観点や隣接する別契約へ探索を広げないでください。

変更によって既存の振る舞いが新しい利用箇所や公開結果へ接続された場合は、内側の担当箇所の確認だけで完了とせず、その利用結果からも確認してください。内側の確認は、外側から区別できない条件や原因を特定するために必要な場合だけ追加し、同じ条件の重複確認を要求しないでください。

見落としを確認した場合は、新しい役割名や中間レポート名を作らず、`testing-review.md（未記載）` のように実際の提出元レポート名を出典として記録してください。

各 ID と確認した見落としについて、技術的な確認結果、今回修正するかどうか、同じ問題へまとめる場合の対応先を決め、すべての判断が揃うまで結論を確定しないでください。

修正後レビューで初めて提出された指摘は、修正前から同じ条件を破っていた未確認の経路か、今回の修正によって生じた退行かを、修正前後のコードまたは修正履歴から区別してください。区別できない場合は推測せず、確認できた事実と未確認の理由を記録してください。

修正履歴が、その修正で経路または振る舞いを追加したと記録し、現在のコードでも追加後の状態を確認でき、矛盾する証拠がない場合は、その履歴を修正前後の区別に使ってください。Git 履歴を利用できないことだけを理由に、記録された修正内容を未確認へ戻さないでください。

指摘した現象が実在しても、それだけで修正対象にしないでください。エラーの型や文言、受理する入力形状など、元の要求、公開仕様、または実在する利用側が保証していない条件を、裁定で新しい契約として追加しないでください。

修正が必要かどうかと、同じ原因の問題をまとめるかどうかは、元の要求、受入条件、現在の変更、確認した証拠から判断してください。

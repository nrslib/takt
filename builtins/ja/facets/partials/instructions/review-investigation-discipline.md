元要件、計画、累積差分から、今回変更された観測可能な契約、境界、責務所有者を先に特定してください。

共通手順で全文確認した判断基準・判断材料は、今回の契約・境界・実在する影響経路へ適用されるものだけを調査へ使ってください。責務所有者が不明な場合、新しい信頼境界・共有状態・外部契約がある場合、または反証によって前提が崩れた場合は、コード上の探索を追加してください。判断基準・判断材料の提供がない場合も、元要件、現在のコード、観測可能な契約から探索を完遂してください。

判断基準・判断材料を参照しただけで確認済みとは扱わないでください。今回の契約に適用される基準を特定し、各基準の対象となる変更定義と利用箇所を列挙して、実コードへ一つずつ照合してください。適用・非適用・未確認のいずれかを根拠とともに決め、適用した基準については対象箇所を全件確認するまでレビューを完了しないでください。根拠が不足している場合は確認済みとせず、必要なファイル・参照・実行経路を追加で調査してください。

Source Path の内容が長い場合は、変更された定義名・契約語を使って関連する基準を検索し、その基準の前後を読み込んでから対象へ適用してください。基準を参照したという宣言や一般論の列挙だけでは照合済みと扱わず、レビュー結果には各適用基準を対象箇所へ適用した結果と根拠を反映してください。

レビュー対象の全定義（型、イベントやメッセージ、関数、設定、共有値など）を先に列挙してください。その一覧の各項目について、適用可能な判定表・箇条書きの基準を個別に照合し、別の問題を見つけたことを理由に未確認の定義や基準を残さないでください。

判定基準に具体例・禁止例・許可例がある場合は、対象の実際の名前・値・構造をその例と直接比較してください。一般的に妥当そうだという印象や、別の問題を確認したことだけを根拠に、例との照合を省略したり問題なしと判定したりしないでください。

判定基準の結論と具体例の対応を維持してください。対象が問題条件または禁止例に一致する場合は問題なしへ反転させず、許容条件または許可例に一致する場合だけ問題なしとしてください。

変更差分は読み取りの起点であり、上限ではありません。適用する基準の判断に必要なコードと証拠を確認してください。探索範囲と finding 権限は、有効な role procedure と review authority policy に従ってください。

外部設定や API から渡される識別子、または文書に形式が定められた識別子を変更する場合は、仕様に書かれた具体例から実際の値を組み立ててください。その値が、作成する箇所から変換・検索、利用箇所、最終結果まで同じ形式で渡るか確認してください。fixture・mock・test input が値の一部を別々のフィールドで持つ場合も、仕様どおりに組み立てて実装と照合してください。fixture と実装が同じ誤った形式を使っているだけの成功テストは、正しい動作の証拠にしないでください。実装とテストが同じ誤りを共有する場合は、別の問題に分けず、同じ finding で説明してください。

- 置換・移動では、変更前後の観測可能な挙動を比較する
- 値、状態、型、schema、resolver、normalizer、adapter、共有 helper の変更では、その定義、参照、実際に到達する入口と消費先を追う
- 失敗、中断、再試行、並行、補助入口は、その状態軸が変更契約または到達可能な影響経路に実在する場合だけ確認する

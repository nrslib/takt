**完了義務監査（検証へ渡す前に必須）:**

1. `fix-plan.md` の各修正単位を、適用される不変条件と対象経路ごとの原子的な完了義務に分解してください。振る舞い修正、利用側移行、旧経路削除、既存契約保存は別の義務として扱い、各義務に一意の義務IDを付けてください。`fix-report.md` に前回の修正または retry の義務がある場合、同じ不変条件・経路・種別の義務はIDと意味を維持し、新たに発見した義務だけIDを追加してください。既存IDの振り直しや別の義務への転用は禁止です。正本が mechanism / source / path を forbidden / obsolete とする old-path removal では、callsite だけでなく、production definition、owned state、constructor / setup input、mutator / API、fallback、全 consumer、tests / fixtures / docs / report evidence を、適用可能な有限 inventory として個別に棚卸ししてください。禁止 mechanism を到達不能にするだけでは不十分です。正本が removal を要求するなら、対応する definition、state、API も削除し、tests が obsolete API / state に依存しないことを個別の義務と証拠にしてください。何を残せるかは正本とコードの根拠で決めてください。loop / reduce / recursive traversal / aggregation の不変条件は、正本とコードで適用可能な独立 control-flow dimension へさらに分解してください。sibling の breadth / position（first / middle / last、後続 branch が結果を更新する場合）、適用可能な node kind / wrapper を通る recursive descent、base / empty、branch 間の accumulator / merge / max、order / preservation などを個別の義務とします。機械的な全組合せは作らず、実装構造と契約に根拠がある有限な dimension だけを扱ってください
2. 編集前に各義務の受入条件と、違反時に失敗する反証方法・観測点を確定してください。編集後はその同じ方法で現在のコード、差分、対象テストまたは再現結果を確認し、広い品質ゲートの成功や自己申告だけで完了にしないでください。preservation の scope は正本が明示する exact symbols / interfaces / behaviors に限定してください。public / exported に見えるという理由だけで保全義務を拡張しないでください。forbidden mechanism と衝突する未指定の legacy API / state を compatibility として残さないでください。durable な回帰証拠は、契約が観測する behavior を検証し、obsolete implementation identity / API をテスト操作の前提にしないでください。正本が複数実装を許す場合は、behaviorally valid な代替を拒否しないことも確認してください。mutation / falsification は各義務を壊す変更を kill できるようにしますが、特定の実装形状を固定する根拠にはしません。1つの falsification / mutant（例えば wrapper counting）で、後続 sibling の skip、accumulator の reset、descendant の skip など別の dimension の完了を兼ねないでください。各独立 dimension には単一変更の counterexample / mutant と owned test failure evidence を要求し、必要なら別の obligation row にしてください。durable な回帰証拠の各 assertion の specificity（error type / category / message、object identity、helper / API name、call count / order など）を、正本の exact element へ対応付けてください。正本が reject / throw だけを定めるなら、例外が発生したことだけを assert し、exact type / category / message は明示された契約の場合に限って固定してください。incidental な wording / identity / structure を固定してはいけません。正本または plan が equivalent implementation / value や incidental detail が非契約であることを明示する場合は、完了前に非契約の message / identity / structure だけを変えた一時的な behaviorally equivalent substitution を少なくとも1つ実行し、owned regression tests が通ることを確認してから substitution を revert してください。実行結果を post-edit evidence に記録し、実行していない自己申告は証拠としません。mutation / falsification による invalid obligation の kill と valid alternative の受理を対で確認し、どちらか未確認なら test-evidence obligation は未完了とします。ただし全テストに無差別な alternative を作らず、正本 / plan が許容を明示する場合、または assertion の specificity が契約より狭い場合に限り、有限で適用可能な substitution を要求します
3. 修正報告の「完了義務」表へ全義務を1行ずつ記録してください。旧経路削除を一行にまとめず、適用可能な production definition、owned state、constructor / setup input、mutator / API、fallback、consumer、callsite、tests / fixtures / docs / report の依存を原子的な義務に分け、それぞれの修正後 evidence を記録してください。max / min / aggregation では、最初の branch とは異なる後続 sibling が terminal result を決める fixture を含め、全 applicable sibling を走査して accumulator が保持・更新されることを観測してください。正本とコードが single-entry を保証する場合だけ、その根拠を記録して除外できます。修正前/差し戻し時の状態、実装根拠、修正後の証拠、状態を埋め、証拠を取得できない義務は完了ではなく未完了または blocker と記録してください
4. 検証へ渡す前に、該当する全行が修正後の証拠付きで「完了」になっているか照合してください。1つでも未完了なら「修正完了」と報告せず、未完了または blocker として記録してください

## 仕様記法

- 合意を成果物へ正確に渡すため、コード・設定・インフラ・テストを作成または変更するゴールでは、解釈が実装結果を実質的に変える重要な振る舞いを Gherkin にする。期待結果は Gherkin、その他の条件と仕様全体の確認条件は acceptanceCriteria に分担する。
- Gherkin の Feature、Rule、Background、Scenario、Scenario Outline、Examples、Given、When、Then、And、But は英語の予約語を使い、続く説明を会話の言語で書く。調査・分析・レビュー・企画・文書作成・運用・意思決定支援のゴールは、目的と受け入れ条件を Markdown で表す。
{{#if formalSpec}}
- 登録先の mode が true のゴールでは、合意した要件を Quint と Alloy の両方で表す。各要件の成立条件、守る性質、要求される結果への到達義務を両記法へ保ち、それぞれの正式な構文で記述する。
{{formalSpecVerifierConstraints}}
- 仕様の整合と到達可能性を確かめられるよう、状態、初期値、遷移、守る性質を同じモデル内で対応させる。各遷移が性質を保ち、要求された結果へ到達する経路を表す。
- Quint の定義は action Name = ...、temporal Name = ... のように適切なモードで書く。初期化は各状態変数へのプライム付き代入で表す。Alloy の可変ライフサイクルは、各遷移の predicate とトレース制約をそろえて表す。
- 状態機械、違反トレース、関係インスタンスの理解に役立つ場合は、小さな ASCII 図を添える。
{{/if}}
{{#if formalSpecCommentsEnabled}}
- 各形式仕様を単独で理解できるよう、各宣言、遷移、不変条件、時相プロパティ、所有関係、カーディナリティの直前に、その条件と要求する振る舞いを説明する自然言語コメントを付ける。一つの形式構造が扱う各要件を、隣接するコメントで説明する。
- 状態やドメイン値は、各値の名前と意味をコメントに列挙する。各記法の本文とコメントから、開発者が要件の条件と結果を読み取れるようにする。
- 完成前に、各要件の形式表現と隣接する意味コメントを照合し、状態遷移との対応を確かめる。
{{/if}}

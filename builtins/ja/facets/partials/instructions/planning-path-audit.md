**影響経路監査（計画確定前に必須）:**

1. 計画を作る前に、正本から観測結果へ独立に影響する「原子的な契約要素」を列挙してください。named field/member、variant、default と explicit の優先関係、複数候補の authority / precedence / override（どの入力・正本が勝つか）、mode、order など、別々に変更・欠落・並替えできる要素を含めます。collection / list / map では member identity、membership / cardinality、order、duplicate、omission、正本またはコードで定義された tie / precedence も要素として分けます。runtime の immutability や `Object.freeze` は実行時の in-place mutation を防ぐだけであり、正本・source fixture の有限な variant、isolated copy、または同じ consumer boundary へ等価な入力を与える mutation testing を不適用にする根拠ではありません。親 object、section、path 名を挙げただけでは、その配下の独立要素を確認済みとみなしません。列挙した各 atomic element に stable ID を付け、その ID を mutation ledger と最終表で再利用してください。親のラベルや path 名を ID の代わりにしてはいけません
2. 各原子的要素を、実在する consumer の read、transform、terminal、または値を変えずに守る preservation へ対応付けてください。各 consumer 境界で受理される state、拒否される state、拒否時の failure behavior も正本とコードから記録し、positive state だけで確認済みとしないでください。accepted finding の applicable な有限 scope inventory には、コード変更が必要な defect path だけでなく、現在正しいため verify-only / preservation とする sibling path も同じ詳細度で含め、最初に見つけた変更対象だけへ縮めないでください。top-level entry が独立した sibling を順に評価する場合は、direct helper だけへ短絡せず、その entry から実際に通る shared / prior stage と各対象 consumer / terminal を記録してください。無関係な架空の stage は追加しないでください。現在の実装に存在する stage のうち、実在する top-level production entry から、task / accepted finding が定める有限 scope 内の対象 consumer / terminal（verify-only / preservation を含む）まで実際に通る定義、生成、変換・検証、保存・復元、利用側、retry・fallback・parallel、外部結果だけを、入口から terminal までコードで追跡してください。各 applicable な契約要素 / path について、少なくとも1行は実在する top-level production entry から、実際の shared / prior stage、対象 consumer、terminal までを end-to-end に追跡する canonical row としてください。isolated copy や direct consumer-boundary mutation は追加の falsification であり、canonical な全経路の代用にはなりません。direct helper 自体が正本とコード上の production entry である場合だけ、その根拠を明記して canonical row として扱えます

canonical な入口から terminal までの行は endpoint の列挙ではありません。値を実際に read / load / select / resolve / parse / transform / serialize / escape / interpolate / template / dispatch / persist する全ての実在する中間 stage を、各 stage の source path、function / helper 名、実行順とともに記録してください。値に影響する中間 stage を1つでも省略した path は未完了とし、無関係な stage は追加しないでください

その行では、実在する全ての file / module と function / helper を caller → callee の実行順で明記してください。top-level entry が独立した sibling branch へ到達する場合は、1つの endpoint の要約へまとめず、その entry から各 branch の consumer と terminal までを個別に追跡してください

全ての canonical row と evidence-path entry は、実在する top-level production entry から開始し、terminal より前に実行される shared / prior、値に影響する stage、effectful stage を実行順で含めてください。defining source や direct consumer から途中開始してはいけません。各 sibling terminal について entry からの完全な prefix を再記載し、「同上」などで省略しないでください。この prefix stage のいずれかを省略した row は未完了とし、最終 reconciliation を失敗にしてください

各 accepted finding / 修正単位と各 stable element ID について、根因、境界、対象経路の evidence inventory を維持してください。各 inventory entry には source file path、symbol / function / helper、存在する場合は関係する caller → callee を明記し、caller 関係がない場合はその旨と direct production entry の根拠を示してください。これらの具体的な source 参照を伴わない意味要約は evidence とみなしません
3. 出力契約の「入力・状態・経路の確認表」は、正本とコードの双方で適用を確認できる有限な組合せに限り、原子的要素 × 具体的な入力/state × entry path ごとに1行作ってください。同じ path でも独立に変更できる要素は別行にするか、同じ行で要素ごとの反証を明記します。適用根拠のない組合せ、unsupported な state/path、機械的な直積、架空の経路は作らないでください。各行に実在する関数・helper・consumer・terminal、edit / migrate-remove / verify-only の扱い、観測可能な期待結果を記載し、「全consumer」「同上」「関連テスト」などで省略しないでください

registry / config が選ぶ finite variant（locale、template、asset、provider mode など）は、各 variant の具体的な source asset path、選択 input / state、shared / variant-specific stage、terminal、期待結果、falsification を個別に記録してください。共通実装だけを理由に異なる asset / input variant を1行へまとめてはいけません。同一 path と observation の場合だけ、1行内に各 variant の全情報を明記できます。正本またはコードにない variant は作らないでください。共通実装で現在正しい variant / path は verify-only と明記し、対称性だけで edit 対象にしないでください。各 variant の edit / verify-only を曖昧にしないでください
4. 各原子的な要素の falsification は、何を変更・欠落・並替え・別 state 化するかと、違反時にどの観測結果または terminal が失敗するかを具体化してください。falsification は必ず拒否を意味するとは限りません。正本とコードがその state を受理する場合は、期待される preservation / propagation / transformation を観測してください。uniqueness 制約のない collection の duplicate では silent dedupe をせず duplicate membership が sorted terminal に保持されること、omission では欠落した member が terminal に再出現しないこと、tie では実装済みの precedence / stability を観測することを個別に示します。accepted / rejected は根拠から決め、制約がないことだけを理由に accepted-state の falsification を省略しないでください。collection / list / map では、正本とコードで適用可能と確認できる member の入替、duplicate、omission、membership / cardinality、tie / precedence などの各 state と失敗観測を個別に記録します。runtime の immutability や `Object.freeze` を理由に、正本・source fixture の有限な variant、isolated copy、または同じ consumer boundary への等価入力による mutation を除外しないでください。ただし consumer が受理しない状態や根拠のない状態は作らないでください。全 collection に全状態を強制せず、有限で適用可能な state だけを扱います。現在 positive な正本や入力でも、既存の entry path から到達できる source-of-truth entry の unknown 化などの negative state は適用可能な反証として扱います。verify-only path も変更対象でないことを理由に falsification を省略しないでください。generic なテスト名や「テストを追加する」だけでは反証になりません

literal-data preservation または boundary safety が不変条件なら、各 applicable variant で、実在する変換構文に意味を持つ最小の adversarial sentinel（replacement metacharacter、escape character、delimiter など）を入力し、各中間 boundary と terminal で exact value の保持を観測してください。どの transform で各反証が値を変質させるかを特定し、全 character の機械的な直積は作らず、実在する transform に関係する sentinel だけを扱います。適用可能な sentinel や boundary の反証を、正本とコードの根拠なしに後から「到達不能」として取り消してはいけません

有限 inventory に含まれる適用可能な各 atomic field / member / variant について、edit か verify-only かを問わず、他の入力・state・要素を固定した単独の sentinel mutation（その要素だけを変更・欠落・並替え等する反証）を個別に記述し、実在する canonical top-level production entry を通し、その要素について具体的な terminal / artifact の観測結果を記録してください。境界だけで行うテスト、複数要素を同時に変更する mutation、単に要素を列挙するだけでは代用できません

stable element ID をキーにした mutation ledger を維持してください。適用可能な各 ID について、具体的な baseline の入力または state を mutation とは別に示し、baseline からその要素だけが変わる mutation と、その結果の mutated terminal / artifact の観測を記録してください。baseline だけの確認や preservation だけの記述は、verify-only path を含め、falsification ではありません。正本が要素を変更不能と定める場合は isolated copy または同じ consumer boundary への等価な入力を使い、mutation が unsupported なら正本とコードの根拠付きでのみ除外し、baseline の確認で代用してはいけません

正本またはコードが file、asset、configuration reference を必須と定めている場合、適用可能な unavailable または omitted state を個別の反証として含め、canonical entry から実際の consumer を通って具体的な failure terminal へ失敗が伝播することを追跡してください。placeholder、delimiter、その他の transform token が実在する変換を駆動する場合は、data sentinel に加えて token 自体を単独で欠落・変更する反証を記録し、正本とコードが定める unexpanded、rejected、または changed な terminal を観測してください。値に影響する effectful な中間 stage、特に persistence、write、dispatch については、適用可能な bypass / omission mutation または boundary spy を用い、その結果の terminal / artifact の欠落・変化を記録してください。正本とコードに根拠のある negative state と stage だけを含め、全 stage や state の直積は作らないでください
5. 最終出力前に、正本から再導出した applicable な有限集合の原子的要素、入力/state、entry だけを表の個別行へ対応させ、コード変更が必要な defect path と verify-only / preservation の sibling path の双方に同じ詳細度の個別 falsification があることを照合してください。表に挙げた適用可能な反証を、後段で「到達不能」として矛盾して取り消してはいけません。除外する場合は正本とコードによる適用不可の根拠を記録してください。適用根拠のない組合せ、unsupported な state/path、機械的な直積、架空の経路や negative を補ってはいけません。根拠付きで追跡できない経路や要素が残る場合は計画を確定せず、追加調査またはタスク全体の再計画が必要な理由を記録してください

最終 reconciliation では、正本 / config の finite な asset / variant 一覧と、表に表現した実際の call graph を突合してください。applicable な asset path、中間 function / helper、terminal、個別の falsification のいずれかが欠けている場合は計画を確定しないでください

適用可能な stable element ID が inventory、mutation ledger、最終表の間で一対一に対応し、件数も一致することを照合してください。除外する unsupported ID は、baseline の確認で代用せず、正本とコードの根拠を記録してください。同じ path を1行にまとめる場合も、各 ID について独立した baseline → 単独要素 mutation → mutated terminal / artifact の観測を含め、含められない場合は別行にしてください

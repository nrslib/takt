# レビュー指摘の裁定

提出された指摘が技術的に正しいかと、今回の変更で修正する必要があるかを分けて判断し、必要な修正だけを確定する。

## 判定の順序

外部確認待ちは最後に判定する。

1. 外部の失敗結果が届いている場合は、同じ入力・期待結果を現在のコードと照合する。現在のコードが受入条件の違反を起こすと確認できれば、既存の問題IDで修正対象に戻す。要求がアプリに届いていない外部の障害などは、コード起因としない。
2. 次に、その受入条件に必要な環境内の検証が、現在のコード状態で未実施・失敗・古い版なら、その検証または原因の調査を残作業とする。未実施だけでコードの欠陥と断定しない。
3. どちらにも当たらず、必要な環境内の検証が現在のコードで成功し、根拠のある未充足の条件が外部でしか観測できない場合だけ、外部確認待ちとする。

## 判断基準

防御対象外と明記された脅威への指摘と、指摘された失敗のうち副次的な環境で起きる部分は、表の該当する行を先に確認する。当てはまらない場合は、元の要求や受入条件への違反、退行など、通常の行で判断する。

| 状況 | 扱い |
|------|------|
| 修正した問題について、現在のコードに対する修正と、その受入条件を閉じるために必要な環境内の検証が完了し、残る未充足の受入条件が、要求またはプロジェクトの既存の契約に根拠を持ち、この実行環境では観測できない確認（別の実行環境、外部サービス、実機、人による確認など）だけである | 外部確認待ち（修正対象にしない） |
| 元の要求または受入条件へ直接違反している | 修正する |
| 今回の差分または修正が新しい退行を導入した | 修正する |
| 変更した契約を成立させるため、現在の利用箇所の移行が必要である | 修正する |
| 既に修正すると判断した問題と同じ原因・条件・受入条件を持つ未確認の利用箇所である | 同じ問題へ統合して修正する |
| 実在する別の問題だが、今回の要求や修正から必要性を導けない | 今回の範囲外 |
| 現在の挙動を欠陥とする根拠がなく、より強い方式や保証だけを要求している | 必要以上の拡張 |
| 変更前の文書・知識が、攻撃主体と手段を示して防御対象外と明記した脅威への防御だけを求めている。要求はその契約の変更を求めていない。攻撃主体、起動・同意の条件、対象になる入力の範囲、入力を解釈・実行する処理、実効権限と credential、到達できる保護資産は変わらず、既存の防御も迂回・省略されていない | 必要以上の拡張 |
| 指摘された失敗のうち、文書・知識で副次的と位置づけられた環境（OS、ブラウザ、CPU アーキテクチャなど）に起因する部分がある。要求も変更前の利用者向けサポート契約もその環境での対応や確認を求めておらず、今回の変更はその環境で以前動いていた経路を壊していない | 今回の範囲外 |
| 現在のコードまたは証拠が指摘内容と矛盾する | 根拠なし、または確認後は問題なし |
| 必要な外部環境がなく、実装上の欠陥を確認も反証もできない | 環境上確認不能 |

## 原則

- 指摘が正しかったかの判断（ID と履歴）と、現在のコードの変更が必要かの判断を分ける。以前「修正する」と判断した問題でも、現在のコードに対する修正と必要な環境内の検証が完了していれば、指摘の判断を変えずに修正対象から外し、残る確認だけを「外部確認待ち」として引き継ぐ。これは判断済みの指摘の再裁定ではない
- 外部確認待ちにできるのは、次の条件をすべて満たす場合だけとする
  - 残る条件が、要求またはプロジェクトの既存の契約に根拠を持つ。検証の手段や、CI に該当のジョブがあることだけを根拠に受入条件へ格上げしない。根拠のない条件は「今回の範囲外」とし、外部確認待ちにも修正対象にもしない
  - その問題の受入条件を閉じるために要求で求められている、または直接必要な、この実行環境で実行・参照できる検証が、現在のコード（その時点の commit またはコード状態）に対して実施済みで成功している。未実施・失敗・古い版に対する結果がある場合は、外部確認待ちにせず実施または修正の対象とする。ただし、未実施の検証があることだけでコードの欠陥と断定しない。受入条件に関係しない検証（任意の CI ジョブなど）が残っていても外部確認待ちを妨げない
  - 外部でしか観測できない理由を具体的に示せる
- 外部確認の結果が届き、受入条件の違反が現在のコードに起因すると確認できた場合だけ修正対象に戻す（reopened と同じ扱い）。外部サービスの停止、確認設備や CI の障害など、コードに起因しない失敗は修正対象にしない
- 外部確認待ちだけが残る場合、修正対象はない

- 副次的な環境で指摘された失敗は、環境ごとに分けて判定する。同じ原因で主要な環境も失敗する場合、主要な環境の修正は通常どおり修正対象にする。副次的な環境に起因して新しい機能がその環境だけで動かなくても、要求も変更前の利用者向けサポート契約もその環境での対応や確認を求めておらず、今回の変更による退行でもなければ、理由とともに「今回の範囲外」として記録する。処理前のエラーや文書への記載も求めない
- 要求も変更前の利用者向けサポート契約もその環境での対応や確認を求めていなくても、今回の変更が副次的な環境で以前動いていた経路を壊した場合は修正対象にする。公式の仕様に基づいてこの実行環境で実装し、ここで動くテスト（モックや仕様どおりの入力の再現など）で確かめられる範囲を直す。その環境での実装自体がここではできない場合は、その環境で処理前に理由の分かるエラーで止め、利用者向け文書に制約を記載することを受入条件にする。この場合の完全な対応は、理由とともに「今回の範囲外」として記録する
- 副次的な環境での確認は、要求や変更前の利用者向けサポート契約に根拠がなければ受入条件にせず、理由とともに「今回の範囲外」として記録する。前回までの裁定で受入条件にしていた場合も外し、元の条件と外した理由を裁定に残す。修正対象にも外部確認待ちにもせず、根拠がないまま以後のラウンドで受入条件へ戻さない
- 副次的な環境のサポート契約は、要求がサポート契約の変更を明示した場合はその要求に従い、それ以外は変更前の版で判断する。副次的という位置づけ、CI にその環境のジョブがあること、既存コードの一部が対応していることだけをサポート契約の根拠にしない
- 副次的な環境での対応や確認を要求または変更前の利用者向けサポート契約が求める場合や、失敗の原因が環境ではなく設定済みの既定値や依存先の拒否などにある場合は、通常どおり判定する

- 現在のコード、要求、レポート、実行証跡で確認できる事実を根拠にする
- 指摘の重大度、REJECT、修正案、発見時期だけを理由に修正対象へ含めない
- 実在する欠陥と過剰な修正案が同じ指摘に含まれる場合は分けて判断し、必要最小限の修正だけを採用する
- 原因、破られる観測可能な条件、受入条件が同じ指摘は1つの問題へまとめる。担当箇所が同じでも条件が異なる問題は分ける
- 修正する問題について、定義元から利用箇所と外部から観測できる結果まで、同じ原因で影響を受ける実在経路を確認する
- atomicity、transaction、rollback、資源上限、互換経路などを、確認済みの欠陥の解消に不要なら追加要求にしない
- 要求・変更境界と適用される設計基準から成立する欠陥を、数値目標や障害実測がないことだけで対象外にしない。結果が正しいことと、途中の処理が設計上の条件を満たすことを分けて判断する。適用条件や影響経路が不明なら、欠陥と断定せず未確認の根拠を示す
- 判断できない懸念を推測で除外せず、必要な情報とともに未解決の前提として記録する
- 提出された全 finding ID を1回ずつ判断し、最初の修正対象を見つけた時点で残りを省略しない

## 不足している検証の判断

- テスト不足を修正対象にする前に、何を根拠にその検証が必要なのかを確認する。元の要求、今回の振る舞いの変更、確認済みの欠陥と照合し、検出すべき失敗と、既存の検証では検出できない理由を示す。そのうえで必要最小限の検証範囲を決める。現行実装が正しくても、明示された検証や変更した振る舞いの回帰テストは省略しない
- 成果物の更新や回帰テストが要求されていても、レビュアーが提案した自動判定の方法や追加の保証まで必須とは限らない。公開する説明文を正しく更新することと、任意の言い換え・否定・矛盾を自動で検出する仕組みを作ることは、別の要件として判断する
- 検証を補助する仕組みの不備や追加の反例が示された場合も、それによって元の必須条件を確認できなくなるかを判断する。任意の検証強化を新たな受入条件にしない。必要な検証と、必要以上に広い判定方法を区別する

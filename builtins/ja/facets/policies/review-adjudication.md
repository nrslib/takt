# レビュー指摘の裁定

指摘の技術的な成立と、今回の修正を必須とする判断を分ける。要求・既存契約への違反と現実の影響を確認し、必要な修正を採用する。副次的な環境に起因する部分は、対応・確認の義務と、以前動いていた経路の退行を分けて判断する。既存の問題に残る不足は、その問題と進行中の計画を引き継いで解消する。

提出された指摘は、その入力で働く防御と確認できる経路・処理結果で判定する。既存の防御が指摘の入力を拒否すれば元の主張を反証し、禁止された入力が実際の入口から状態を変えれば、その違反を採る。「AがBを利用できる」という条件だけから「A以外によるBの利用は禁止」や「Bの出所を毎回機械的に証明する義務」は導かない。別の経路・拒否条件・出所保証は独立した提案として、守る条件と具体的な違反・影響を確かめて必要性を判断する。独立した根拠のない追加保証は今回不採用・非blockingとし、裁定全体を未解決にしない。明示された義務、重大な影響のある実在の欠陥、元の主張で真に未確定の前提は維持する。

## 採否の基準

| 基準 | 判断 |
|------|------|
| 事実として成り立つか | 実在する防御の効果を含めて、指摘が示す失敗や構造上の違反が現在のコードで実際に成り立つことを確かめる |
| 今回の修正が必要か | 要求・既存契約で必要な保証、現実の入力条件、残した場合の具体的影響と、修正による入力制約・複雑さ・正常利用の退行を比較する。品質・設計の改善、機能追加や仕様変更は今回の要求や変更との関係も確かめる。不具合は今回の作業や計画と無関係でも対象にできる |
| 脅威モデルの内側か | 失敗の成立に必要な入力・状態・権限・並行性・量が、そのシステムに求められる範囲に入ることを必要とする |
| 防御対象外という契約が適用できるか | 変更前の文書・知識が主体と手段を明示して防御対象外とし、要求もその変更を求めず、攻撃主体、起動・同意の条件、入力の範囲と解釈・実行、実効権限・資格情報、保護資産への到達性が変わらず、既存の防御も迂回・省略されていない場合は、その防御だけを求める指摘を必要以上の拡張とする |
| 採用する欠陥と直し方を分ける | 守る条件への違反を確認した欠陥について、提案されたトランザクション、上限、互換経路などが過剰なら、欠陥だけを最小の修正として採り、過剰な直し方は退ける。代案が別の保証を要するなら、その保証の必要性を独立に判断する |

技術的に成立しても、今回の要求・既存契約にない保証や証明方式を直ちに受入条件にしない。確認した違反と影響を残し、今回修正するか、持ち越すか、要求外とするかを理由とともに決める。明示された必須条件や重大な影響を持つ実在の欠陥は、修正の手間だけで免除しない。低い重大度だけで退けず、再現用の PoC を一律に必須としない。採否が未確定なものは、確認済みの反証と区別して未解決とする。重大度、指摘の数や票数、好み、発見時期、別の観点の網羅だけで採否を決めない。採否の理由は、事実、守る条件、脅威モデル、今回の修正の必要性で示す。行番号や経路の説明の誤りだけでは、正しい箇所で成り立つ同じ欠陥を退けない。

修正済みの問題に後から別の保証・入力制限・証明方式が提案された場合は、元の受入条件が未達かを先に確かめる。元の条件が満たされていれば、新しい提案を元の問題の「修正不足」や `reopened` として自動的に追加しない。別の提案として今回の必要性を判断し、守る義務や修正範囲の変更が必要なら再計画へ渡す。

人が採らないと決めた保証について、判断の内容・理由・適用範囲が入力として供給されている場合は、それを現在の裁定に対応付ける。同じ保証の言い換えを新しい修正や受入条件として再導入しない。要求の変更、判断の前提を崩す新しい具体的証拠、または適用範囲外の重大な影響があれば、従前の判断との違いを示して必要な要求判断へ返す。黙って上書きしない。判断が供給されていない場合は、その存在や内容を推測しない。

## 今回の範囲と修正の境界

品質・設計の基準は、今回の要求や変更に関連する改善・リファクタリングに適用する。今回の変更と関係しない既存コードの重複整理などは範囲外とする。構造上の欠陥には、適用される基準への具体的な違反が必要であり、障害の実測や攻撃シナリオを一律に求めない。不具合については、過去の計画にないことも、計画との因果関係がないことも、退ける理由にならない。

今回の変更が追加・変更した経路で、要求・スキーマ・文書に件数や大きさの上限がないデータを扱う場合、取得・同時保持量がデータ全体に比例する必要があるかを判断する。要求する結果を保ったまま取得範囲や同時保持量を抑えられるのに、不要な全件取得や全件の同時保持が残る構造は、数値の上限、SLO、障害の実測がなくても設計上の欠陥として採る。

全入力の走査が必要な処理は、必要な総取得・処理量と、同時保持の必要性を分けて判断する。小さく固定された集合はその上限を、実効的な上限付きバッファは同時保持量を抑える働きを考慮し、全体の同時保持が必要な処理はその必要性を根拠に判断する。全件出力が要求である場合は、出力を削る上限の追加と、出力を保ったまま逐次化して保持量を抑える修正を区別し、後者で解消できる欠陥を採る。

現在そう動くことだけでは、保持すべき既存契約とはならない。意図された仕様変更と契約違反を区別するため、要求による明示的な置き換え後も守るべき既存契約を保持対象とする。修正方法は、要求が指定した方式と必要な安全条件を守る範囲で選択できるものとし、欠陥を解消する最小の修正を採る。

## 既存の問題と計画の引き継ぎ

現在の問題と進行中の計画の完了を引き継ぐため、提出された指摘の統合先は、前回の裁定と進行中の修正計画にある問題との対応を優先して決める。現在の解消状態は、その問題の受入条件に対応する最新の修正・検証の記録を現在のコードに照合して判断する。以前のラウンドの記録は、それらだけでは統合先や引き継ぎが決まらない場合に、必要な箇所だけを補足として参照する。経過の組み立て直しはしない。

前回の裁定や進行中の修正計画にある問題と、原因・破られる観測可能な条件・受入条件が同じ指摘は、場所や入力が異なっても、その問題の ID・受入条件・計画で決まった方式を保ったまま、未完了の部分として扱う。失敗した経路が修正で新しく加わったと分かる場合は、修正による退行として区別し、当初はその経路がなかったことと根拠を記録する。分からない場合は区別を記録せず、同じ問題の残作業として扱う。元の指摘 ID と出典に、今回確認した場所・経路・証拠を追加する。原因・破られる条件・受入条件のいずれかが異なる場合は別の問題として扱う。

共通原因を解消する計画の適用・検証が進行中なら、未配線や検証不足はその計画の残作業として完了を引き継ぐ。接続・検証済みの正本と方式は維持する。進行中の計画がなく、修正済みとした問題が適用範囲内で再発し、同じ条件を破る共通の仕組みまで確認できた場合は、方式の見直しが必要と判断する。再発と共通の仕組みを確認できなければ、見直しの要否を論じず、通常の原因分析の対象とする。見直しの要否は新しい方式の確定とは分け、根拠と維持すべき条件を修正計画へ渡す。要求の方式指定や必須条件と衝突する場合は、その衝突と必要な要求上の判断を示す。

## 副次的な環境と受入条件

文書・知識・要求が示す環境の位置づけと、要求または変更前の利用者向けサポート契約を基準に、環境ごとに判断する。サポート契約の変更が明示されている場合は、その要求を適用する。同じ原因で主要な環境も失敗する場合、その修正は通常どおり対象とする。

対応や確認の義務は、要求と変更前の利用者向け文書が対象の機能に約束した範囲で判断する。一般的な機能要求に環境の除外がないこと、副次的という位置づけ、該当する CI ジョブや実装済みの経路があることだけでは、その環境での対応や確認の約束にはならない。対応の約束と、その環境で確認する義務も別に判断する。追加の対応・確認の義務を確定するため、変更前の利用者向け文書に対象の約束があるかを確かめ、約束がなければ、それを根拠とする追加の対応・確認は今回の範囲外として判断を確定する。

| 基準 | 判断 |
|------|------|
| 副次的な環境に起因する失敗で、要求も変更前のサポート契約も対応・確認を求めず、今回の変更による退行でもない | 退行の修正と区別して今回の範囲外とする。新しい機能がその環境だけで動かない場合も、その環境への対応の追加・処理前のエラー・文書への記載は同じ扱いとする |
| 要求も変更前のサポート契約も対応・確認を求めないが、今回の変更が副次的な環境で以前動いていた経路を壊した | 修正対象とし、下記の範囲を受入条件にする |
| 要求または変更前のサポート契約がその環境での対応・確認を求める、または原因が環境固有ではなく設定済みの既定値・依存先の拒否などにある | 通常の採否の基準で判断する |

対応・確認の義務がない副次的な環境の退行は、公式仕様に基づく実装と、この実行環境で動くテスト（モックや仕様どおりの入力の再現など）で確かめられる範囲の修正を受入条件にする。その環境での実機確認や、その環境の CI ランナーでのテスト実行は受入条件に含めない。

その実装自体がここではできない場合は、影響する環境で副作用を伴う処理より前に、未対応である理由の分かるエラーで止め、利用者向け文書へ制約を記載することを受入条件にする。主処理の起動前でも、状態を変えた後に偶発的な例外で止まる動作は、この条件を満たさない。完全な対応は、理由とともに今回の範囲外とする。実機確認ができないことだけでは、ここでの実装自体ができない理由にはならない。

副次的な環境での確認に要求や変更前のサポート契約の根拠がなければ、今回の範囲外とし、受入条件・修正対象・外部確認待ちから外す。以前の裁定で受入条件にしていた場合も、元の条件と外した理由を残す。以後その条件を戻すには、要求や変更前のサポート契約の根拠を必要とする。

## 外部確認待ちと残作業

採用した指摘の判断と現在の解消状態を分け、受入条件を満たすために残る作業で扱いを決める。外部確認待ちは、修正と必要な環境内検証の完了後に、残る確認条件そのものの根拠と、外部でしか観測できない理由がそろう場合に限る。確認手段、CI ジョブ、実装済みの経路、過去の裁定に条件があることだけでは、その確認を受入条件にする根拠にならない。

| 基準 | 判断 |
|------|------|
| 修正と必要な環境内検証が現在のコード状態で完了し、残る受入条件がない | 解消済みとし、元の採否・問題 ID・履歴は維持する |
| 修正が完了し、受入条件に要求上必要な環境内の検証が現在のコード状態で成功し、残る根拠のある条件を外部でしか観測できない理由が具体的である | 残る条件を外部確認待ちとする。外部確認待ちだけなら修正対象はない |
| 修正が未完了、または必要な環境内検証が未実施・失敗・古い版の結果である | 受入条件の充足に必要な作業を確定するため、必要な修正・検証または原因調査を残作業とする。検証の実施状態とコードの欠陥の有無を区別し、欠陥の判断には失敗や構造上の違反の証拠を要する |
| 外部の失敗結果が、同じ入力・期待結果で現在のコードに起因する受入条件違反を示す | 既存の問題 ID で修正対象に戻す。外部設備・サービスの障害などコードに起因しない失敗は、実装修正と分ける |
| 欠陥の確認・反証に必要な外部環境をリポジトリの実装・設定・テスト準備では用意できず、利用可能な代替証拠でも決まらない | 欠陥の成立・反証を決める証拠が不足している状態を示すため、環境上確認不能として、未確認の条件と必要な証拠を残す |

## 検証や成果物の不足

検証や成果物の不足は、明示された義務、変更した振る舞いの回帰防止、確認済みの欠陥と結び付けて判断する。守る条件、検出すべき失敗、既存の検証や成果物では満たせない理由を根拠とし、その失敗を検出する最小の層と必要な範囲を受入条件にする。実装が正しくても、明示された検証や必要な回帰検証の不足は対象になる。

成果物の更新や回帰検証の義務と、提案された自動判定の方法や追加の保証は別に判断する。検証を補助する仕組みへの反例も、元の必須条件を確認できなくなるかで判断する。より広い判定や別の観測方法を加える場合は、その必要性の根拠を要する。

## 過去の工程逸脱

やり直しても取り消せない過去の工程逸脱だけを理由に修正対象にしない。ただし、逸脱が停止済みで、成果物・外部状態に影響が残らず、現在のコードを指定条件で検証済みである場合に限る。残る影響、必要な検証、機密情報・外部操作・権限の境界違反は通常どおり判断する。

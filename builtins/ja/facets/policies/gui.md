# GUIポリシー

GUIの構造、状態の所有、表示と動作の分離、操作意図の経路、現在状態からの裁定を、変更の影響が追跡できる形で判定する。

## 原則

| 原則 | 基準 |
|------|------|
| 階層 | 画面に属するコンポーネントがRootから辿れ、各部分木の責務が読める |
| 状態の範囲 | 状態を一貫させる必要がある最小の部分木に担当がある |
| Passive View | 表示部品は描画パラメータを扱い、遷移・通信・共有状態変更の裁定を担当しない |
| Mediator | 画面または領域の担当が、現在状態と操作意図から受理・拒否、遷移、副作用を決める |
| 操作経路 | 操作意図が担当へ届く経路を追跡でき、処理済みの意図が重複実行されない |
| 変更容易性 | 汎用表示部品が特定画面の通信手順や遷移へ結合せず、責務ごとの変更範囲が読める |
| 実害と構造 | 実行時の不具合だけでなく、所有者不在、責務混在、変更経路の隠蔽も根拠に含める |

## 階層と状態の所有

| 基準 | 判定 |
|------|------|
| UIがRootから辿れず、表示・状態・操作の担当も追跡できない | REJECT |
| 複数部品が同じ事実を別々に保持し、更新順で表示や操作結果が変わる | REJECT |
| 子が別の部分木の状態を、担当が用意した操作入口を経ずに変更する | REJECT |
| 状態が利用範囲と寿命に合う部分木へ置かれ、担当から表示までの経路が読める | OK |
| Rootが画面の組み立てを担い、必要な状態を部分木へ委譲する | OK |

## 表示と動作

| 基準 | 判定 |
|------|------|
| 表示部品が画面遷移、通信、共有状態変更、業務上の受理判断を個別に行う | REJECT |
| 表示部品が描画に必要な値を受け、操作意図を担当の操作入口へ通知する | OK |
| 画面または領域の担当が現在状態を読み、操作の受理・拒否と遷移を決める | OK |
| 表示と裁定を一つの小さな画面関数に置いているが、両者の責務と経路がコード上で区別できる | 変更理由を確認する |

既存のフレームワークの部品は、表示と裁定の責務境界に沿って配置する。形式の変更ではなく、責務混在と変更経路を確認する。

## 操作意図とイベント

| 基準 | 判定 |
|------|------|
| 操作意図が担当の操作入口を飛び越えて別の状態を直接変更する | REJECT |
| 担当外の中間部品が意図を意味を変えずに上位へ委譲する | OK |
| 担当が操作を受理・拒否した後、祖先が同じ保存・削除などの操作を重複実行する | REJECT |
| callback、操作の委譲、Chain of Responsibilityを同じものとして扱い、担当や停止条件が読めない | REJECT |

## 状態遷移と変更範囲

| 基準 | 判定 |
|------|------|
| 状態ごとに受理できる操作が異なるのに、各表示部品が個別の条件で判断する | REJECT |
| 状態、意図、遷移、遷移後の表示が同じ担当から追跡できる | OK |
| 表示部品の汎用性を保つために、画面固有の通信や遷移を汎用部品へ追加する | REJECT |
| 変更理由が独立する表示、状態、外部副作用が一つの責務に混在し、変更経路を追えない | REJECT |

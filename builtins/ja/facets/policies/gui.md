# GUIポリシー

GUIの階層、状態所有、操作意図の経路、表示と動作の責務を実害に基づいて判定する。

## 原則

| 原則 | 基準 |
|------|------|
| 階層の包含 | UIがRootから辿れる階層にあり、独立widgetも担当する部分木を持つ |
| 状態の所有 | 共有状態と外部副作用を、整合性を裁定できる所有者へ置く |
| 操作意図 | 子から上位の操作入口へ意図を通知し、担当者まで経路を追跡できる |
| 表示と動作 | 表示値の描画と状態・副作用の裁定を、必要な範囲で分離する |
| 実害の根拠 | 所有者不在、境界破壊、操作の重複など観測できる問題だけを拒否する |
| 方式の尊重 | hook、Context、dispatch、query、form、bindingなどの方式名だけで拒否しない |
| 最小の変更 | クラス名、ライブラリ、遷移表、全state外出しなどを要求の根拠なしに強制しない |

## 階層と状態所有

| 基準 | 判定 |
|------|------|
| UIがRootの階層に含まれず、どの状態所有者からも追跡できない | REJECT |
| 子が所有者の公開更新契約を経ずに、親のstate、共有store、または別部分木の正規状態を書き換える | REJECT |
| 小さな画面が必要な状態をRootまたは画面の所有者に集中し、整合性が明確 | OK |
| hover、focus、入力途中、開閉など部分木に閉じる状態をlocal stateで持つ | OK |
| 状態をContext、store、query、formなどで共有し、所有者と更新経路が明確 | OK |
| Rootがすべての子孫状態を所有しない | REJECTの根拠にしない |
| stateを外部へ出した、またはRootへ集めたという形式だけを確認する | 判断根拠にならない |

同じ正規状態を複数の所有者が別々に持って同期させ、更新順によって表示や操作結果が変わる場合は、実際の不整合を指摘する。状態をどこに置くかは部分木の整合性と変更経路から決める。

## 表示と動作

| 基準 | 判定 |
|------|------|
| 表示コンポーネントが担当する所有者の公開操作入口を使わず、通信・共有状態変更・外部副作用を裁定する | REJECT |
| Viewが表示値を受け取り、公開callbackや標準APIで操作意図を通知する | OK |
| Viewと状態裁定を同一コンポーネントに置いているが、小さく、所有者と境界が追跡できる | OK |
| hook、reducer、Context Provider、store、query、formがMediatorの役割を実装する | OK |
| Passive View、Mediator、state machineという名称や専用クラスを使っていない | それだけではREJECTにしない |
| 表示責務と動作責務を分けるためだけに、大きな移行や新しい抽象層を追加する | 要求と変更影響を確認する |

## 操作意図とイベント

| 基準 | 判定 |
|------|------|
| 子の操作が所有者の公開操作入口を飛び越え、別の所有者を直接変更する | REJECT |
| 中間コンポーネントが操作callbackやdispatchを意味を変えずに委譲する | OK |
| 担当所有者が状態と意図から受理・拒否を決め、同じ意図を祖先がもう一度実行しない | OK |
| 担当外の中間ノードが意図を上位へ渡す | OK |
| ネイティブイベントの伝播とアプリケーションの意図通知を区別している | OK |
| イベント経路の停止を形式だけで要求する | REJECTの根拠にしない |
| 同じ操作意図が複数の経路から二度実行される | REJECT |
| 担当者が処理した後に祖先が同じ意図を別の処理として重ねる | REJECT |

操作callbackのprops中継が深いという形だけで拒否しない。各中間ノードが状態を再所有したり操作の意味を変えたりしていないか、実際の経路で確認する。

## フレームワークと構成

| 基準 | 判定 |
|------|------|
| 標準hook、Context、dispatch、query、form、bindingを利用し、状態所有者と操作経路が明確 | OK |
| 親が公開したcallbackを子が呼び、担当者が状態を更新する | OK |
| Mediatorというクラス、特定のライブラリ、固定のディレクトリ構成がない | それだけではREJECTにしない |
| すべての状態を外部storeへ移し、local stateを禁止する | GUIの要件とはしない |
| 方式を変えるだけで所有者不在や重複処理が解消されない | REJECT。実害の根本原因を修正する |

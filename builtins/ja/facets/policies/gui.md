# GUIポリシー

画面の組み立て、状態の置き場所、表示部品から画面へ操作を渡す経路、現在状態による判断を確認する。

## 判定基準

| 基準 | 判定 |
|------|------|
| Rootから画面とその部品をたどれ、どこで操作を処理するか分かる | OK |
| 一覧と詳細が同じ注文を別々の`selectedId`で持ち、表示がずれる | REJECT |
| 部品内だけで使う入力値や開閉状態を、その部品が持つ | OK |
| 表示部品が値を表示し、`onSelect`や`onSave`で操作を上位へ知らせる | OK |
| 表示部品が画面固有のAPIを呼び、保存後の移動先まで決める | REJECT |
| 画面が現在状態を確認し、操作を受け入れるか拒否して状態を更新する | OK |
| 行→一覧→画面の順に削除要求を渡し、画面が削除を実行する | OK |
| 処理済みまたは拒否した操作を祖先がもう一度実行する | REJECT |
| 保存ボタンだけで保存中を判定し、キーボード操作からは保存中でも再送信できる | REJECT |

## 例

```text
NG: 共通の ResultsTable が、行クリックで注文APIを呼び、
    注文詳細のURLへ移動する
    → 別画面で表を使うたび、注文用のAPIと移動先まで受け入れることになる

OK: 画面が rows と onSelect(id) を表へ渡し、
    表は行を表示して onSelect(id) を呼ぶ
    → 画面が選択、通信、移動先を決める
```

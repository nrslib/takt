# フロントエンドポリシー

URL、画面遷移、HTML操作、通信状態、アクセシビリティ、ブラウザ安全性を、画面の責務と変更の影響経路に基づいて判定する。

## 原則

| 原則 | 基準 |
|------|------|
| URLと画面 | URLから画面へ到達する経路、履歴、パラメータの扱いを確認する |
| HTML操作 | ネイティブ要素の操作、フォーム、フォーカス、既定動作を利用者の契約として確認する |
| 通信状態 | 読み込み中、成功、空、失敗、キャンセルを画面の表示と操作へ反映する |
| アクセシビリティ | accessible name、role、state、キーボード操作、フォーカスを確認する |
| ブラウザ安全性 | HTML、URL、Storage、Cookie、別オリジンへ入出力する値の境界を確認する |
| 変更経路 | 汎用表示、画面処理、状態、通信の変更理由を分け、影響範囲を追跡する |
| 根拠 | コード、仕様、実在する入口と出力から確認できる問題を判定する |

## URLと画面遷移

| 基準 | 判定 |
|------|------|
| 新しい画面がRouterやフレームワークの入口から到達できない | REJECT |
| URLのpath、query、hashの値を画面が読むのに、型・未指定・不正値の扱いがない | REJECT |
| 画面内のボタンやリンクが、利用者の意図に対応する遷移と履歴操作へつながる | OK |
| 直接URL、戻る・進む、対象なし、権限不足の経路が画面状態として扱われる | OK |
| ルートだけ追加され、メニュー、リンク、外部からの入口が変更契約に含まれるのに配線されていない | REJECT |

## HTML操作とアクセシビリティ

| 基準 | 判定 |
|------|------|
| 操作できる見た目の要素にaccessible name、キーボード操作、適切な要素またはroleがない | REJECT |
| formの入力とlabelが関連付かず、エラーや必須状態を利用者が識別できない | REJECT |
| selected、expanded、checked、disabledなどの状態が支援技術へ伝わらない | REJECT |
| ダイアログやメニューの開閉で、フォーカスの移動・閉じる操作・復帰先が壊れる | REJECT |
| 同じ一覧にある操作要素の対象を、名前または行・グループとの関連付けで識別できない | REJECT |
| 生成したaccessible nameが空、対象を誤認させる、または読み上げとして意味をなさない | REJECT |
| accessible name、role、文言の変更で、利用者が操作対象を識別できない、状態を理解できないなどの破綻が生じる | REJECT |
| DOMのcapture/bubbleとアプリケーションの意図通知が同じ操作を二度実行する | REJECT |

## 通信状態と表示

| 基準 | 判定 |
|------|------|
| 読み込み中、空、失敗、キャンセルを同じ表示や空配列として扱い、利用者が回復手段を選べない | REJECT |
| 通信失敗時に再試行、入力修正、戻るなどの操作経路が状態から追えない | REJECT |
| 汎用表示部品が特定画面のURL、API、再試行、画面遷移を内部に持つ | REJECT |
| 通信を担当する画面または領域が表示パラメータと操作入口を表示部品へ渡す | OK |
| 同じ利用者操作がform、click、親callbackなど複数の入口から通信を二重実行する | REJECT |

## データ取得、キャッシュ、ページング

| 基準 | 判定 |
|------|------|
| 結果を変えるURL、利用者、tenant、filter、sort、page、cursorなどがcache keyや依存へ含まれず、別データを共有する | REJECT |
| 更新後のinvalidation、refetch、またはライブラリの契約に沿うcache更新がなく、古い表示を正規の結果として残す | REJECT |
| cursor/offsetの再取得で、ページの連続性、重複、欠落、並び替え後の表示を扱う条件がない | REJECT |
| query、手書き通信、画面内の保持などの方式が、取得条件と更新経路を満たしている | OK |

## フロントエンドとサーバーの責務

| 基準 | 判定 |
|------|------|
| サーバーが管理・確定する在庫、決済、認可、業務状態を、クライアントの表示判断だけで確定したことにする | REJECT |
| 入力中の形式検証、表示filter、並べ替え、previewなどのUI専用処理を画面の状態として扱う | OK |
| サーバーが決めた許可操作や表示状態を描画し、操作をサーバーのcommandへ渡す | OK |
| 同じ業務判定を複数層で再実装し、結果がずれたときの正本と反映経路が不明 | REJECT |

## ブラウザ安全性

| 基準 | 判定 |
|------|------|
| ユーザー入力をHTML、script、URL、styleへ挿入する経路で、エスケープまたはサニタイズの境界がない | REJECT |
| HTMLの直接挿入、外部遷移、Storage、Cookie、別オリジン通信の値の出所と許可範囲が追えない | REJECT |
| CSRF、認証情報、機密情報の扱いが通信のサーバー契約と一致しない | REJECT |
| 危険なブラウザAPIを使い、その必要性と入力境界がコードから確認できない | REJECT |

深い認証・認可、暗号、サーバー側検証の判定はセキュリティの専門知識へ委ねる。フロントエンドでは、ブラウザを通過する値と外部へ出る操作の経路を具体的に確認する。

## 構造と変更容易性

| 基準 | 判定 |
|------|------|
| 汎用表示部品が特定画面の通信、URL、状態遷移へ直接結合し、表示変更が画面処理の変更を要求する | REJECT |
| 同じ意味の表示、失敗状態、操作の契約が複数の画面で別々に再構成され、片方の変更でずれる | REJECT |
| 表示部品は描画パラメータと操作意図を扱い、画面・領域の担当が通信と状態遷移を扱う | OK |
| componentの分割・共有化が責務、変更理由、再利用単位から説明できる | OK |
| propsの委譲が意味を保ったまま行われ、操作と状態の担当が追える | 変更影響を確認する |

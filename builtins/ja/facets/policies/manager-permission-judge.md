# 道具使用の判断基準

- 最初に、以下の既存の禁止と対象ゴールの制約を評価する。許可の原文や保存済みの人の承認でも、これらを解除することはできない。
- リポジトリの成果物（ソース、テスト、設定、ドキュメント、依存の定義）を書き換える操作は拒否する。
- コミット・マージ・push など、取り込み先を動かす操作は拒否する。
- 外部へ送信する操作、および取り消せない操作は拒否する。ただし、以下のゴール中止道具には専用の確認規則を適用する。
- 別の AI エージェントを起動する操作は拒否する。
- 禁止・制約の内側では、全体・workspace・対象プロジェクト・対象ゴールの許可原文を出典の範囲とファイルパス付きで読み、拒否 > 毎回確認 > 許可の順に評価する。どこかの範囲で拒否に当たれば拒否し、拒否がなく毎回確認に当たれば ask にする。そのどちらでもなく許可に当たれば allow にできる。広い範囲の許可は、狭い範囲の拒否や毎回確認を上書きしない。
- 操作に結び付く保存済み問い合わせと回答は、status、decision、scope、consumedAt、取り下げ状態も含めて読む。消費済みの once を新たな許可として扱わない。
- 読み取り失敗や量の上限超過が入力に含まれる場合、原文がないことを許可と解釈せず、人への確認（ask）にする。
- ゴールの実行状態を変える `takt_pause_goal` / `takt_resume_goal` / `takt_abort_goal` は読み取り操作ではなく、原則 ask とする。対象と状態変更の意図を確認し、中止では取り消せないことを確認事項に含める。既存の禁止・ゴール制約は引き続き優先する。
- 読み取りのみで副作用がなく、人の指示と manager の役割・方針に合い、上記の禁止・制約・拒否・毎回確認に当たらない操作は許可してよい。
- 人にしか決められない事項を含む操作は、人に確認を選び、何を決める必要があるかを理由に書く。
- 情報が不足する場合や判断に迷う場合は、人に確認または拒否を選ぶ。不確実性を許可で埋めない。
- 引数の読み取りらしい見た目、道具の名前、読み取り専用を主張する注釈だけでは許可しない。操作全体の作用を審査する。

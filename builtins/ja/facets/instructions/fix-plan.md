レビュアーの全指摘を、局所対応ではなく一貫した修正へまとめる実行計画を作成してください。

**重要:** このステップではソースを編集しないでください。Previous Response ではなく、Report Directory 配下を再帰的に確認し、現在のコードと合わせて一次情報として使ってください。

**参照方針:**
- parse 可能な Finding Contract ledger がある場合は、open findings を対象の正本とし、個別レポートは原因・再現条件・受入条件の根拠として使う
- ledger がない場合は、Report Directory の最新レビューレポートを対象の正本とする
- persists / reopened、または修正後に新しい構造問題が報告された場合のみ、各レポートの履歴を新しい順に2件まで確認し、以前の修正方針で不足していた前提を特定する

**やること:**
1. 全 open findings と受入条件を列挙し、各 finding ID / 出典を漏れなく1つの修正単位または後続確認へ対応付ける
2. 独立した局所問題、同じ原因に属する構造問題、有効な Policy の全条件を満たす環境要因により実証できない事項を分ける。局所問題は直接修正する単位とし、構造問題はまとめ、環境要因により実証できない事項は実装修正から除外する
3. 各構造問題について、正本から全不変条件、成立例、失敗例・境界値を導き、責務・正本と、実際に関与する入口・型・schema・検証境界・利用側・状態・副作用・失敗経路を定義する
4. 修正単位間の依存順と完了条件を定め、境界・正本、利用側の移行、重複・旧経路の削除を分断しない。環境要因により実証できない後続確認は実施順序へ含めない
5. 各修正単位の方法と証拠を事前照合し、競合する候補案は受入条件を保って置き換える。全不変条件を反証できるテストまたは再現可能な証拠と、品質ゲートを定義する。有効な Policy の全条件を満たす、環境要因により実証できない証拠は現在の完了条件から分離し、決定的な代替証拠と後続確認を定める
6. 同じ要求・設計前提で適合する方法を定義できない場合は計画を確定せず、タスク全体の再計画が必要な根拠を示す

# GUI知識

GUIを階層、状態の所有、操作意図の経路、表示と動作の分離から理解するための基礎知識を提供する。

## UIの階層

画面はRootを頂点とするUIの部分木として構成する。Rootは画面全体を含む構造上の境界であり、すべての状態や副作用を一つのコンポーネントへ集めることを意味しない。画面内の領域や独立widgetには、それぞれの部分木を担当する所有者を置ける。

UIの責務は、概念上は次の役割に分けて考える。

| 役割 | 主な責務 |
|------|----------|
| Root | UIを含む階層の起点、画面やwidgetの組み立て |
| 状態所有者 | その部分木で整合性が必要な状態、操作、外部副作用の裁定 |
| 表示View | 表示値を描画し、利用者の操作意図を上位へ通知 |

1つの小さな画面がこれらを1つのコンポーネントにまとめてもよい。役割を分ける目的はクラス名やファイル配置を増やすことではなく、状態の所有者と操作の経路を追跡できるようにすることである。

## 状態の所有

状態は、その状態を一貫させる必要がある最小の部分木に置く。表示だけに閉じる一時状態は表示コンポーネントのローカル状態でよく、複数の枝で共有する状態は共通の所有者へ移す。画面をまたぐ状態や横断的な状態はContext、外部store、その他の共有機構で所有してよい。

| 状態の性質 | 配置の考え方 |
|------------|--------------|
| hover、focus、入力途中、開閉など表示だけの状態 | 利用するコンポーネントまたは小さな部分木 |
| 親子や兄弟で整合させる状態 | 最小共通の状態所有者 |
| 深い階層や複数画面で共有する状態 | Context、store、その他の共有状態機構 |
| サーバー由来のデータと再取得状態 | query、data fetching hook、状態所有者など、整合性契約を持つ機構 |

子が親や共有状態の値を、所有者が公開した更新契約を経ずに直接書き換える構造は、誰が整合性を裁定するかを隠す。親が公開した操作callback、Contextのdispatch、storeの公開API、formのbindingを利用することは、子から更新が見えても所有者の契約を経由するため、それ自体で状態所有の破壊にはならない。子が自分だけで使うローカル状態を持つことも許容する。

## 表示と動作の分離

Passive Viewは、状態を変更する判断や外部副作用を自分で裁定せず、表示に必要な値を受け取って描画し、利用者の操作意図を通知する基本モデルである。Mediatorは、現在の状態と操作意図から次の状態や副作用を裁定する役割である。

このモデルはフレームワークがない場合にも説明しやすい。Reactのhook、reducer、Context Provider、query hook、form controller、Vueのcomposable、Angularのserviceなどが同じ責務を実現する場合、それらをMVPのクラスへ変換する必要はない。表示と動作の責務、状態の所有者、操作経路が追跡できればよい。

表示コンポーネントが小さなローカル入力を管理することや、入力部品が標準のbindingを使うことは許容される。問題になるのは、表示の都合を理由に通信、共有状態の変更、業務上の裁定などの所有者を隠すことである。

## 操作意図とイベント経路

ネイティブイベントの伝播は、アプリケーション上の操作意図の通知とは別の層である。ブラウザやフレームワークが提供するイベント経路と、状態所有者へ意図を届ける経路を区別する。

| 経路 | 用途 |
|------|------|
| ネイティブイベントの伝播 | 入力元、既定動作、外部環境との統合 |
| 公開callback | 子が親の操作入口へ意図を通知 |
| Context、dispatch、store | 階層内の共有状態所有者へ意図を届ける |
| query、form、bindingのAPI | フレームワークやライブラリが提供する状態・操作の入口 |

イベント経路の停止や重複防止は、実際の操作契約と所有者から決める。中間コンポーネントが公開callbackを受けて上位へ渡すだけなら、階層を越える隠れた操作とは限らない。

操作意図は、担当する状態所有者に到達するまで階層に沿って委譲する。中間ノードが担当しない意図を上位へ渡すことは、Chain of Responsibility（責任連鎖）の基本的な使い方である。担当者が操作を受理または拒否した後に、祖先が同じ意図を別の操作として重ねて処理すると、意図しない重複処理になる。

## 状態機械

状態機械は、状態、操作意図、遷移、遷移に伴う副作用を明示するモデルである。ダイアログの開閉、送信中と完了、選択可能な操作など、状態によって受理できる意図が変わる場合に役立つ。

reducerの分岐、hookの状態遷移、Contextのdispatch、storeのaction、queryのloading/error/success状態なども、同じ情報を追跡できるなら状態機械の実現方法となる。遷移表、専用ライブラリ、Mediatorという名前、特定のクラス構成を採用していること自体は品質の証明にならない。

## 設計判断の目安

| 観測できる構造 | 判断 |
|----------------|------|
| UIがRootから辿れ、各共有状態と操作に所有者がある | 階層構造が成立 |
| 表示Viewが値を描画し、公開された操作入口から意図を通知する | Passive Viewの責務分離が成立 |
| hook、Context、dispatch、query、form、bindingで状態と操作を実装し、所有者を追跡できる | フレームワークに適合した実現 |
| 小さな画面で状態と表示を同じコンポーネントへ置き、所有者と経路が明確 | 分割を強制しない |
| 中間propsやcallbackを通るが、意味を変えず担当者へ意図を届ける | 深さだけで不備とは判断しない |
| DOMイベントとアプリ操作を同じ経路で処理し、同じ操作が二度実行される | 重複処理を調査する |
| パターン名やクラス名がないことだけを根拠に設計を不備とする | 判断根拠にならない |

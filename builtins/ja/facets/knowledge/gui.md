# GUI知識

コンポーネントをRootから始まる階層に組み立て、表示と操作の処理を分ける。

## Rootから始まる階層

Rootが画面を組み立て、画面が一覧や詳細などの部品を組み合わせる。

```
Root
└── 注文画面
    ├── 注文一覧
    └── 注文詳細
```

この階層をたどると、どの画面に部品が表示され、どこで操作を処理するかが分かる。Rootは画面を組み立てる場所として使い、状態はその状態を使う画面や部品の近くに置く。

## 状態を置く場所

一覧と詳細で同じ注文を選ぶなら、共通の親で`selectedId`を持ち、両方へ渡す。部品内だけで使う入力途中の値や開閉状態は、その部品で持つ。

保存の状態を一覧や詳細の両方が表示するなら、画面で`saveState`を一つ持つ。複数画面で使うログイン情報のように長く残る状態は、それを使う画面を含む共有部分で持つ。状態を置く範囲は、同じ値を読む部品と、その値が残る時間に合わせる。

## 表示と操作を分ける

表示部品は、画面から受け取った値を表示し、操作を上位へ知らせる。保存ボタンは`onSave`を呼ぶ。画面側は保存中か確認し、保存できるときだけ通信を始める。成功または失敗で状態を更新し、ボタンやメッセージへ反映する。

```
editing    --保存--> submitting --成功--> success
                               └--失敗--> failure
submitting --保存--> 受け付けない
```

`submitting`の間は保存ボタンを無効にし、同じ保存を二度送らない。成功したら完了を表示し、失敗したらエラーと再試行を表示する。この判断を画面が行い、表示部品は渡された値を表示する。

## 操作を上位へ渡す

部品内で処理しない操作は上位へ渡す。例えば行から一覧へ、一覧から画面へ削除要求を伝え、画面が現在の状態を確認して削除する。処理した操作や拒否した操作を祖先で再実行しない。

## 既存パターンとの対応

MVPのPassive Viewは、表示部品が描画に必要な値を受け、操作意図を通知する考え方である。処理できる上位へ操作を順に渡す仕組みをChain of Responsibilityと呼ぶ。Mediatorは、画面や領域が現在状態を見て操作を受け入れるか、次の状態と必要な処理を決める考え方である。状態機械は、その状態と遷移を表す。

フレームワークではprops、callback、binding、hook、reducerなどの標準の仕組みで、この役割分担を実現する。例えば、祖先が渡したcallbackを子孫が呼び、操作を直接その祖先へ知らせる。

# 根拠に基づく判断

計画・実装・検証・レビューで、要求、観測事実、提案、未確認事項を区別して判断する。

## 原則

| 原則 | 基準 |
|------|------|
| 要求の正本 | 元要件・仕様・公開契約と、計画・報告・提案を区別する。提案は繰り返し記載されただけでは必須要件にならない |
| 双方向の確認 | 判断を支持する証拠と、否定する現在のコード・証跡の両方を確認する |
| 実在経路 | 入口から観測点まで既存の検証・中断・後片付けを含めて追跡し、実際に働く防御を取り除いた仮想経路を欠陥の根拠にしない |
| 効果と正常系 | 防御の存在だけで成立とせず、禁止された結果・副作用を防ぐタイミングと、必要な正常系の保存を確認する |
| 明示義務の保存 | 要求が方式・構造・テスト・文書まで定めていれば、結果が同じという理由で省略しない |
| 未確認の明示 | 証拠の欠如を成功にも欠陥にも読み替えず、判断できた範囲と未確認範囲を分ける |

## 判断と作業権限

- 方式が指定されていない場合は、提案への一致ではなく要求された条件の成立で判断する。現在の挙動や既存テストも、要求に反する振る舞いを正当化する根拠にはしない
- 記録がないことと、必須の実装・検証手段がないことを分ける。不足を主張する場合は、根拠となる義務、満たされていない条件、既存の実装・検証でその条件を満たせない理由を示す
- 判断に必要な情報が足りない場合は、不明な前提と、その確認に必要な情報を示す。推測で原因を確定したり、必須条件を緩めたりしない
- この原則は実行・編集権限や工程の完了条件を変更しない。実装担当に要求されたテスト実行や証跡の提出は省略せず、読み取り専用の担当は新しい実行を行わずに未確認範囲を記録する

## テスト不足の根拠

- テストを必須の追加修正とする場合は、明示された検証義務、新規・変更された振る舞いの代表的な未検証条件、または確認済み不具合の再発防止に結び付ける。新規・変更された振る舞いを根拠にする場合は、今回変更された操作・受け渡し・状態遷移と未検証条件の関係を示す。現在の実装に不具合がなくても、これらのテスト不足は修正対象になる
- 仮想的なコード変更を既存テストが検出できるかは、テストの感度を調べる材料であり、そのテストを今回必須とする根拠ではない。変更していない内部状態に任意の破壊を仮定するだけで、既に確認された振る舞いの受入条件を拡張しない
- 現在の観測点では不十分と主張する場合は、要求された振る舞いのどの条件が未検証かを示す。より深い層、別の状態コピー、後続操作での観測を提案するだけでは不足の証明にならない。既存の観測と実装経路で条件を確認できる場合、追加の観測方法は任意の改善として扱う
- 入力・失敗条件の未検証と、同じ条件に対する観測方法の追加を分ける。新しい呼び出し元から既存処理を利用することや、その内部状態が後続操作で使われることだけで、既存処理の全状態を今回の検証義務へ広げない。既に通している条件に別の観測を必須とするなら、その観測を要求する契約、今回変更した受け渡しや更新規則、または現在確認できる不整合を示す


# 契約置換ポリシー

既存契約の保持、現行利用側の移行、置換対象の旧契約を支える互換・移行を分離し、要求ソースが認めた範囲だけを実装する。

## 原則

| 原則 | 基準 |
|------|------|
| 対象外契約の保持 | 要求の変更対象外にある観測可能な既存契約は維持する |
| 利用側移行 | 置換対象の旧契約を使う現行利用側は新契約へ移行する |
| 旧経路削除 | 明示的に支援対象とされた経路を除き、置換対象の旧経路は削除する |
| 明示要求だけを採用する | 後方互換、legacy support、移行支援、並存は、要求ソースが明示した対象・範囲だけを許可する |
| 必要な方式だけを使う | 明示された対象を満たすために必要な方式だけを追加・維持する |
| 同一決定境界の衝突 | 明示変更と維持候補が同じ観測値・状態遷移・副作用を競合して決める場合、重なる状態では明示変更をそのまま適用する |
| 主操作の終端到達 | 主操作の入力・決定が生成、永続化、状態遷移を経て、後続の実行・表示・APIなどの終端 consumer へ届く経路を先に追跡する |

## 置換対象の旧形式

置換要求に旧形式の読込が明記されていない場合、旧形式の正規表現・変換分岐・fallback は削除対象とする。保存済みデータの存在、読込境界への隔離、低リスクという事情は、互換性を許可する根拠にならない。レビューでは旧形式の残存を問題として扱い、削除を修正案に含める。

旧形式との併存が明示されている場合は、(1) 新規書込が新形式だけを生成すること、(2) 新形式を読込・復元すること、(3) 要求された旧形式を読込・復元することを別々に確認する。旧形式の読込を許可したことから、書込、移行、backfill、別契約の互換性まで推論しない。

| 判定 | 基準 |
|------|------|
| REJECT | 旧形式を新形式へ置き換える要求で、旧形式の読込・変換・fallback・互換経路が明示されていないのに残す |
| REJECT | 保存済みデータの存在、読込境界への隔離、低リスクという理由だけで旧形式の支援を正当化する |
| OK | 要求が明示した範囲に限り、指定された旧形式の読込だけを新形式と併存させる |

## 判定基準

| 基準 | 判定 |
|------|------|
| 変更対象外にある観測可能な既存契約を維持する | OK |
| 置換対象の旧契約を使う現行利用側を新契約へ移行する | OK |
| 旧契約の生成・読込・alias・fallback・変換・upcaster・backfill・data migration・rebuildを、対象への明示要求なしに追加・維持する | REJECT |
| 明示された支援の対象・範囲を超える、または不要な方式を追加する | REJECT |
| API互換の要求をevent upcaster、data migration・backfill、Read Model rebuildなど別の支援対象へ広げる | REJECT |
| 要求ソースにない期限、廃止時期、終了条件、移行日程を要求または補完する | REJECT |

## 明示変更と維持契約の重なり

既定値、優先順位、選択結果、状態遷移、または副作用を要求ソースが明示的に変更した場合、同じ決定境界にある既存候補との重なりを解消する。変更対象外契約の保持は、明示変更と競合しない入力・状態・効果に限る。

| 基準 | 判定 |
|------|------|
| 明示変更の候補と維持候補が同時に成立し、同じ観測値・状態遷移・副作用を別々に決める | 明示変更を winner とし、維持候補は独立した残りの振る舞いだけ保持する |
| 既存選択肢の可用性を維持することを、その選択肢の旧既定値・旧優先順位も維持することへ広げる | REJECT |
| 明示された既定値・優先順位を、現行実装や安全性の好みから `best effort`、任意、「可能なら」へ弱める | REJECT |
| 同じ位置、名前、または結果ラベルを持つ操作を、状態保持・再実行・副作用が異なるまま同一視する | REJECT |
| 同じ決定境界を共有しない契約まで組合せて網羅する | REJECT。契約外の組合せ軸を追加しない |
| 競合する候補を個別入力で検証し、両方が共存する入力で winner と操作効果を検証しない | REJECT |
| 選択値やカーソルが操作を指し、その操作効果が候補を区別する場合に、値の一致だけを検証して選択された操作の種類・効果を検証しない | REJECT |
| 同じ決定を競合する最小共存状態で、選択値と要求に関係する状態遷移・副作用を直接検証する | OK |
| 現行実装・既存テスト・mock・fixture・完了報告が示す挙動を、明示変更と競合する入力・状態・副作用について既存契約として保持する | REJECT。明示変更を適用する |

## 主操作と終端 consumer

変更対象の主操作は、選択や生成だけで完了したとみなさず、下流の終端 consumer が実際に使う状態まで追跡する。復旧、互換、fallback などの secondary 経路は、主操作の経路を閉じた後に、主操作を置き換えない独立した契約として、要求された保持範囲だけを確認する。

| 基準 | 判定 |
|------|------|
| 主操作の producer、永続化または状態遷移、後続 consumer、terminal effect が同じ不変条件を共有する | 1つの経路として追跡し、各境界の観測可能な効果を直接検証する |
| 主操作の決定を保存した後、別の実行・処理がその保存値を読む | 保存値の生成から後続 consumer の実行結果までを先に確認する |
| secondary 操作が同じ選択画面や状態を共有する | 主操作の winner を置き換えず、secondary は要求された独立した効果だけ保持する |
| secondary の可用性・互換性を理由に、主操作の terminal consumer や状態遷移を評価対象から外す | REJECT |
| 主操作と secondary の組合せを、実在する決定境界・consumer が要求していない軸まで増やす | REJECT。主操作の最小 end-to-end 契約に限定する |

## 根拠の境界

現行コード、既存テスト・利用箇所、mock・fixture・test double、修正完了報告、保存済みデータ、公開・リリース状態、読込境界への配置・隔離は、影響経路と現行利用側を調べる証拠として扱う。それだけでは、置換対象の旧契約を維持する要件にならない。

保持すべき既存契約と判断する場合は、元要件・受入条件・公開仕様・実在する利用側の依存のいずれがその振る舞いを要求するかを特定する。特定できない挙動は、現在そう動いているという事実として扱う。

明示的な支援要求がある場合も、対象と範囲を記録し、その振る舞いを直接検証する。支援対象ごとに独立して判定し、1つの対象への要求を他へ広げない。

## contract-lifecycle 判定基準

### ライフサイクル網羅

| 基準 | 判定 |
|------|------|
| 変更したフィールドや振る舞いを生成元または型定義だけ更新している | REJECT |
| 検証、直列化、導出値、別入口、利用元が旧来の意味を残している | REJECT |
| 影響するすべてのライフサイクル境界が同じ必須の意味を保つ | OK |
| 契約を受け取れず導出もできない根拠を示して、影響しない境界を除外している | OK |

### 等価経路

| 基準 | 判定 |
|------|------|
| 一方の入口だけが制約を検証または保存し、等価な入口が迂回できる | REJECT |
| 再試行、再生、import、導出経路が仕様なしに契約の意味を変える | REJECT |
| 等価経路の意図的な違いを元要件または仕様が定めている | OK |

### 入口別経路と資源所有権

| 基準 | 判定 |
|------|------|
| CLI、API、pipeline、再実行などで producer、validator、consumer のいずれかが異なる | 別経路として扱う。1経路の充足だけでは他を証明しない |
| 到達不能または契約に非影響である根拠なく経路を除外する | REJECT |
| 所有者または所有権移譲が不明なまま、last consumer より前に資源を解放する | REJECT |
| 調査または再開に必要な永続 artifact を一時資源と同様に消去する | REJECT |
| 成功、失敗、中断、再試行で所有権と last consumer に沿った寿命契約を保つ | OK |

### 元契約に対する解消

| 基準 | 判定 |
|------|------|
| 局所修正だけで、等価なライフサイクル経路を確認せず解消扱いにする | REJECT |
| 元要件と矛盾する現行実装の振る舞いを、テストが固定しているだけ | REJECT |
| 元要件が影響するすべての経路で成り立つ証跡がある | OK |

# レビューポリシー

全レビュアーが共有する判断基準と行動原則を定義する。

## 前提

このレビューは、依頼に基づきレビュー対象として提供されたコードベースへ行う防御的な品質・セキュリティ監査である。第三者のシステムへの適用や攻撃手法の開発は目的に含まれない。

## 確認方法

レビュアーはコード、仕様、型、schema、test、caller、設定、提供されたレポート、ログ、記録済みの実行結果を読み、変更の正しさを確認する。

- build、型検査、lint、unit test、integration test、E2E、品質ゲートを新たに実行しない。別名のscriptや直接runnerで同じ処理を起動することも含む
- 対象実装を起動して、新しい合否結果や再現結果を作らない。test codeや既存の実行経路を読むことは確認範囲に含める
- build、lint、test、動作確認の結果は、提供されたレポート、ログ、記録済み証跡に実際に書かれている範囲だけを使用する
- 判断直前の再確認では、対象コードと記録済み証跡を再読する。証跡を得たcommandは再実行しない
- 必要な証跡がない、古い、または対象条件を直接観測していない場合は、その範囲を未確認と記録する。証跡の欠如だけをfindingやREJECTの理由にしない
- 振る舞い上の問題を現在のコードと提供済み証跡から確認できない場合は、推測でfindingを作らず未確認とする

## 指摘の再評価と追跡

- 提出された指摘を扱う場合だけ適用する。判断根拠と未確認事項は共通の判断原則に従い、判定ラベル・修正権限・報告形式は担当工程の契約を維持する
- 既存IDが渡されている場合はそのIDと元の受入条件を維持し、現在の根拠・反証を対応付ける。IDや履歴のない入力に、架空のIDや過去の指摘を補わない
- 既存指摘の再評価では、元要件・前回裁定から受入条件の「対象・入力や前提・評価時点・期待結果」を先に特定し、現在の証拠を同じ条件へ照合する。最新レビューの言い換えで対象や評価時点を変えたり、同じ概念の別の値・別の利用場面を元の条件へ混ぜたりしない。異なる条件を追加する場合は、その条件自体が必須である根拠を別途示す
- 元の受入条件と、再レビューで提案された追加の観測方法を分ける。追加要求で指摘を継続する場合は、その要求自体の必須性を現在の根拠で確認する。同じIDの継続や複数担当の一致だけでは、必須性は成立しない
- 前提の反証とは、指摘の前提そのものが誤りで修正が不要だった場合を指す。修正によって元の問題がなくなったことは反証ではない。反証された場合は確認のみでよい理由を記録し、指摘が残ると仮定して不要なコード・テスト変更を要求しない
- 必須条件を緩めず、実在する不足を確定してから計画不備・実装不足・証拠不足を分類する。任意の実行記録の欠如だけは差し戻し理由にせず、未確認として記録する


## 原則

| 原則 | 基準 |
|------|------|
| 即座修正 | 今回の変更で導入した問題と、要件・安全条件の達成に因果的に必要な問題を持ち越さない。採用指摘の解消に必要な変更と修正で新たに発生または露出した阻害要因のうち、その受入条件の達成に必要なものを同じ修正単位に含め、無関係な問題や裁定で除外された指摘の再採用は含めない |
| 曖昧さ排除 | 「もう少し整理して」等の曖昧な指摘は禁止。ファイル・行・修正案を具体的に示す |
| ファクトチェック | 推測ではなく実コードを確認してから指摘する |
| 実践的修正案 | 理想論ではなく実装可能な対策を提示する |
| 状態整合性 | 副作用や状態変更では、実在する正常・失敗・中断経路の漏れ・重複・不整合を確認する |
| 契約影響経路 | 新しい契約は、定義と参照から確認できた入力・変換・保存・消費の経路で一貫していることを確認する |
| 契約一貫性 | 共通化・抽象化で担う契約は、既存の同種分岐にも同じ基準で適用されていることを確認する |
| 意味契約 | ID、source、trace、issue/PR番号などの意味付きフィールドは、保存形式だけでなく下流が解釈する意味まで確認する |
| 外部契約検証 | 外部サービス・SDK・生成物の意味契約を、一次情報または実型で確認する |
| 仕様完全性 | 利用者向け契約を変える場合、実装・テスト・ドキュメントが同じ探索順、上書き規則、特殊記法、失敗条件を説明していることを確認する |
| 元要件固定 | タスク指示書の必須項目を、実装都合で optional・対象外・別要件に読み替えない |
| 解消判定 | resolved 判定は修正内容ではなく、元 finding の受入条件と元要件に戻って確認する |
| 欠陥クラス再走査 | 欠陥を解消済みと認める前に、同じ意味・契約・根本原因を持つと確認した経路を元の受入条件で再走査する |
| 懸念の処理 | 変更契約へ関係する懸念だけを判定し、finding にしない場合は根拠を明示する |
| 振る舞い保証 | テストやログの有無ではなく、期待する振る舞いが検証されているかを確認する |
| 実証可能性 | 環境要因により実証できない事項と、現在の証拠で確認できる実装欠陥を区別する |
| ボーイスカウト | 今回の変更が依存・影響拡大・新規露出する既存問題だけを、タスクスコープ内で改善させる |

計画レポートの留意点（通常計画では確認事項に記録された持ち越し事項）を照合する。欠陥の証拠と既存のスコープ基準を満たすものは、既知事項であることを明記して指摘として提出する。それ以外の項目は指摘にせず、レポート契約の「非finding化した懸念」（testing-review では「未確認範囲」）の欄へ「計画の留意点として持ち越し」と根拠・持ち越し先とともに記録する。この記録は指摘数・REJECT判定・修正対象に算入しない。判断済みの指摘は、再オープン条件を満たさない限り既存の裁定を維持する。

## finding の判定不変条件

| 状況 | 扱い |
|------|------|
| 現在のコードまたは証跡で確認でき、修正を要する欠陥 | issue として報告する |
| 証拠が足りない、探索範囲が不足している、結果を確認できない | 未確認範囲として記録し、issue にしない |
| 不存在または未配線を主張する | 元要件または既存公開契約から存在・配線が必須と導け、必要な全経路を探索済みのときだけ locationless issue にする |
| 品質ゲートの実行・証跡の有無を問題にする | issue にしない |
| 環境要因により実証できず、現在のコードまたは再現可能な証拠からも修正すべき欠陥を確認できない | 未確認範囲として記録し、issue・REJECT にしない |
| 元要件・観測可能な契約を確認しても必要性を導けない、追加の網羅性・対称性・実装やテストのスタイル保証を要求する | issue にしない。言及する場合は非findingの分類と根拠を示す |

- 公開 enum / union に値があること、または一部の convenience method が存在することだけでは、全値に対応する convenience method の公開契約は導けない。元要件、既存の公開仕様、または実在する利用経路が要求するときだけ、不足を issue にする
- APPROVE は issue 0 件、REJECT は issue 1 件以上とする。承認、要約、正常確認を issue として補ってはならない。

## 環境要因により実証できない事項

次の条件をすべて満たす場合だけ、環境要因により実証できない事項として実装上の欠陥と分けて扱う。

- 実証に必要な OS、実行能力、外部サービス、資格情報、ハードウェアのいずれかを現在の実行環境が提供していない
- 不足している環境要件を、対象リポジトリの実装、設定、テスト準備では解消できない
- 同じ実行環境で作業を反復しても証拠を増やせない
- 現在実行できる決定的な代替検証と、対象環境へ到達する実行経路を確認済みである

| 基準 | 判定 |
|------|------|
| 現在のコードまたは再現可能な証拠で実装上の欠陥を確認できる | 通常の判定基準を適用 |
| 上記の全条件を満たし、実装上の欠陥を示す証拠がない | 非ブロッキング。未確認範囲として記録 |
| リポジトリ内の設定やテスト準備で不足を解消できる | 環境要因による実証不能として扱わず、通常の判定基準を適用 |
| 対象環境での実証自体が明示要件である | 実装修正ではなく、実行可能な環境で行う後続ゲートとして記録 |

## スコープ判定

| 状況 | 判定 | 対応 |
|------|------|------|
| 今回の変更で導入された問題 | ブロッキング | REJECT |
| 今回の変更により未使用になったコード（引数、import、変数、関数） | ブロッキング | REJECT（変更起因の問題） |
| 今回の変更が依存・影響拡大・新規露出する既存問題 | ブロッキング | REJECT（ボーイスカウトルール） |
| 既存の曖昧または誤った契約を新しい公開入口・adapter・tool から露出した問題 | ブロッキング | REJECT（既存踏襲を免責にしない） |
| 変更の正しさに直接影響する構造的問題 | ブロッキング | スコープ内なら REJECT |
| 変更外ファイルの問題 | 非ブロッキング | 記録のみ（参考情報） |
| 同じ変更ファイル内にあるだけで変更の正しさに直接関係しない既存問題 | 非ブロッキング | 記録のみ（参考情報） |
| タスクスコープを大きく逸脱するリファクタリング | 非ブロッキング | 提案として記載 |

「直接関係する」とは、今回の変更が既存問題に依存する、問題の影響を拡大・新規露出する、またはその問題を直さないと今回の受入条件・変更契約を満たせない場合を指す。同じファイル、関数、hook、クラス、呼び出し経路にあるという近接性だけでは直接関係と判定しない。変更前後で振る舞いと到達範囲が変わらず、今回の要件達成にも不要な既存問題は非ブロッキングとする。

ボーイスカウトによる因果範囲内の局所改善は推奨する。ただし、ボーイスカウトを理由にタスクの適用範囲を拡大し、要求達成に不要な既存問題、性能改善、設計変更、リファクタリングを blocking finding にしてはならない。

## 判定基準

### REJECT（差し戻し）

まずスコープ判定で変更との因果関係を確認し、その範囲で以下のいずれかに該当する場合は REJECT する。

直後の3つのテスト関連REJECT条件を適用できるのは、今回その検証を追加する義務（明示的な検証要件、検証対象の振る舞い・条件自体の追加や変更、または確認済み不具合）、正本となる受入条件または観測可能な契約、実在する経路で到達可能な具体的失敗、既存テストではその失敗を検出できない根拠、検証を所有する最小レイヤーの5点を全て特定できる場合に限る。1点でも欠ける場合はREJECTせず、追加テストも要求しない。

- 既存テストでは回帰を検出できない新しい観測可能な振る舞いに、契約所有者の最小レイヤーでのテストがない
- 境界変更（権限、拒否、外部実行、共有状態、状態遷移）に対して、主要な許可/拒否・成功/失敗・隔離/解放を既存証跡を含むどのレイヤーでも検証できない
- バグ修正に、変更前の失敗を検出できる既存または新規のリグレッションテストがない
- `any` 型の使用
- フォールバック値の乱用（`?? 'unknown'`）
- 説明コメント（What/How のコメント）
- 未使用コード（「念のため」のコード）
- 呼び出し元所有・共有・外部公開されるオブジェクト/配列を、値を持つ側の更新方法を通さず直接変更すること
- エラーの握りつぶし（空の catch）
- 同じことをするメソッドの増殖（構成の違いで吸収すべき）
- 特定実装の汎用層への漏洩（汎用層に特定実装のインポート・分岐がある）
- 内部実装のパブリック API エクスポート（インフラ層の関数・内部クラスが公開されている）
- リファクタリングで置き換えられた旧コード・旧エクスポートの残存
- 関連フィールドのクロスバリデーション欠如（意味的に結合した設定値の不変条件が未検証）
- 契約変更後の呼び出し元・生成元・利用元・検証元・テストデータ・派生入口の更新漏れ
- ID、source、trace、issue/PR番号などの意味付きフィールドを追加・転送・保存する際に、保存形式だけを確認し、下流の意味解釈や既存フィールドとの混同を確認していない
- 設定・CLI・ファイル形式などの利用者向け契約変更に対して、ドキュメントや例が優先順位、first-match/merge、inline上書き、scope/特殊参照、失敗条件のいずれかを欠落している
- 共通ヘルパー、正規化関数、builder、adapter の追加・変更後に、同じ契約を持つ既存分岐が旧実装のまま残っている
- 新しい公開入口・adapter・tool が既存の曖昧または誤った契約を外部契約として再公開している
- タスクで要求されたフィールド、属性、出力、設定、識別子を、明示根拠なく optional・未設定・対象外として扱う、または入口や実行モードによって欠落させている
- 外部サービス・SDK・生成物の操作ごとのエラー型、ステータス、戻り値、冪等性を確認せず、別操作の契約やモックの成功で代用している
- 副作用や状態変更の実行経路に、漏れ・重複・順序不整合がある
- ログ、エラーレスポンス、テスト出力への機密情報露出
- レビュー本文で契約不整合、副作用、境界値、未確認リスクを認識しているのに finding 化せず、非 finding の分類と根拠も示していない

DRY違反の修正案は、単に共通化を求めるだけでは不十分とする。以下を満たさない共通化案は不適切であり、別案を検討する。

- 共通化先が既存の責務境界・依存方向と整合している
- 新規公開API・wrapper・helperの追加が、既存契約を不自然に広げていない
- 指示書や plan にない追加抽象化を要求する場合、その必要性が根拠付きで説明されている

### Warning（警告）

ブロッキングではないが改善を推奨する。

- エッジケース・境界値のテスト不足
- テストが実装の詳細に依存
- 関数/ファイルが複雑すぎる
- 命名が実体と乖離している
- 理由なしの `@ts-ignore`、`eslint-disable`

### APPROVE（承認）

全ての REJECT 基準をクリアし、品質基準を満たしている場合に承認する。「条件付き承認」はしない。問題があれば差し戻す。

## 振る舞い証跡の判定

設定値、ログ、スナップショット、内部状態を、要求された別の作用の代わりに読むだけでは、その作用を保証できない。一方、状態の遷移・保持そのものが契約である場合は、対象の操作と条件を実際に通して結果の状態を観測するテストを、その契約の直接証拠として扱う。別の作用や後続操作まで要求されている場合は、それらの成立を状態値だけで代用しない。

| 証跡 | 判定 |
|------|------|
| 期待する振る舞いが実行結果として観測されている | OK |
| deterministic なテストで主要な境界条件を検証している | OK |
| 外部環境依存のE2Eのみで、主要境界の再現可能な検証がない | 警告またはREJECT |
| 要求された作用を観測せず、設定値・ログ・内部状態で代用している | REJECT |

提供された検証証跡だけで個別の指摘を閉じない。現在のコード、元の受入条件、証跡が直接観測する条件を照合する。品質ゲートの記録がないこと自体を issue にしない。記録されていないゲートを他の情報から推測して要求しない。

## ファクトチェック

finding は現在のコード、型、スキーマ、一次仕様、または提供された記録済み実行結果で直接裏づける。記憶、検索の不一致、文字化けした出力、実処理を通らないモック、cache や skip により対象を実行していない結果は確定証拠にしない。「存在しない」「未配線」「persists」を主張する場合も、対象契約と現在の実体を確認できなければ finding にしない。

## 指摘ID管理（finding_id）

同じ指摘の堂々巡りを防ぐため、指摘をIDで追跡する。

### Finding ID ルール

- REJECT時に挙げる各問題には `finding_id` を必須で付ける
- 同じ問題を再指摘する場合は、同じ `finding_id` を再利用する
- 再指摘時は状態を `persists` とし、未解決である根拠（ファイル/行）を必ず示す
- 新規指摘は状態 `new` とする
- 解消済みは状態 `resolved` として一覧化する
- `finding_id` のない指摘は無効（判定根拠として扱わない）
- REJECTは `new` または `persists` の問題が1件以上ある場合のみ許可する
- 前回指摘を解消済みとする場合、別の構造問題や契約悪化を新たに導入していないか確認する

### 再オープン条件（resolved → open）

解消済み指摘を再オープンする場合は、現在のコードまたは提供された記録済み証跡による根拠を必須とする。

- 前回 `resolved` の指摘を再オープンする場合、以下3点を必須で提示する
  1. 記録済みの再現条件（コマンド/入力）
  2. 期待結果と実結果
  3. 失敗箇所のファイル/行
- 上記3点が欠ける再オープンは無効（REJECT根拠に使わない）
- 再現する場所や到達経路が変わっても、原因、破られる観測可能な条件、受入条件が同じなら同じ問題として元の `finding_id` を使う。これらのいずれかが異なる場合は別問題として新規 `finding_id` を発行する

### finding_id の意味固定

同じ ID に別問題を混在させない。

- 同一 `finding_id` は同一問題にのみ使用する
- 原因、破られる観測可能な条件、受入条件のいずれかが変わる場合は新規 `finding_id` を発行する
- 根拠ファイル、確認した場所、利用経路、再現入力の違いだけでは別問題にしない。同じ問題について新たに確認した経路と根拠として元の ID へ追加する
- 同一 `finding_id` の説明を後から別問題に差し替えることを禁止する

## 変更履歴ファイルの扱い

過去時点の事実を記録するファイル/セクション (例: `CHANGELOG.md`, `RELEASE_NOTES.md`, `MIGRATION.md`) は、現行コードの仕様書ではなく履歴である。これらを評価する際は履歴としての正しさを基準とする。

| 対象 | 判定 |
|------|------|
| 過去エントリの設定キー・API名・挙動が現行コードと一致しない | REJECT 禁止 |
| 過去リリース時点では正しかった記述 | 修正要求禁止 |
| 新規追加エントリの対象リリース時点での事実誤認 | REJECT 可 |
| Markdown 形式崩れ・重複・リンク切れ・明らかな表記ミス | REJECT または Warning 可 |

### 判断基準

- 履歴は「現在どう動くか」ではなく「その時点で何が変更されたか」を記録する
- 現行コードで名称変更・仕様変更されていても、過去エントリを書き換える理由にはならない
- 過去エントリを修正対象にする場合は、対象リリース時点でも誤りだった根拠を示す
- ファイル名 (`CHANGELOG.md` 等) や慣用的な見出し (`### Changed`, `### Added`, リリース日付つき見出し) で「履歴である」と判別する
- 現行スキーマや現行設定キーとの不一致だけを根拠に履歴ファイル/セクションを REJECT してはならない

## ボーイスカウトルール

来たときよりも美しく。

### 対象

- 今回の変更が依存・影響拡大・新規露出する既存問題（未使用コード、不適切な命名、壊れた抽象化）
- 変更の正しさに直接影響する構造的な問題（責務の混在、不要な依存）

### 対象外

- 変更していないファイル（既存問題として記録のみ）
- 同じ変更ファイル内にあるだけで、変更の正しさ・契約・配線に直接影響しない既存問題
- タスクスコープを大きく逸脱するリファクタリング（提案として記載、非ブロッキング）

### 判定

| 状況 | 判定 |
|------|------|
| 今回の変更が依存・影響拡大・新規露出する既存問題がある | REJECT — 一緒に修正させる |
| 今回の変更が導入した冗長な式、不要な分岐・条件 | REJECT |
| 修正が容易だが変更と因果関係がない問題 | 対象外。容易さをスコープ根拠にしない |
| 変更の結果として未使用になったコード（引数・import等） | REJECT — 変更起因であり「既存問題」ではない |
| 修正にリファクタリングが必要（スコープが大きい） | 記録のみ（技術的負債） |

因果範囲内では、既存コードの踏襲を問題の放置理由にしない。因果範囲外の既存問題は別タスクとする。

## 判定ルール

- 今回の変更が依存・影響拡大・新規露出する既存問題は、既存コードであってもブロッキング（REJECT対象）として扱う
- 「既存問題」「非ブロッキング」に分類してよいのは、変更と直接関係しない箇所の問題のみ
- 「コード自体は以前から存在していた」だけでは判定せず、変更との因果関係を確認する
- 同じファイル、関数、hook、クラス、呼び出し経路にあるという理由だけで既存問題をブロッキングにしない
- 「既存実装と同じ挙動」は、新しい公開入口・adapter・tool がその契約を露出する変更の承認理由にならない
- 本文で触れた懸念を finding 化しない場合は、`false_positive` / `overreach` / `out_of_scope` / `no_issue_after_verification` のいずれかに分類し、根拠を示す
- issue が1件でもあればREJECT。ブロッキング問題を警告や提案へ格下げして APPROVE することは禁止
- Warning と改善提案は issue ではなく、REJECT の根拠にしない。issue が0件なら、Warning や改善提案が残っていても判定は APPROVE とする。言及する場合は、非finding化した懸念または警告の欄へ記録し、finding 欄には入れない

## 堂々巡りの検出

同じ種類の指摘が繰り返される場合、細かい修正指示の反復ではなくアプローチ自体を見直す。

# デザイン忠実再現ポリシー

デザイン参照が指定されている場合、UIの見た目・構造・文言をデザインに一致させる。

## 原則

| 原則 | 基準 |
|------|------|
| デザインが正 | デザイン参照が指定されている場合、それがUIの唯一のソース・オブ・トゥルース |
| 要素の一致 | デザインに存在する要素はすべて実装する。省略しない |
| 独自追加の禁止 | デザインにない要素を独自判断で追加しない |
| 文言の一致 | ラベル・ボタン文言・プレースホルダーはデザインの文言をそのまま使う |
| レイアウトの一致 | 要素の配置順序・並び方向・階層構造をデザインに合わせる |
| 色・間隔の一致 | 色値・余白・角丸・フォントサイズはデザインの指定に従う |

## 適用条件

タスク指示書またはその参照資料にデザイン参照（UIサンプル、モックアップ、デザインファイル等）が含まれる場合だけ、以下の基準を適用する。デザイン参照がなければ対象外とする。

## 判定基準

| 基準 | 判定 |
|------|------|
| デザインにある要素が実装から欠落 | REJECT |
| デザインにない要素が独自に追加されている | REJECT |
| 文言がデザインと異なる | REJECT |
| 要素の配置順序がデザインと異なる | REJECT |
| 色値がデザインと異なる | REJECT |
| 余白・間隔がデザインと明らかに異なる | REJECT |
| デザインにないエッジケースUI（ローディング、エラー、空状態）の追加 | OK |
| デザインが曖昧な箇所の解釈（判断根拠を記録すること） | OK |

## 実装時の手順

1. デザイン参照の要素を列挙する（画面単位・セクション単位）
2. 各要素のレイアウト・文言・色・間隔を確認する
3. 実装がデザインと一致していることを要素単位で照合する
4. デザインが曖昧な箇所は判断根拠を決定ログに記録する

## レビュー時の手順

1. デザイン参照と実装を要素単位で比較する
2. 差分がある場合、各差分について「デザインの指定」と「実装の状態」を具体的に記述する
3. 差分が意図的かどうかを決定ログで確認する
4. 意図的でない差分はブロッキング問題として報告する

## 許容されるケース

- デザインに含まれないエッジケースのUI（ローディング状態、エラー表示、データが空の場合の表示）
- プラットフォーム固有の制約による代替実装（判断根拠を記録すること）
- デザインの解像度が不十分な箇所の合理的な解釈（判断根拠を記録すること）

# GUIポリシー

画面の組み立て、状態の置き場所、表示部品から処理担当へ操作を渡す経路、現在状態による判断を確認する。

## 判定基準

| 基準 | 判定 |
|------|------|
| Rootから画面とその部品をたどれ、どの画面や領域が各操作を処理し、関係する状態を管理するか分かる | OK |
| 複数部品が同じ対象の識別子を別々に持ち、表示や操作の対象がずれる | REJECT |
| 部品内だけで使う入力値や開閉状態を、その部品が持つ | OK |
| 表示部品が値を表示し、操作の意図を上位へ通知する | OK |
| 表示部品が特定画面のAPIを呼び、処理後の遷移や結果まで決める | REJECT |
| Mediatorが現在状態と対象を確認し、操作の受理または拒否、処理、次の状態、結果表示を裁定する | OK |
| 操作の可否を左右する状態を確認せず、受け付けられない操作を実行する | REJECT |
| 受理した操作の処理結果を次の状態や結果表示へ反映しない | REJECT |
| 部品が担当しない操作だけを上位へ順に渡す | OK |
| 処理済みまたは拒否した操作を上位がもう一度実行する | REJECT |
| 確認への回答を待たず、判断の前提となる対象・入力・保存状態を変える操作を実行する | REJECT |
| 確認待ちで、確認と取消の操作を受理し、それぞれの結果を状態へ反映する | OK |
| 仕様が許可または必要とする、確認対象に影響しない独立した操作まで確認待ちの間一律に停止する | REJECT |
| クリック、キーボード、フォームなどの入口が同じ状態判断を通らず、処理中に同じ処理や競合する操作を再送信できる | REJECT |
| 処理中に同じ処理の重複実行や競合する操作は止め、影響しない独立した操作は仕様に応じて続けられる | OK |

## 例

```text
NG: 共通の表示部品が、操作を受けると特定APIを呼び、
    処理後のURLまで決める
    → 別の画面で使うたび、特定の通信と遷移を受け入れることになる

OK: 画面または領域が表示部品へ表示値を渡し、操作の通知を受ける。
    表示部品は値を描画して操作の意図を知らせる
    → Mediatorが現在状態を見て処理、遷移、結果表示を決める

NG: 入力の破棄を確認している間に、別の入口からその入力の保存を始める
    → 確認の前提だった未保存の内容が変わる

OK: Mediatorが確認待ちの状態を見て保存を拒否し、確認への回答を待つ
```


# フロントエンドポリシー

URL、HTML操作、通信状態、アクセシビリティ、ブラウザへ入出力する値を、実際の操作経路と画面の表示から判定する。

## URLと画面遷移

| 基準 | 判定 |
|------|------|
| 仕様で必要なURL、メニュー、リンクから画面を開け、「戻る・進む」で期待する表示に戻る | OK |
| pathやqueryの未指定・不正値・対象なし・権限不足を画面が区別する | OK |
| URLの値を読むのに、型、未指定、不正値の扱いがなく別の対象を表示する | REJECT |
| 画面の操作が、利用者の意図に合うリンクまたはボタンと履歴操作へつながる | OK |

## HTML操作とアクセシビリティ

| 基準 | 判定 |
|------|------|
| クリックできる見た目の要素に名前、キーボード操作、適切な要素またはroleがない | REJECT |
| formの入力とlabel、エラー、必須状態の関連がなく、何を入力すべきか分からない | REJECT |
| selected、expanded、checked、disabledなどの状態が支援技術へ伝わらず、利用者が現在の状態を把握できない | REJECT |
| モーダルダイアログやmenuを開いた後、focusの移動や閉じる操作、focusの戻り先がなく、操作を続けられない | REJECT |
| モーダルダイアログを開いている間にTabまたはShift+Tabで背景へ移動できる、または背景の操作要素をクリック・キーボード・ショートカットで操作できる | REJECT |
| 一覧の編集・削除操作で、どの行の対象か名前または関連付けから識別できない | REJECT |
| DOMのcapture/bubbleと画面への通知で、同じ操作を二度実行する | REJECT |
| 利用バージョンにないpropsを渡す、または生成される要素のname・role・state・操作が実装と合わず、表示・操作・読み上げが壊れる | REJECT |

accessible nameやroleを確認したかだけで判定せず、利用者が操作対象と状態を識別できるかを実装から見る。

## 通信状態と表示

| 基準 | 判定 |
|------|------|
| 未開始、読み込み中、成功、空、失敗、キャンセルを区別して表示する | OK |
| 読み込み中や失敗を空配列へ変換し、待つのか再試行するのか分からない | REJECT |
| 失敗後に、利用者が必要な再試行、入力修正、戻るなどの操作を選べない | REJECT |
| form、click、keyboardなどの入口が同じ操作を二度実行・送信する | REJECT |

## データ取得、cache、ページング

| 基準 | 判定 |
|------|------|
| 利用者、tenant、URL、filter、sort、page、cursorなど結果を変える条件がcache keyや依存に入っている | OK |
| 結果を変える条件がkeyから抜け、別の利用者や画面のデータを共有する | REJECT |
| 更新後にinvalidation、再取得、または利用ライブラリの更新がなく、古いcache表示が残る | REJECT |
| cursorやoffsetの順序、filter、snapshotが合わず、ページの重複・欠落を処理できない | REJECT |
| 既存APIクライアントの型・認証・エラー処理を複製し、変更が片方へ反映されない | REJECT |

## ブラウザとサーバーの役割

| 基準 | 判定 |
|------|------|
| サーバーが管理・確定する在庫、決済、認可、業務状態を、クライアントの表示判断だけで確定したことにする | REJECT |
| 入力中の形式検証、表示filter、並べ替え、previewを画面の状態として扱う | OK |
| サーバーが返した許可操作や結果を表示し、操作をサーバーのcommandへ渡す | OK |
| 同じ業務判定を複数層で実装し、正しい結果と反映経路が分からない | REJECT |

## ブラウザ安全性

| 基準 | 判定 |
|------|------|
| ユーザー入力をHTML、script、style、URLへ渡す経路に、エスケープまたはサニタイズがない | REJECT |
| HTMLの直接挿入、外部遷移、Storage、Cookie、別オリジン通信の値の出所と許可範囲が読める | OK |
| CSRF、認証情報、機密情報の扱いが、ブラウザとサーバーの契約に合わない | REJECT |
| 未検証の入力を`innerHTML`や`eval`へ渡し、コードとして実行させる | REJECT |

## 例

変更前: モーダルダイアログを表示した後も背景のキーボード操作が処理担当へ届き、
        確認待ちの判断と競合する処理を開始する
変更後: モーダルダイアログを開いている間はフォーカスを内部に留め、背景のユーザー操作全体を抑止する

# 問い合わせ返信デスク

問い合わせの一覧から1件を選び、返信を編集して保存する小さなWebアプリです（React 19 + TypeScript + Vite）。
保存はブラウザ内の疑似サーバー（約1秒かかる非同期処理）で再現しています。外部サービスは使いません。

## 起動方法

```sh
npm run dev      # http://127.0.0.1:5173/ を開く
npm run build    # 型チェック（tsc --noEmit）と本番ビルド
npm run preview  # ビルド結果を確認
```

## 操作方法

| やりたいこと | 操作 |
|---|---|
| 問い合わせを選ぶ | 左の一覧のボタンを押す。右に本文、保存済みの返信、返信の編集欄が出る |
| 一覧を検索する | 「検索」欄に入力（件名・お客様名・本文・保存済みの返信が対象）。該当がなければその旨を表示 |
| 返信を保存する | 「返信を保存」ボタン、または入力欄で Ctrl+Enter / ⌘+Enter。Enterだけなら改行 |
| 保存済みの内容へ戻す | 「保存済みの内容へ戻す」 |
| 未保存のまま別の問い合わせを選ぶ | 確認ダイアログで「変更を破棄して切り替える」か「切り替えをやめる」（Escも「やめる」） |
| 操作説明を見る | ヘッダーの「操作説明」または返信欄の「操作説明」。閉じると押したボタンへフォーカスが戻る |
| 保存の失敗を試す | 画面下の「実演用」で「次の保存を失敗させる」にチェックしてから保存。失敗後も入力は残り、「もう一度保存する」で再試行できる |

表示される状態：

- 編集欄の下に「未保存の変更があります」「保存中です…」「保存しました（時刻）」「保存済みの内容と同じです」のいずれかを表示します。
- 空白だけの返信を保存しようとすると、入力欄を `aria-invalid` にして修正を促すエラーを出します（保存回数は増えません）。
- 保存中に一覧から別の問い合わせを押すと切り替えず、一覧の上に理由を表示します。保存ボタンの連打や Ctrl+Enter の押し続けは最初の1回だけ受け付け、以降は「受け付けませんでした」と表示します。
- 「受け付けた保存処理の累計」は、受け付けた保存だけを数えます（入力不備・保存中の重複・ダイアログ表示中の操作は数えず、受け付けて失敗した保存は1回と数えます）。
- 保存に成功すると、一覧の返信・更新時刻と詳細の「保存済みの返信」が新しい内容に変わります。

## 構成

```
src/
  main.tsx                         Reactの起動
  App.tsx                          Root。画面を1つ組み立てる
  screens/
    InquiryDeskScreen.tsx          画面。状態を表示部品へ配り、操作の通知先を渡す
    useInquiryDesk.ts              Mediator。操作を状態機械へ通し、受理された保存だけ通信を始める
    inquiryDeskMachine.ts          状態機械（純粋なreducer）と状態の型
  components/                      Passive Viewの表示部品
    AppHeader.tsx / InquiryList.tsx / InquiryDetail.tsx / ReplyEditor.tsx
    DemoControls.tsx / HelpDialog.tsx / DiscardChangesDialog.tsx / ModalDialog.tsx
  api/fakeInquiryServer.ts         疑似サーバー（保存済みの値を持ち、約1秒後に成功または失敗）
  domain/inquiry.ts                問い合わせの型、初期データ、空白判定、日時表示
verify/machine.check.ts            状態機械と疑似サーバーの確認スクリプト（ビルド対象外）
```

## 設計と6文書との関係

### Rootからの階層と状態の置き場所（knowledge/policies-gui, knowledge/policies-react）

`App → InquiryDeskScreen → 各表示部品` の一本の階層です。値の置き場所は、使う範囲と寿命で決めました。

| 状態 | 置き場所 | 理由 |
|---|---|---|
| 問い合わせ一覧、選択中ID、編集中の返信（下書き）、進行状態（編集中・切替確認中・保存中）、直近の保存結果、拒否理由、操作説明の開閉、失敗予約、保存回数 | `useInquiryDesk`（画面） | 一覧・詳細・編集欄・ダイアログが同じ対象と進行状態を使い、保存や切替の可否判断に必要 |
| 検索語 | `InquiryList` 内の `useState` | 一覧の表示フィルタとしてだけ使い、他の操作の判断に影響しない |
| `<dialog>` の DOM 開閉の同期 | `ModalDialog` 内のref | DOMとの同期だけ。開くかどうかは上位のstateに従う |

- 選択中IDは画面だけが持ち、一覧（`aria-current`）と詳細は同じ値から描画します。対象の識別子を部品ごとに持ちません。
- 下書きは「確定するまで保存済みの値へ反映しない値」ですが、未保存判定・切替確認・保存の判断に使うため画面側の state に置きました。切替を受理したときに reducer が対象の保存済み返信で作り直すので、別の問い合わせの入力は混ざりません。props を Effect でコピーする処理はありません。
- 「未保存の変更あり」「選択中の問い合わせ」「検索結果の件数」「状態表示の文言」は、描画中に state から計算しています（派生値を state に保存しない）。

### Passive View（knowledge/policies-gui）

表示部品は props の値を描画し、`onSelect(id, opener)`・`onSave()`・`onRevert()`・`onOpenHelp(opener)` などで操作の意図を通知するだけです。疑似サーバーを呼ぶのは `useInquiryDesk` だけです。`ReplyEditor` は Ctrl+Enter をフォーム送信へ変換するところまでを担当し、保存するかどうかは判断しません。

### Mediator と状態機械（knowledge/policies-gui, knowledge/policies-react）

- `inquiryDeskMachine.ts` の `deskReducer` は、現在の状態と操作から次の状態を返す純粋な関数です。受理・拒否、拒否理由、次の状態をここで決めます。
- `useInquiryDesk` のハンドラが reducer を通し、保存が受理されたとき（受付回数が増えたとき）だけ `saveReply` を呼びます。結果は `saveSucceeded` / `saveFailed` を dispatch して反映します。reducer の中で通信やタイマーは動かしません。保存要求ごとの `requestId` を照合し、古い応答が新しい状態を上書きしないようにしています。
- 連打で同じイベントループ内に操作が続いても最新の状態で判断できるよう、ハンドラは ref に同期的に反映した状態で判断し、同じ値を描画用の state に渡しています。
- 主な判定：

| 状態 | 保存 | 切替 | 入力・戻す | 操作説明 | 失敗予約 |
|---|---|---|---|---|---|
| 編集中 | 空白なら入力不備、それ以外は受理 | 未保存なら確認待ちへ、なければ切替 | 受理 | 受理 | 受理 |
| 保存中 | 拒否して理由を表示 | 拒否して理由を表示 | 拒否（入力欄は読み取り専用） | 受理（保存の前提を変えないため） | 受理（次の保存にだけ影響するため） |
| 切替確認中 | 拒否 | 「破棄」「やめる」だけを受理 | 拒否 | 拒否 | 受理 |
| 操作説明の表示中 | 拒否 | 拒否 | 拒否 | ― | 受理 |

  確認待ちでは、その前提（対象・下書き・保存状態）を変える操作を拒否します。確認に影響しない「失敗予約」は Mediator 上は止めません（ただしモーダルなので画面からは操作できません）。

### 入口を一つにする（knowledge/policies-frontend, knowledge/policies-react）

保存の入口は `<form onSubmit>` の一つです。ボタン（`type="submit"`）も、再試行ボタンも、Ctrl+Enter（`form.requestSubmit()`）もここを通り、同じ `requestSave` の判断に入ります。クリックと送信から別々に通信を呼ぶことはありません。IME変換中の Enter は無視します。

保存中のボタンは `disabled` ではなく `aria-disabled` にしています。押されても Mediator が拒否して理由を出し、フォーカスも失われません。一覧のボタンも同じで、保存中は `aria-disabled` と `aria-describedby` で「切り替えられない理由」を伝えます。

### HTML操作・アクセシビリティ・モーダル（knowledge/policies-frontend）

- ボタン・ラベル付きの入力欄・チェックボックスなど標準要素を使っています。選択中は `aria-current`、入力不備は `aria-invalid` と `aria-describedby`、保存中は `aria-busy`/`aria-disabled`、失敗は `role="alert"`、状態や拒否理由は `role="status"` で伝えます。
- 2つのダイアログは共通の `ModalDialog`（ネイティブ `<dialog>` の `showModal()`）です。背景は inert になるため、Tab/Shift+Tab のフォーカス、クリック、キーボードショートカット（Ctrl+Enter を含む）は背景へ届きません。`aria-modal` だけには頼っていません。さらに Mediator 側でも、ダイアログ表示中の保存・切替を拒否します。
- 開いたらダイアログ内へフォーカスを移し（切替確認では安全な「切り替えをやめる」）、閉じたら開いたボタンへ戻します。戻り先はクリック時の `event.currentTarget` から受け取り、Safari のようにクリックでボタンがフォーカスされないブラウザでも戻るようにしています。Esc（`cancel`）でも上位の状態判断を通して閉じます。

### 通信状態の表示（knowledge/policies-frontend）

保存の状態（未保存・保存中・成功・失敗・入力不備）を区別して表示します。失敗時は入力を残したまま理由と「もう一度保存する」を示します。初期データはローカルで同期的に得られるため、読み込み中の状態はありません。キャンセル操作は仕様にないため用意していません。保存成功時は、サーバーが返した問い合わせで一覧の該当項目を置き換えるので、一覧と詳細が同時に更新されます。

### ブラウザとサーバーの役割、安全性（knowledge/policies-frontend）

- 空白だけかどうかは入力中の形式検証として画面で判定します。保存したかどうかと保存時刻は疑似サーバーの応答で確定します（画面側で保存済みと決めることはありません）。
- ユーザー入力はすべて React のテキストとして描画し、`innerHTML` は使いません。Storage・Cookie・外部通信はありません。

### 対象外にしたもの

URLによる対象指定や再読込後の保持は仕様上不要なので、Routerや永続化は入れていません（frontend文書のURLの項は適用する場面がありません）。TanStack Query などのデータ取得ライブラリも使っていません。

## 検証したこと

- `npm run build`（`tsc --noEmit` と `vite build`）が成功することを確認しました。
- 状態機械と疑似サーバーについて、手順と期待結果を `verify/machine.check.ts` に書きました。内容は、初期表示、空白の入力不備、連打時に受付が1回になること、保存中の切替・入力・戻すの拒否、約1秒の保存と一覧への反映、失敗予約による失敗・下書きの保持・再試行での成功、古い応答を無視すること、切替確認（やめる／破棄）、戻す、操作説明中の拒否と閉じた後の再開です。
  ただしこのセッションの実行環境では `npx`・`node`・`npm run verify` の実行が許可されなかったため、**このスクリプトは実行していません**。`npm run verify` で実行できます（esbuild でバンドルして Node.js で実行します。`@types/node` は未導入のため `tsc` の対象外です）。
- ブラウザでの手動操作（フォーカス移動、読み上げ、モーダル中の背景操作の抑止）は、この環境では確認していません。上記の設計はコードを読んで確かめたものです。

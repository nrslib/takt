# 実装生成によるGUI・frontend基準の検証

問い合わせ返信アプリの生成結果を動かし、不具合から基準を修正する実験。モデルが書いた実装は評価者が修正せず、生成セッション終了時のまま保存する。

## 課題と実行条件

同一課題は `baseline/TASK.md`。React・TypeScript・Viteで、一覧、返信編集、非同期保存、失敗と再試行、未保存編集の破棄確認、共通ヘルプを実装する。

追加の設計資料はGUI・frontend・Reactのknowledgeとpolicyの6ファイルだけ。`$coding`、他のスキル、AGENTS.md、過去の会話、既存実装、評価コード、模範解答を参照しない新規セッションで生成する。仕様や識別子、コンポーネントの分け方を、評価者が追加で教えることはしない。

Lunaは `gpt-5.6-luna` / effort `max` / Codex CLI 0.155.1を使用。CLIの標準指示と事前学習済みの知識まで排除した実験ではない。スキルの本文やプロジェクトの指示を参照していないことは、実行引数だけでなく、実際のセッションとツール呼び出しで確認する。

## 変更前に見つかった問題

旧基準から生成した実装は `baseline/`。独立レビュー後の比較用ブラウザ検証では15件中12件成功、3件失敗した。

| 操作 | 実際の結果 | 不足していた責任 |
|------|------------|------------------|
| ヘルプを開いてTab・Shift+Tabで移動する | 背景の操作要素へ移動できる | モーダル表示中の背景操作の抑止 |
| 未保存編集の破棄確認を開いてTab・Shift+Tabで移動する | 背景の操作要素へ移動できる | 同上 |
| 破棄確認への回答前に保存通知を送る | 確認待ちでも保存処理が始まる | Mediatorでの確認状態の判断 |

3件目はUIの操作可否とは別に処理担当の判断を確かめる検査。まず編集状態で同じ通知経路から保存できることを確認し、確認待ちの間だけ拒否すること、取消後には再び受理することを検証する。ユーザー操作による背景への移動は前の2件で別に検証する。

最初のサンプル評価と今回の比較は、検査の内訳が異なる。今回の比較では「保存済みへ戻す」と「検索の復帰」をまとめ、処理担当による確認中の保存拒否を加えた。さらに独立レビューで仕様にない390pxでの横幅制約を除外し、15件にした。旧実装も同じ15件で再検証しており、以前の検証件数と混ぜて比較しない。

## 基準の修正

- GUI: 確認への回答を待つ間は、それと競合する操作をMediatorで拒否する。受理・拒否と、処理結果の状態への反映を別々に判断する。
- GUI: 状態と操作は必要な範囲で管理する。独立した領域まで一律に止めない。
- frontend: モーダルでは、フォーカスの移動と復帰に加え、表示中の背景操作を抑止する。`aria-modal`だけでは操作を止められない。
- React: 共通の親で管理するstateのOK例を、兄弟が共有する状態に限定した。callback、hook、Context、form actionなどで責任を実現でき、専用のクラスやすべての階層での手動転送は要求しない。

最初の改訂では、確認中の「対象変更・保留中の処理」を拒否すると記述したが、再生成した `candidate/` にも保存受付で確認待ちを見ない問題が残った。そこで「確認への回答前に、判断の前提となる対象・入力・保存状態を変えない」と対象を明確にし、破棄確認中の入力を保存するNG例を加えた。

別課題の `independent-regions/` は操作の独立性を満たす一方、領域固有の状態と送信処理をすべてAppに持たせていた。生成READMEも兄弟カードであることを親への集約理由にしていたため、Reactの親での状態管理に共有という条件を補った。機能検査が通ることと、意図した責任の分け方であることを区別する。

この修正後の `independent-regions-v2/` も、宛先ごとに異なる状態を「兄弟カードの共有状態」と説明していた。最後に、独立した操作領域にはそれぞれのMediatorがあり、その領域で完結する状態と操作を持つことを階層の説明に組み込んだ。`independent-regions-v3/` では、各領域がそれぞれ状態と送信処理を持ち、Rootは共通ヘルプを管理する実装になった。

## 比較方法

`check-reply-desk.mjs` が同一課題の15件を検証する。生成結果ごとに変更するのは要素を見つけるためのadapterだけで、操作と期待結果は共通にする。

ネイティブの `dialog.showModal()` について、ChromiumではTab移動中に `document.activeElement` が一時的にBODYになることを実測した。BODYだけでは不具合と判定せず、背景の操作要素へ移るかを調べる。この調整は新実装の生成前に行った。独立レビューで、開いた直後の可視性・内部フォーカスの確認と非同期描画の待機を加え、旧実装を再検証した。各版のコードとハッシュは `evidence/test-frozen.json` と `evidence/harness-review-revision.json` に記録している。Playwrightのimportをパッケージ名に変えた保存版も別に記録している。

Opusの実行では、一覧行の「未保存」表示を編集前と比較してしまう検査側の誤りが見つかった。比較の開始点を、編集して確認を開いた後、保存通知を送る直前に直した。旧実装・改訂1・改訂2・Opusのすべてに同じ15件を再実行した。変更理由・旧検査・旧結果・新検査のハッシュは `evidence/opus-harness-calibration.json` と関連ファイルに残している。

別課題では、二つの宛先へのメッセージ入力と送信を生成する。一方の処理中や破棄確認中も他方を使えることを含め、`check-independent-regions.mjs` で検証する。この課題の確認は領域内の表示であり、画面全体のモーダルではない。検証コードは生成された実装を読む前に用意する。

再実行時は各サンプルで `npm ci`、`npm run build` を実行し、ローカルでViteを起動する。評価側のPlaywrightをインストールしたリポジトリから、URL・adapter・結果保存先を渡して実行する。

```sh
node eval/results/frontend-generation/2026-09-22/check-reply-desk.mjs \
  http://127.0.0.1:4177 \
  eval/results/frontend-generation/2026-09-22/evidence/baseline-adapter.json \
  /tmp/frontend-baseline-result
```

## 実行できる最小例

アプリ全体とは別に、`eval/fixtures/frontend-design/src/gui-patterns/` に問題を切り分けた2組を追加した。

| 比較 | 問題がある例 | 問題を防ぐ例 |
|------|--------------|--------------|
| 確認中の保存要求 | `confirmation-a.tsx` | `confirmation-b.tsx` |
| モーダル表示中の背景操作 | `modal-a.tsx` | `modal-b.tsx` |
| 拒否した保存要求の上位への転送 | `guard-a.tsx` | `guard-b.tsx` |

`eval/scripts/frontend-gui-browser.mjs` で既存のguardペアを含む6例を実行し、悪い例では問題が起き、良い例では防げることを確認する。この結果だけでプロンプトが改善したとは判断しない。生成結果の比較、既存32例のモデルレビューとは別の検証である。

保存の検査ではブラウザの時計を停止し、処理中の拒否を確認してから完了まで進める。実時間が経過しても処理中のままであることも検査する。最終実走記録は `evidence/fixtures-browser-clock.log`。

既存のguardペアも、保存完了後に編集中へ戻り、古い拒否メッセージを消し、保存内容を表示する例に修正した。両例の違いは、空入力・処理中の拒否後に親の保存処理へ進むかどうかだけである。

## 結果の解釈

| 生成条件 | 同一課題の動作 | 別課題の動作 | コード上の確認 |
|----------|----------------|--------------|----------------|
| 旧基準 | 12/15 | 未実施 | 確認中の保存を受理、モーダルから背景へTab移動 |
| 最初の改訂 | 14/15 | 9/9 | 確認中の保存拒否は未達。別課題は領域固有の状態を親に集約 |

返信課題の最終検査結果は `evidence/{baseline,candidate,candidate-v2,opus}-final/`。別課題の結果は `evidence/independent-regions-reviewed/`、`evidence/independent-regions-v2-reviewed/`、`evidence/independent-regions-v3-final/`。途中のサンプルは不足を残した生成結果であり、すべてを推奨実装として提示するものではない。

Lunaの `candidate-v2/` は15項目を通ったが、コード上では入力変更の通知に確認待ちの判定がない。この経路は15項目に含めていないため、結果を「すべての通知を正しく拒否する」証明として扱わない。Opusの同じ箇所は `deskReducer` の `draftChanged` で編集中かを確認する。Opus自身が作った `verify/machine.check.ts` も生成後に評価者が実行し、確認中の入力変更拒否を含めて通過した。これはモデル自身が書いた検査であり、独立した15項目とは別の証拠である。

## コードを見る入口

返信課題は [`opus/src/screens/inquiryDeskMachine.ts`](opus/src/screens/inquiryDeskMachine.ts) と [`opus/src/screens/useInquiryDesk.ts`](opus/src/screens/useInquiryDesk.ts) から追える。

- `App` が画面を組み立て、画面が一覧・詳細・編集部品へ値と操作の通知先を渡す。
- 編集部品のボタンとショートカットはフォーム送信へ合流し、画面のMediatorへ保存の意図を知らせる。
- 状態機械が編集中・確認待ち・保存中を見て操作を判断し、受理された保存だけをhookが開始する。
- 成功・失敗は状態機械へ戻され、一覧・保存済み返信・入力欄・結果表示へ反映される。

これらの名前やファイル分割を共通基準に指定したわけではない。Opusが6文書と課題から選んだ実装である。

独立した二領域の例は [`independent-regions-v3/src/App.tsx`](independent-regions-v3/src/App.tsx)。各 `MessageComposer` が `useMessageComposer` を呼び、入力・確認待ち・処理状態・タイマーを領域ごとに持つ。共通ヘルプの操作は親へ通知する。9項目では仕様にあるヘッダーと二つの入力欄の入口を検証した。生成結果に追加された操作概要のヘルプ入口は、この検査の対象外である。

追加確認では、失敗した本文を編集してから結果欄の「この本文を再試行する」を押すと、結果欄に表示された失敗本文ではなく現在の入力を送ることを実測した。領域の責任の配置は改善したが、この表示と対象のずれは残っている。共通9項目と分けて `evidence/independent-regions-v3-retry.json` に記録し、生成コードには修正を加えていない。

## レビュー用32例の別評価

二回目の改訂時点のLunaは、React基準なし・ありの両方で32件の自動採点を通過した。理由もコードと照合した。初回のReactあり回答では `total-a` の初期値の説明が誤っており、最終結果と混ぜて成功扱いしない。

Opusは両構成とも前後の説明文を追加したためJSON形式の検査に失敗した。配列内の32判定は両構成とも期待と一致し、主要な拒否理由もコードに対応するが、出力全体を自動PASSへ読み替えていない。Reactなし回答の冒頭はOK/REJECT件数が逆で、検索画面のURLについては課題から確定できない補足があった。

このモデルレビューの入力は二回目の改訂で固定したもので、後続の領域説明の明確化を含まない。使用した32個のコードは `evidence/model-review-v2-fixtures/`、プロンプトと参照資料は `evidence/model-review-final-inputs/` に保存している。

保存のguardペアを修正した後は、この2例だけを最新の領域説明を含む基準で再評価した。Luna max、続くOpusともReact基準なし・ありの両構成でJSON形式と判定を通過し、理由もコードと照合した。Opusの初回は認証情報へアクセスできず起動エラーとなり、同じ入力を権限を拡張した環境で再実行した。入力・ハッシュ・両方の出力は `evidence/guard-final-review/` に保存している。旧32例と修正後2例は別の評価として扱う。

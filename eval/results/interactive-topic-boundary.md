# 対話モードの話題境界と調査結果の扱い

この評価は、１つの会話で `caccia` の要件整理を終えた後、別領域の Quint 診断改善へ移る入力を使う。対話継続、`/go`、`/tell` で古い話題が混ざらないことを測る。ユーザーが２件を同じタスクにすると明示する対照もある。追加の `/go` ケースでは、アシスタントが確認したコード上の事実と提案を、ユーザーが採用していない実装義務へ変えないこと、および明示採用された方式を残すことを測る。

生成モデルは Claude Opus `claude-opus-5` と Codex Luna `gpt-5.6-luna`（推論強度 `max`）で、日英の各ケースを３回ずつ、キャッシュなしで実行する。調査権限の意味判定だけ `llm-rubric` を使い、判定モデルは Codex Luna `gpt-5.6-luna`（`high`）とする。それ以外は対象話題の識別子・要件の存在と、対象外話題の識別子の不在を機械判定する。

## 変更前の実測

通常の10ケースは60出力中48件が総合合格した。内訳は次の通り。各セルは６出力中の総合合格数で、日英各１ケースを３回実行した値である。

| 経路 | Claude Opus | Codex Luna |
| --- | ---: | ---: |
| 対話継続・assistant | 2/6 | 6/6 |
| 対話継続・Grill Me | 2/6 | 6/6 |
| `/go`・別タスク | 4/6 | 4/6 |
| `/tell`・別タスク | 6/6 | 6/6 |
| `/go`・明示的に同じタスク | 6/6 | 6/6 |

通常ケースの指標別では、対象 Quint 要件の検出が60/60、旧話題の扱いが48/60、テキスト再生の検査が60/60、対話継続の質問・整理形式が24/24だった。対象要件の語彙判定は、Quint 名やファイル名がなくても「検証／構文エラーの行番号と原因」が揃う応答を受理するよう補正した。変更前の１出力で対象要件と応答形式の判定が不合格から合格へ変わったが、同じ出力は `caccia` に言及しており、総合合格数は変わらない。Claude の対話継続では `caccia` が「別タスク」「対象外」という断り書きにも現れ、`/go` では両モデルで以前のタスクが混入した。基線の `/tell` は両モデルとも6/6、Codex の対話継続は assistant と Grill Me を合わせて12/12であり、その経路では失敗を再現していない。従って「変更前に１〜３がすべて失敗する」という当初の受入条件は、この固定入力とモデルでは満たしていない。

調査権限の４ケースは24出力中５件が総合合格した。意味判定と旧話題の不在を分けると次の通り。意味判定の合格は `llm-rubric` の pass 値で数え、スコアの小数値を合格件数へ丸めていない。

| ケース・モデル | 総合 | 調査・採用の意味判定 | 旧話題なし |
| --- | ---: | ---: | ---: |
| 未採用・Claude Opus | 1/6 | 6/6 | 1/6 |
| 未採用・Codex Luna | 1/6 | 2/6 | 4/6 |
| 明示採用・Claude Opus | 0/6 | 6/6 | 0/6 |
| 明示採用・Codex Luna | 3/6 | 6/6 | 3/6 |

未採用ケースの Codex 出力には、調査で見つけた `formalSpecPrompts.ts` や関数を必須の作業対象に固定する例があった。Codex の未採用ケースで意味判定が不合格だったのは4/6であり、合格２件のうち１件は旧話題混入で総合不合格だった。一方、調査ケースの総合不合格19件をすべてその権限境界の失敗とは扱わない。Claude の意味判定は未採用・明示採用とも全件合格で、主な失敗は旧話題の混入だった。

通常ケースの生出力は `.tmp/interactive-topic-boundary-before-v2/results.json` に保存した。元の採点に含まれた識別子判定の偽陰性を修正し、同じ60出力だけを再採点した値が `.tmp/interactive-topic-boundary-before-v2/rescored-topic-results.json` である。調査４ケースは最初の採点設定が判定モデルに非対応だったため、設定を直して同じ変更前テンプレートから再生成し、`.tmp/interactive-topic-boundary-before-research/results.json` に保存した。保存済みの84件の生成入力が、変更前テンプレート・固定 fixture・共通の再生制約から再構築した文字列と完全一致することを `.tmp/interactive-topic-boundary-before-research/prompt-equivalence.json` で確認した。通常ケースの元出力は変えていない。

## 変更後の測定

変更前と比較可能な14ケース×２モデル×３回の84出力に加え、`/tell` で会話最後の Quint とは異なる先行 `caccia` タスクを送信先に選ぶ対照を日英各１ケース、計12出力追加した。初回候補の96出力は `.tmp/interactive-topic-boundary-after/results.json` に保存した。追加対照は変更前の84出力へ合算せず、送信先を本文生成前に選ぶ新しい配線の検証として別に報告する。

初回の採点では94/96だった。不合格２件のうち、比較可能な `/go` 明示結合ケース１件は判定の偽陰性だった。出力には `caccia` のファイル・要件と「未解決の review thread を残さない」「unresolved review threads が存在しない」という受入条件があり、旧判定式だけが後二者を受理しなかった。日英の同義な不在表現を受け入れ、否定の反転表現は拒む判定式に修正した。さらに対話継続では Quint 名やファイル名がなくても B 固有の要件語が揃う応答を受理するよう補正した。同じ最終判定を保存済み初回候補へ当てると、対象話題95/96、対象外話題の扱い96/96、対話継続形式24/24、総合95/96となる。

残る実際の不合格は追加 `/tell` 対照の Codex 日本語１出力で、`caccia` の機能と受入条件を残した一方、ユーザーが明示した `src/features/caccia/` を省略した。旧話題の混入ではなく、明示対象の保持に失敗した。送信先タスクでユーザーが指定・採用した変更対象、要件、受入条件を残す規則を日英の `/tell` テンプレートへ追加した。初回の95/96を最終改善率とは扱わない。

| 集計 | 変更前 | 初回候補の元採点 | 初回候補の判定補正後 | 最終候補の判定補正後 |
| --- | ---: | ---: | ---: | ---: |
| 比較可能な14ケース・両モデル・３回 | 53/84 | 83/84 | 84/84 | 84/84 |
| 通常の話題境界10ケース | 48/60 | 59/60 | 60/60 | 60/60 |
| 調査権限４ケース | 5/24 | 24/24 | 24/24 | 24/24 |
| `/tell` 宛先選択の追加対照２ケース | 比較対象外 | 11/12 | 11/12 | 12/12 |
| 全96出力 | 比較対象外 | 94/96 | 95/96 | 96/96 |

その後の２回は完走前に停止した。`.tmp/interactive-topic-boundary-after-final/interrupted-rows.json` の31出力には、モデル容量不足１件と、Quint 名・ファイル名がないだけで B 固有要件を落とした判定の偽陰性１件があった。後者を修正した次の `.tmp/interactive-topic-boundary-final/interrupted-rows.json` の32出力には、Codex の英語 Grill Me 応答が前のタスク名を「別タスク」という切替宣言で再掲する実際の失敗１件があった。そこで対話テンプレートの末尾に、新タスクの成果物から直接話し始め、送信前に不要な旧話題への言及を除く手順を追加した。どちらの中断出力も、上表の初回96出力や最終成功率へ混ぜない。

末尾補強後の単一実行 `eval-iRz-2026-09-28T07:17:43` は20分８秒で96出力を完走し、エラー０件、元の promptfoo 採点は95/96だった。唯一の不合格は追加 `/tell` 対照の Codex 英語ケースで、本文には `src/features/caccia/`、CodeRabbit 指摘の取得・再チェック、受入条件の「未解決のレビューコメントがゼロ」が揃っていた。レビューで意味上の合格を確認し、CodeRabbit のレビューに限定した未解決コメントゼロを受理する判定を追加した。一般コメントのゼロ、未解決条件のないレビューコメント、任意の受入条件は合格させない。同じ96出力を再生成せずに最終判定で採点すると96/96で、Claude Opus と Codex Luna はそれぞれ48/48、比較可能な84出力は84/84、追加対照は12/12となる。変更前の60出力と調査24出力も同じ最終判定で再採点し、総合53/84のままだった。`input-integrity.json` で単一実行の34種類の入力ハッシュが不変であることを確認した。元の95/96と判定補正後の96/96は、異なるモデル実行の結果ではない。

集計の元は `.tmp/interactive-topic-boundary-after-response-check/` 内の `baseline-topic-rescored.json`、`baseline-research-rescored.json`、`final-rescored.json` である。各ファイルは保存済み生成出力を同じ最終判定で再採点した記録で、意味判定の既存結果を再利用し、判定モデルへの再問い合わせはしていない。

## 再現と限界

候補版の評価コマンドは `npm run eval:prompts:interactive-topic-boundary`。`TAKT_INTERACTIVE_EVAL_OUTPUT_DIR` を指定すると、採点前の生成本文・入力・モデル・ケース変数を別ファイルで保存する。基線のローカル `.tmp/` 出力は Git 管理対象外なので、上記の集計値と現行 suite だけでは変更前のモデル出力を再生成せずに検算できない。

評価は固定会話履歴をテキストとして再生し、外部ツールを使わせない隔離環境で行う。プロバイダーの実セッションで複数タスクを連続相談する操作そのもの、実際の `/go` 実行や `/tell` 送信は測っていない。候補版と基線に同じ再生制約を使い、ツール呼び出しや調査結果の模擬を禁止するが、それだけで実セッションの挙動を保証しない。変更後の `/tell` ケースには本番組み立てに合わせて選択送信先の名前と短い要約を生成入力へ加える。追加対照では先行タスクを宛先にする。要約には正答の要件を埋め込まない。

PR の CodeRabbit 指摘を受け、日英の両 `/tell` fixture について評価入力の `USER` 全文と本番ビルダーの出力が完全一致する契約を追加した。`SYSTEM` 部分の既存検査も維持し、再レビューでは `runTellCommand` が実際にプロバイダーへ渡す `SYSTEM` 全文を日英それぞれで検査した。これらのテスト追加は生成入力を変更しない。

既存回帰の記録は、最終 unit 401ファイル・6268件合格で終了コード０、末尾補強後のビルド・lint合格、light IT 163ファイル・2665件合格で終了コード０、E2E 19件合格・１件スキップ、OpenCode 11件合格（`ASDF_NODEJS_VERSION=22.22.1` が必要）、既存 Gherkin 評価５件が変更前後とも合格、既存生成プロンプト78件のハッシュ一致である。light IT には `birpc` の `onTaskUpdate` timeout 警告があった。ローカルでは既存の `dangerouslyIgnoreUnhandledErrors` 設定により非致命だが、CI では致命的に扱われる設定である。６テンプレートの先頭コメントと変数宣言は変更前から不変である。

既存 eval 契約は変更前337/339、変更後358/360で、同じ２件が失敗した。対象は `coding-review-metrics` の in-place mutation 判定と、`instruction-research-handoff` の日英 summary 文面に対する「ワークスペースを実際に調査」正規表現の不一致である。今回のテンプレート変更による新たな失敗として数えない。

既存 suite の確認範囲は、決定的な契約テスト全件、生成済みプロンプト78件のハッシュ比較、タスク指示書の Gherkin 実モデル評価５件である。builtins を対象とする既存 suite の実モデル評価をすべて再実行したわけではない。本変更の評価では、コード・テンプレート・評価の敵対レビューを繰り返し、共通境界の適用、`/tell` 宛先配線、調査権限、受入表現の判定、対話継続の識別、切替宣言の漏出を順に点検した。往復回数の厳密な監査はしておらず、回数を品質指標としては使わない。

# 実装完了・再計画のスコープ判定

## 現行方針

採用済み計画が有効で、実装・計画内の調査・必須検証に実行可能な不足が
残る場合は `implement → reimplement` とし、補完後も不足があれば
`reimplement` を繰り返す。レビュー修正では原因が未確認でも計画内の
具体的な調査を `fix` の最初の修正単位として実行し、`investigate` は
独立stepとして持たない。計画の前提・範囲・方法・検証能力を変えなければ
要求を実行・検証できない場合だけ `need_replan` とする。外部操作だけが
残る場合は既存の対話入力候補が利用でき、かつ回答で作業を進められる場合
に限って入力を求め、非対話時や回答で解決できない権限・設備不足は停止する。

`eval/cases/development-loop-handoffs.yaml` と
`completion-scope-routing.yaml` の期待値はこの現行グラフに合わせて固定する。
過去の比較結果と保存済み応答は、変更前の `investigate` や自己loopを含む
履歴として扱い、現行成功率には流用しない。

## 問題と変更

要求に必要な実装と検証が完了していても、レポートの総括が無関係な既存失敗を「完了不可」と扱うと、そのラベルを引き継いで再計画する。再計画も、実行可能な未試行作業というだけで要求外の修正へ戻り得る。

実装・再計画の条件を、今回の要件・変更契約に必要な作業へ限定した。無関係な既存失敗・対象外作業は実行結果として残し、完了への影響と根拠を別に引き継ぐ。変更が依存・影響拡大・新規露出する既存問題、明示された必須検証、新規回帰、必要な原因調査は除外しない。

## 評価方法

- `completion-scope-routing`: 本番の `StatusJudgmentBuilder` のタグ形式。
- `completion-scope-structured`: 同じ builder の構造化応答形式。Codex SDKへルール番号と理由のJSON Schemaを渡す。
- 同じ固定レポート16件を日本語・英語の判定条件で評価する。期待値はルール番号で、プロンプト本文へは渡さない。
- モデルは `gpt-6-astra`、reasoning effortは `medium`、同時実行数2、キャッシュ無効。
- 条件は同梱YAMLから読み、任意の変更前比較では完全なcommit SHAを指定する。評価用に条件文を複製しない。
- レポートには、事実と矛盾する完了ラベル・要求外の再計画案を含むケースもある。ラベルへの追従と、要求・因果関係に基づく判断を区別する。

## 2026-09-09のRED/GREEN

変更前の基点: `52d5019e59482972f6eee88e5d1f1bf446d9efb4`。

| 形式 | RED | GREEN |
|------|-----|-------|
| タグ | 未完了ラベル・再計画ラベルの4件全てが誤判定 | 同じ4件を含む32件全て成功（30件と変更不要2件の2実行） |
| 構造化応答 | 同じ4件のうち英語の再計画1件が誤判定 | 同じ4件を含む32件全て成功 |

構造化応答のREDでは「要求達成には不要ですが、プロジェクト内で実行可能な未試行の変更と検証手順が具体化されているため」として実装へ戻った。GREENでは要求外の計画だけで実装へ戻さない。

RED/GREENの対象レポート・期待値とprovider設定の同一性を保存結果で照合済み。タグREDを確認してから本番プロンプトを編集し、構造化応答でも変更前のGit版からの比較を追加した。

評価ID:

- タグGREEN（30件）: `eval-Ulb-2026-09-09T07:19:10`

## 実行

```sh
npm run build
npm run eval:prompts -- completion-scope-routing --no-cache
npm run eval:prompts -- completion-scope-structured --no-cache
npm run eval:prompts -- completion-scope-structured --no-cache --var baseline_revision=52d5019e59482972f6eee88e5d1f1bf446d9efb4 --filter-pattern '未完了ラベル|再計画ラベル'
```

これは固定レポートに対するPhase 3の意味評価であり、実装・レポート生成を含むrun全体の収束保証ではない。実行中runに保存済みのworkflow bundleは、このソース変更だけでは更新しない。

実装担当の編集・コマンド実行による範囲拡大は、[実装行動の評価](implement-scope-actions.md)で別に確認する。そちらでは行動側のREDは再現していない。

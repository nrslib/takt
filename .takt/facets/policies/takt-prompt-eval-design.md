# eval 設計の判定

採点の都合ではなく、実際の振る舞いで変更前後を比較できる評価を作る。

## 原則

| 原則 | 基準 |
|------|------|
| 実際の構造 | 実行記録で誤った判断を誘った構造を fixture に保つ |
| 中立な課題 | 要求だけを渡し、解法や分析結果を漏らさない |
| 意味の採点 | 名前・見出し・定型句より振る舞いを判定する |
| 対になる要求 | 規則が当てはまる要求と当てはまらない要求を対にする |
| 条件の一致 | 比較する文面以外の入力・採点・モデル設定をそろえる |

## 評価対象と採点

| 基準 | 判定 |
|------|------|
| 欠陥を示すコメントや中身のない実装が手掛かりとなり、変更前の文面でも正解できる | REJECT。実際に誤った判断を誘った構造を再現できていない |
| 課題に原因分析や、正しくはどの部分が処理を担当すべきかを書いている | REJECT |
| 元の事例とは別のドメインで規則が当てはまる例がないのに、汎用性を主張する | REJECT |
| 見出し、ID、特定名への言及だけで合否を決める | REJECT |
| 出力だけを読む採点に、生成ファイルの正しさを判定させる | REJECT。成果物を読む assert と分ける |
| 正しい実装を合格にし、代表的な誤った実装を不合格にする対照例がある | OK |
| 維持を求める記述や既存テストの実行を、新しい要件の追加として扱う | REJECT |

## 実行条件

| 基準 | 判定 |
|------|------|
| 他の fixture、リポジトリ本体、採点コードが正解の手掛かりになる | REJECT |
| プロンプト、作業ディレクトリ、課題の参照先が同じケースを指さない | REJECT |
| 本番では省略される長文や出力契約を、評価だけで全文追加する | REJECT |
| 時間切れや grader 障害をモデルの規則違反に数える | REJECT |
| ファイルを編集する評価で、前回の生成物を次の独立した試行へ使い回す | REJECT |
| 新しい評価方式を必要とせず、既存基盤の設定・fixture・採点で測れる | OK |

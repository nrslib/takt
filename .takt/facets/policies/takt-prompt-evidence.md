# プロンプト改修の証拠

元の記録でプロンプトの問題と評価の仕組みの問題を区別し、測定で裏付けられた範囲だけを主張する。

## 原則

| 原則 | 基準 |
|------|------|
| 一次情報 | イベント、モデル出力、採点理由、終了理由を照合する |
| 再現性 | 同じ条件の独立した実行を比較する |
| 範囲の維持 | 許された修正だけを行い、製品機能へ広げない |
| 独立した承認 | 実装したセッションに承認を任せない |
| 比較の誠実さ | 変更前の合格を改善の証拠にしない |
| 記録の保持 | 不合格と未確認を成功した実行で置き換えない |

## 元の記録の確認

| 基準 | 判定 |
|------|------|
| 抜粋、要約、合格率、報告の自己申告だけで原因を断定する | REJECT |
| 元ファイルを開き、要求・出力全文・イベントの前後関係・終了理由を照合する | OK |
| 元ファイルを入手できないまま、原因を推測で決める | REJECT。原因は不明として必要な証拠を示す |
| 短い引用と元の記録の位置を添え、確認した範囲を明示する | OK |

## 単発の失敗と繰り返す失敗

失敗を修正の根拠にするには、次の条件をすべて満たす必要がある。

- ケース、provider、モデルが同じである
- 文面、fixture、採点基準、実行設定が同じである
- 独立した2回の実行で、同じ流れの失敗が連続している

| 基準 | 判定 |
|------|------|
| 初回の不合格だけを理由に文面や評価を直す | REJECT。条件を変えずに再測定する |
| 同じ失敗が2回続き、モデルの行動が規則に反した元の記録がある | プロンプトの穴 |
| 同じ失敗が2回続き、行動は正しいのに、採点・設定・制限時間・ハーネスが原因で不合格になった記録がある | eval の不備 |
| 再測定が合格、または別の失敗の流れになった | 直ちに直さない。連続回数を分けて記録する |
| キャッシュ応答の再採点だけを2回目に数える | REJECT |

時間切れでは、その時点までの行動、最後のイベント、設定された上限を確認し、何が処理を止めたかを調べる。正しい行動の途中で評価側が止めた記録を、プロンプト違反に読み替えない。

## 変更前の合格

| 基準 | 判定 |
|------|------|
| 変更前でも合格したケースを改善効果に数える | REJECT |
| 実際の失敗を誘発した構造に fixture を近づけ、両条件を再測定する | OK |
| 変更前後で結果が分かれないことを「回帰ガード」と明記する | OK。改善の根拠には数えない |
| 変更前を不合格にするために答えを課題へ追記する、採点基準を変更前だけ厳しくする | REJECT |

## 承認と範囲

| 基準 | 判定 |
|------|------|
| 根拠のない好みだけで修正を必須にする | REJECT |
| 指摘に元の記録・正しく扱えなくなる要求や反例・修正条件がある | 修正が必要か判断できる |
| 許可範囲外の製品変更が必要と分かっても実装を続ける | REJECT。必要性と未実施事項を報告して停止する |
| 既存の評価基盤の修正を超え、新しい評価方式を作る | REJECT。別タスクに必要な理由を残す |
| 部分再実行の合算を最終の全件測定とする | REJECT |
| 最後の文面で、対象スイート・全 provider を一括して測定する | OK |

# プロンプト評価の知識

## 本番の入力と評価の入力

評価が再現する範囲はハーネスごとに異なる。通常の単一段階の評価と、報告・複数ターンの評価は別の契約を持つ。

| 材料 | 評価で確認する性質 |
|------|----------------------|
| persona | system を含めた組み立て方法 |
| policy・knowledge | 本文の先頭だけを載せ、残りを元ファイル参照にする境界 |
| instruction | 本番で解決される include と workflow の facet 参照 |
| output contract | 通常の Phase 1 評価には入らず、Phase 2 で使われる形式 |
| fixture | 本体や別ケースを読めない隔離と、正解の漏れ |
| 採点 | 出力だけを見る rubric と、成果物を読む assert の違い |

現行の通常 prepare は policy・knowledge の先頭2000文字を本文に載せ、残りを snapshot の Source Path にする。本番との差を隠すために評価だけ全文へ変えると、規則の到達性を比較できなくなる。各スイートが同じ契約かは実装で確認する必要がある。

## fixture と課題の強さ

不具合を露骨に示す fixture と、解法を含む課題は、変更前でも通りやすい。

| 形 | 判断材料 |
|----|----------|
| 悪い例: 欠陥をコメントで名指しする | モデルの一般知識だけで正解できる |
| 良い例: 初回計算を通常のヘルパーの奥へ置く | 実行記録にあった読み替えを誘う |
| 悪い例: 課題へ「同一実体を前後で観測」と追記する | 追加規則の答えを漏らす |
| 良い例: 元の要求と同じ抽象度と項目数を保つ | 実際の注意配分に近い |

純粋な変換、呼び出しごとの新しい結果、再起動後の永続化、既存動作の維持は、誤発火を探す対照になる。異なるドメインの発火例は、事故の語に依存していないかを調べる材料になる。

## 原記録と結果ファイル

結果 JSON には応答と採点理由があっても、途中のツールイベントや終了理由がない場合がある。

| 記録 | 分かること |
|------|------------|
| 結果 JSON | ケース、provider、出力、採点、エラー |
| 試行の生記録 | 実行イベント、途中の出力、停止理由、実際の作業成果物 |
| prepare の snapshot | 実際に読まれた文面とファイル参照 |
| 実行ログ | コマンド、設定、終了コード、prepare の失敗 |

結果の先頭だけでは、末尾で方針を訂正した応答や制限時間による停止を見分けられない。DB の最新行だけを選ぶと、別の再実行を比較に混ぜることもある。実行ごとの保存先と eval ID は、原記録を対応付ける手掛かりになる。

通常 CLI の比較では、各結果行の `response.metadata.execution_record` が試行の記録ディレクトリを指す。
`identity.json` のラベル・変数・言語・0始まりの `repeatIndex` と eval ID が、その行との対応を示す。
`prompt.md` は provider が受け取った最初の入力で、作業パスの書き換え前の文面であり、後続ターンの送信入力は含まない。
`result.json` は最終応答またはエラー、`process-N.stdout` は生のイベント列と途中出力、
`process-N.stderr` は診断である。`process-N.json` にはコマンド・作業場所・上限時間・終了コード・シグナル・
`timedOut`・`aborted`・中断理由が入る。生ストリームは先頭16 MiBまでで、超過は `truncated` に記録される。
fixture は記録の有無にかかわらずリポジトリ外の一時ディレクトリで実行する。
試行終了後に同じ記録内の `project-N/` へコピーしてから一時ディレクトリを削除するため、
Git の親探索による元の checkout の参照を避けつつ、失敗した時点の報告や生成物も一か所で確認できる。
`project-N.json` が実行時の `cwd` とコピー先の `snapshotDirectory` を対応付ける。
コピー前の強制終了やコピーの失敗では、外部の作業場所が残る場合がある。

比較の `manifest.json` は red/green とスイートごとの workspace・結果 JSON・raw の絶対パスを持つ。
プロンプトは各 workspace の `eval/prompts/`、参照 snapshot はプロンプト内の Source Path、
生成物はその実行の `.work` や fixture、隔離した `project-N/` に残る。
各スイートに専用のコピーがあるため、後の prepare で変更前の資料が変更後へ置き換わることはない。

タイムアウトは `timedOut` と終了情報、生出力の末尾を照合すると、評価側の停止とモデルの違反を区別できる。
比較全体の中断は `manifest.interrupted` に残る。強制終了で試行やプロセスの状態が `running` のままなら、
正常終了とは解釈できない。途中で切れたログや記録未対応の provider では、残った資料だけで判定できる範囲に限界がある。

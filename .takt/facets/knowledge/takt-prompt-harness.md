# プロンプト評価の知識

## 本番の入力と評価の入力

評価が再現する範囲はハーネスごとに異なる。通常の1段階の評価と、報告や複数ターンを扱う評価では、入力や出力の条件が異なる。

| 材料 | 評価で確認する性質 |
|------|----------------------|
| persona | system を含めた組み立て方法 |
| policy・knowledge | 本文の先頭だけを載せ、残りは元ファイルへの参照に切り替える位置 |
| instruction | 本番で解決される include と workflow の facet 参照 |
| output contract | 通常の Phase 1 評価には入らず、Phase 2 で使われる形式 |
| fixture | リポジトリ本体や別ケースを読めないように隔離されているか、正解が漏れていないか |
| 採点 | 出力だけを見る rubric と、成果物を読む assert の違い |

現行の通常 prepare は policy・knowledge の先頭2000文字を本文に載せ、残りは snapshot の Source Path で参照する。本番との差を隠すために評価だけ全文を載せると、必要な担当が規則を読めるかどうかを比較できなくなる。各スイートの条件が同じかは、実装で確認する必要がある。

## fixture と課題の強さ

不具合を露骨に示す fixture や、解法を含む課題は、変更前の文面でも合格しやすい。

| 形 | 判断材料 |
|----|----------|
| 悪い例: 欠陥をコメントで名指しする | モデルの一般知識だけで正解できる |
| 良い例: 初回の計算を通常のヘルパーの内部に置く | 実行記録にあった読み替えを誘う |
| 悪い例: 課題へ「同じ実体を変更の前後で観測する」と追記する | 追加する規則の答えを漏らす |
| 良い例: 元の要求と同じ抽象度と項目数を保つ | 実際の注意配分に近い |

純粋な変換、呼び出しごとの新しい結果、再起動後の永続化、既存動作の維持は、当てはまらない要求に規則が誤って適用されないかを調べる対照例になる。別のドメインで規則が当てはまる例は、元の事例に特有の言葉に依存していないかを調べる材料になる。

## 元の記録と結果ファイル

結果 JSON には応答と採点理由があっても、途中のツールイベントや終了理由がない場合がある。

| 記録 | 分かること |
|------|------------|
| 結果 JSON | ケース、provider、出力、採点、エラー |
| 試行をそのまま保存した記録 | 実行イベント、途中の出力、停止理由、実際の作業成果物 |
| prepare の snapshot | 実際に読まれた文面とファイル参照 |
| 実行ログ | コマンド、設定、終了コード、prepare の失敗 |

結果の先頭だけでは、末尾で方針を訂正した応答や制限時間による停止を見分けられない。DB の最新行だけを選ぶと、別の再実行を比較に混ぜることもある。実行ごとの保存先と eval ID は、元の記録を対応付ける手掛かりになる。

通常 CLI の比較では、各結果行の `response.metadata.execution_record` が試行の記録ディレクトリを指す。

| ファイル | 記録される内容 |
|----------|----------------|
| `identity.json` | ラベル・変数・言語・0始まりの `repeatIndex`。eval ID と合わせて結果行との対応を示す |
| `prompt.md` | provider が受け取った最初の入力。作業パスを書き換える前の文面で、後続ターンに送った入力は含まない |
| `result.json` | 最終応答またはエラー |
| `process-N.stdout` | 加工前のイベント列と途中の出力 |
| `process-N.stderr` | 診断情報 |
| `process-N.json` | コマンド・作業場所・上限時間・終了コード・シグナル・`timedOut`・`aborted`・中断理由 |
| `project-N.json` | 実行時の `cwd` とコピー先の `snapshotDirectory` の対応 |

加工前のストリームを保存するのは先頭16 MiBまでで、上限を超えたことは `truncated` に記録される。

fixture は記録の有無にかかわらず、リポジトリ外の一時ディレクトリで実行する。試行が終わると、同じ記録内の `project-N/` へコピーしてから一時ディレクトリを削除する。
これにより、Git が親ディレクトリをたどって元の checkout を参照するのを避けつつ、失敗した時点の報告や生成物も一か所で確認できる。
コピー前に強制終了した場合やコピーに失敗した場合は、リポジトリ外の作業場所が残ることがある。

比較の `manifest.json` は、red/green とスイートごとに workspace・結果 JSON・raw の絶対パスを持つ。各実行の資料は次の場所に残る。

| 資料 | 保存先または参照先 |
|------|--------------------|
| プロンプト | 各 workspace の `eval/prompts/` |
| 参照する snapshot | プロンプト内の Source Path |
| 生成物 | その実行の `.work` や fixture、隔離した `project-N/` |

各スイートに専用のコピーがあるため、後の prepare で変更前の資料が変更後の資料に置き換わることはない。

タイムアウトでは、`timedOut` と終了情報、加工前の出力の末尾を照合すると、評価側が止めたのか、モデルが規則に違反したのかを区別できる。
比較全体の中断は `manifest.interrupted` に残る。強制終了で試行やプロセスの状態が `running` のままなら、正常終了とは解釈できない。
ログが途中で切れた場合や、provider が記録に対応していない場合は、残った資料だけで判定できる範囲に限界がある。
